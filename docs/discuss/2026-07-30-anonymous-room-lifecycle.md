# FileDock 匿名会话与房间生命周期讨论记录

## 原始需求

> 根据 `docs/first/LanShare_PRD.md` 文档规划，给出下一阶段实现功能规划，对于不清楚的问题一定要询问我。

用户接受的阶段范围是：实现匿名会话、匿名用户身份、完整房间生命周期，以及本阶段房间功能依赖的全局 SSE；暂不实现文件上传下载和聊天。

用户补充约束：

- 数据库表通过 GORM `AutoMigrate` 创建或更新。
- 计划会交给低智能编码模型执行，因此规格必须具体、无歧义，并明确状态、边界、接口与验收标准。
- 项目处于开发阶段，不需要兼容尚未发布的旧表结构或旧错误码。
- 所有面向用户的功能必须同时支持简体中文（`zh-CN`）与 English（`en`）。

## 问答记录

### 1. 下一阶段范围是什么？

**问题：** 下一阶段是否只实现匿名会话与基础房间，还是把完整房间生命周期和当前房间依赖的 SSE 一并实现？

**推荐答案：** 实现匿名会话、昵称、房间创建与加入、成员管理、三种准入方式、延期、解散、清理，以及这些功能依赖的全局 SSE 和基础页面；文件、聊天和文件相关 SSE 后移。

**用户回答：** 接受该范围。

### 2. 数据库建表方式是什么？

**问题：** 本阶段新增数据表是否通过 GORM 自动建表？

**推荐答案：** 使用 GORM `AutoMigrate`，服务启动时在对外监听前完成；失败则启动失败。

**用户回答：** 确认，通过 GORM AutoMigrate 实现。

### 3. 会话令牌和匿名用户分别解决什么问题？

**问题：** 浏览器打开页面即可创建或加入房间时，服务端如何稳定标识用户？会话令牌是否就是匿名用户身份？

**推荐答案：** 服务端为浏览器创建持久匿名用户记录和会话记录；JWT Cookie 是浏览器证明自己对应哪个会话的凭证，用户 ID 才是稳定身份。刷新、重新打开页面和同一浏览器多个标签页均恢复同一匿名用户。

**用户回答：** 接受一个浏览器配置对应一个匿名用户的设计。

### 4. 一个匿名用户可以同时拥有或加入多少房间？

**问题：** 是否限制同一浏览器匿名用户只能创建一个房间且只能加入一个房间？

**推荐答案：** 最多拥有 1 个有效自建房间，同时最多加入 5 个其他有效房间，既避免滥用，也支持实际多房间使用。

**用户回答：** 确认。

### 5. Cookie 和 localStorage 哪个更适合保存令牌？

**问题：** `session_token` 是否应从 Cookie 改存 localStorage？

**推荐答案：** JWT 存在 `HttpOnly` Cookie；localStorage 中的令牌可被页面脚本读取，发生 XSS 时更容易被盗取。Cookie 可由浏览器自动携带，并通过 `HttpOnly`、`SameSite` 和 HTTPS 下的 `Secure` 降低风险。

**用户回答：** 确认使用 Cookie。

### 6. “活跃房间”是什么意思？

**问题：** 房间数量限制中的“活跃”是指用户在线，还是房间关系尚未结束？

**推荐答案：** 改称“有效”：房间未过期、未销毁，且用户成员关系仍有效；与用户当前在线、离线无关。

**用户回答：** 确认，改成“有效”更易理解。

### 7. JWT 为什么不放 Authorization 请求头？

**问题：** Cookie 与请求头的安全本质是否类似，选择 Cookie 是否主要为了统一浏览器会话处理？

**推荐答案：** 是。浏览器用户接口仅使用 `session_token` HttpOnly Cookie，避免前端保存和手工拼装令牌；Cookie 仍需防范 CSRF，因此采用 `SameSite=Lax`，写操作保持同源，并为后续增加来源校验留出边界。管理员接口未来可继续独立使用 Bearer Token。

**用户回答：** 确认。

### 8. 会话是否同时校验 JWT 和数据库？

**问题：** 只验证 JWT 签名是否足够？

**推荐答案：** 不足。JWT 验证签名、算法和有效期，随后根据其中的会话 ID 查询 SQLite，确认会话未撤销、未过期且仍属于该用户。这样可支持身份重置和主动失效。

**用户回答：** 确认。

### 9. 会话过期和续期规则是什么？

**问题：** 默认有效期、自动续期窗口及 Refresh Token 如何设置？

**推荐答案：** 默认 30 天；剩余有效期不超过 7 天时自动续期；不实现 Refresh Token。未来管理员可修改默认时长。

**用户回答：** 确认默认 30 天，不支持 Refresh Token；管理员调整默认时长记录到 `todo.md`。

### 10. 当前服务是否直接支持 HTTPS？

**问题：** “为 HTTP 服务增加可配置 HTTPS/TLS 能力”是 FileDock 自身监听 HTTPS，还是只写 Nginx 方案？

**推荐答案：** FileDock 原生支持用户提供的证书和私钥；两者均未配置时使用 HTTP，两者只配置一个时启动失败。反向代理仍可作为未来部署选项。

**用户回答：** 确认原生可配置 HTTPS。

### 11. 是否在本阶段自动生成自签名证书？

**问题：** 自动生成自签名证书会带来浏览器证书警告，是否首版实现？

**推荐答案：** 本阶段不生成自签名证书，只支持加载用户已有证书；自动生成和信任引导后续实现并记录待办。

**用户回答：** 确认，加入 `todo.md`。

### 12. HTTP 模式是否允许使用 PIN、JWT 和未来文件传输？

**问题：** 首版是否强制要求 HTTPS？

**推荐答案：** 不强制，局域网开发和首版允许 HTTP；必须在文档中明确 HTTP 下 PIN、Cookie 和未来文件内容可能被同网段监听。HTTPS 模式 Cookie 必须启用 `Secure`，HTTP 模式不能启用，否则浏览器不会发送。

**用户回答：** 确认首版允许 HTTP。

### 13. 文件下载权限未来如何约束？

**问题：** 获得下载地址的非成员能否直接下载？

**推荐答案：** 不能。未来下载必须同时满足当前仍是房间有效成员，以及当前用户是文件发送者或明确接收者；URL 不能作为授权凭证。

**用户回答：** 确认。

### 14. 服务端文件是否应加密保存？

**问题：** 暂不做端到端加密时，上传后的文件能否避免以可直接查看的明文形式落盘？

**推荐答案：** 后续文件阶段采用服务端流式加密落盘、下载时流式解密；不宣称为端到端加密，因为服务端持有密钥并能解密。

**用户回答：** 确认。

### 15. 大文件加密是否需要整文件驻留内存或额外占用双份空间？

**问题：** 例如 2 GiB 文件加密时，空间和内存如何变化？

**推荐答案：** 使用 1 MiB 独立加密块和流式处理，内存保持在少量块级缓冲；最终保存为一个物理密文文件，不拆成大量 1 MiB 文件。加密认证信息会增加少量空间，但不长期保留明文与密文双份文件。

**用户回答：** 确认。

### 16. 文件加密算法和密钥层级如何设计？

**问题：** 后续文件阶段采用什么算法、密钥和存储形式？

**推荐答案：** 使用 XChaCha20-Poly1305、1 MiB 独立块；每文件独立数据密钥，由首次运行自动生成的服务主密钥保护；文件仍保存为单一物理密文文件。上传和下载均流式处理，耗时会增加但不应形成明显的内存或磁盘瓶颈。

**用户回答：** 确认。

### 17. 并发限制应限制什么？

**问题：** “一个房间最大上传两个文件”是否会错误限制多人下载场景？

**推荐答案：** 上传与下载使用独立并发池。默认上传为全局 4、单房间 2、单用户 2；下载为全局 50、单房间 10、单用户 2。一个上传者不会消耗下载名额，十个接收者可在下载池范围内并发。

**用户回答：** 确认。

**推荐答案：** 后续文件阶段使用现有全局 SSE 推送排队位置和名额可用事件；收到名额后自动触发下载，若浏览器阻止自动下载则展示明确按钮。

**用户回答：** 确认。

**问题：** 上述参数现在是否开放配置或管理界面？

**推荐答案：** 先按固定默认值实现；管理员调整能力后续实现并记录待办。

### 20. 新匿名用户如何选择昵称？

**问题：** 是否预置《水浒传》一百零八将和《三国演义》人物名称，并允许随机或手工输入？

**推荐答案：** 未建立会话时显示名称输入框和骰子按钮，默认填入随机候选；点击骰子重新随机，用户也可手工输入。当前候选写入程序，管理员维护候选库后续实现。

### 21. 昵称唯一范围是什么？

**问题：** 昵称只需在房间内唯一，还是整个服务中的有效匿名用户全局唯一？

**用户回答：** 确认。

### 22. 昵称如何比较和校验？

**问题：** 如何避免大小写、Unicode 兼容字符、不可见字符造成视觉重名或恶意昵称？

**推荐答案：** 长度为 2～20 个 Unicode 字符；先执行 NFKC 归一化；英文比较忽略大小写；禁止控制字符、零宽字符、双向控制字符及系统保留名称。显示值和用于唯一比较的规范值分开保存。

**用户回答：** 确认。

### 23. 随机昵称候选全部占用时怎么办？

**推荐答案：** 先尝试人物名称，再生成类似 `张飞-1024` 的带四位数字名称，极端情况下使用类似 `访客-A7K9P2` 的随机兜底，并继续执行全局唯一校验。

**用户回答：** 确认。

### 24. 昵称修改如何影响已加入房间？

### 27. 房主能否退出房间？

**问题：** 房主关闭页面、退出成员关系或解散房间分别如何处理？

**推荐答案：** 房主不能退出成员关系，只能解散；关闭网页不改变房间和房主关系。再次打开页面后，首页恢复此前创建的有效房间，并可进入或解散。

**用户回答：** 确认。

### 28. 解散房间为什么需要短暂延迟？

**问题：** 原方案中的“等待 5 秒”用于什么？

**推荐答案：** 延迟窗口用于让所有成员收到通知、锁定页面，并给已经开始的小文件下载一次短暂完成机会；不是让房间继续接受操作。

**用户回答：** 保留延迟并改为 10 秒。

### 29. 房间解散状态机如何定义？

**问题：** 房主解散后的页面、下载、状态和清理顺序是什么？

**推荐答案：** 房间先进入 `destroying` 10 秒；禁止新操作、立即取消上传，已经开始的下载可继续。10 秒后进入 `destroyed`，强制停止未完成下载；随后在 10 秒～5 分钟的随机延迟后异步清理关联数据，分散多个房间同时清理造成的负载。

**用户回答：** 确认。

### 30. 房主和其他成员解散后的页面行为是否相同？

**问题：** 房主是否也停留 10 秒？

**推荐答案：** 不同。房主操作成功后立即退出房间并回首页；其他成员收到 SSE 后停留在被蒙层锁定的房间页，查看提示和 10 秒倒计时，倒计时结束后通过替换历史记录的方式回首页。

**用户回答：** 确认。

### 31. 自然过期是否复用解散流程？

**问题：** 房间自然到期时是否直接删除？

**推荐答案：** 自然过期也进入相同的 `destroying` 10 秒流程，只是 `reason` 不同，确保前端和后台状态机只有一套。

**用户回答：** 确认。

### 32. 房间号冷却多久？

**问题：** 被销毁房间的四位房间号何时可以重新使用？

**推荐答案：** 房间进入 `destroyed` 后冷却 10 分钟；关联数据清理完成且冷却期结束后才允许彻底删除占号记录并复用房间号。

**用户回答：** 确认。

### 33. 当前阶段是否提前实现 SSE？

**问题：** 原 PRD 将 SSE 放在后续阶段，但当前房间审批、在线状态和销毁体验大量依赖 SSE，是否应提前实现基础能力？

**推荐答案：** 本阶段实现全局 SSE 基础设施及成员、审批、延期、销毁、在线状态事件；文件、排队、聊天等事件后续接入。

**用户回答：** 确认。

### 34. SSE 使用一条全局连接还是按房间多条连接？

**问题：** 多房间、多个标签页时是否为每个房间建立 SSE？

**推荐答案：** 每个标签页只建立一条 `GET /api/v1/stream`；服务端根据事件类型、目标用户和目标房间推送，同一浏览器的多个标签页分别只有一条连接。

**用户回答：** 确认，不采用两条或多条业务 SSE 链路。

### 35. SSE 如何鉴权和分发？

**问题：** 全局 SSE 是否另传 Bearer Token？私有事件和房间事件发给谁？

**推荐答案：** 与普通用户 API 一样使用 `session_token` Cookie。私有事件发送给该用户的全部标签页；房间事件发送给该房间所有有效成员对应的全部连接。不得依赖前端传入房间 ID 决定越权订阅。

**用户回答：** 确认。

### 36. SSE 是否持久化并支持断线补发？

**问题：** 当前是否实现 `room_events`、事件序号和 15 分钟补发？

**推荐答案：** 本阶段不持久化 SSE 事件、不实现 `lastSeq` 补发。断线重连后，前端重新请求会话、首页或房间快照恢复权威状态。

**用户回答：** 确认。

### 37. 多个标签页如何计算在线状态？

**问题：** 同一浏览器打开多个标签页时，一个标签页关闭是否算离线？

**推荐答案：** 以用户全部 SSE 连接数计算：任一标签页连接即 `online`；全部连接断开立即变为 `away`；持续 60 秒仍无连接才变为 `offline`；任何标签页重连立即恢复 `online`。

**用户回答：** 确认。

### 38. 为什么使用一个统一在线状态事件？

**问题：** “统一事件比维护 online/away/offline 三种事件更容易扩展”是什么意思？

**推荐答案：** 只使用 `room.member_presence_changed`，由 payload 的 `status` 表达三态。将来增加新状态或字段时不需要增加事件类型和三套前端监听逻辑。

**用户回答：** 确认。

### 39. 房间页如何显示在线状态？

**问题：** 在线、暂离、离线的基础视觉是什么？

**推荐答案：** 成员信息旁用绿、黄、灰小圆点表达三态；本阶段保证语义和无障碍文本，具体视觉后续页面设计时微调。

**用户回答：** 确认。

### 40. 房主踢人后，被踢用户如何离开页面？

## 最终共同理解

1. 下一阶段交付匿名身份、会话安全、昵称、完整房间生命周期、三种房间准入、成员管理、全局 SSE、在线状态、异步清理和基础页面。
2. 本阶段不交付文件上传下载、文件落盘加密、下载排队、聊天、文件/聊天 SSE、事件持久化、断线补发和管理员页面。
3. 同一浏览器配置对应一个匿名用户，多标签页共享 Cookie、用户 ID 和房间关系；每个标签页仅建立一条全局 SSE。
4. JWT 只存于 `session_token` HttpOnly Cookie，并与 SQLite 会话记录双重校验；默认 30 天、剩余 7 天自动续期、不使用 Refresh Token。
5. HS256 密钥首次自动生成；存在有效会话但密钥文件丢失时服务启动失败。
6. 昵称在所有有效匿名用户中全局唯一，具有严格 Unicode 规范化和安全校验；随机候选与手工输入并存。
7. 一个用户最多拥有 1 个有效房间、加入 5 个其他有效房间；房间最多 50 个有效成员。
8. 房间默认标题是持久化的 `房间 <四位房间号>`，当前不可修改；房主不能退出，只能解散。
9. 房间支持 `open`、`password`、`owner_approval` 三种创建时确定且当前不可修改的准入方式。
10. PIN 固定四位数字并使用 bcrypt；审批默认等待 10 分钟，具有重复申请、冷却和容量限制。
11. 房主解散或自然过期均进入 `destroying` 10 秒，再进入 `destroyed`；房主立即回首页，其他成员看到锁定蒙层和倒计时后回首页。
12. 清理在房间销毁后随机延迟 10 秒～5 分钟，由单 worker 串行执行；自动最多尝试两次。
13. 房间号从进入 `destroyed` 起冷却 10 分钟，并且只有数据清理成功后才可复用。
14. 全局 SSE 仅为本阶段实时状态服务；不持久化事件，重连通过 REST 快照恢复。
15. 在线状态为 `online`、`away`、`offline`，统一通过 `room.member_presence_changed` 表达；多标签页按用户总连接数计算。
16. 当前 API 和业务错误全部迁移为五位错误码，成功仍固定 `200`；错误码、多语言键和 HTTP 状态保持稳定映射。
17. 普通 HTTP API 最终消息继续由后端根据 `Accept-Language` 翻译；SSE 只发送机器事件信息，由前端双语资源翻译。
18. 前端语言资源拆为独立 `zh-CN` 和 `en` 文件，并在构建时校验键结构一致；未知事件或缺译执行安全兜底和快照恢复。
19. FileDock 原生支持加载用户证书启用 HTTPS，但首版允许 HTTP，也不自动生成自签名证书。
20. 所有后续文件安全、并发和排队决定已经保留为未来文件阶段的明确约束，本阶段不提前实现文件接口。
