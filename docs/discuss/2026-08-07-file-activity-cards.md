# 文件动态操作卡片合并讨论

日期：2026-08-07

## 原始需求

当前一次文件操作会在“文件动态”中产生多条记录，尤其是上传、下载等场景，信息重复且占用空间较大。希望将同一次操作的多条事件合并为一张紧凑动态卡片，同时通过详情入口保留完整状态历史。用户补充询问：已经上传过的私密文件再次转发给他人时，应如何合并和展示。

## 逐项问答

### 1. 私密文件转发是否独立成卡片

问题：历史私密文件转发应作为独立的“转发操作卡片”，不与原上传卡片合并；每次点击发送生成新的操作标识。同一次批量选择多个文件时按文件分别生成卡片，同一文件一次发送给多个成员时合并为一张转发卡片，是否确认？

回答：确认。

结论：每次转发都是独立操作；多文件按文件分别展示；同一文件发给多人合并为一张卡片；再次转发同一文件也产生新卡片。

### 2. 转发卡片的接收者展示

问题：同一文件一次转发给多个成员时，主卡片是否只显示“已转发给 3 位成员”，具体成员名单放到三点详情中？

回答：确认。

结论：主卡片显示接收者数量，详情显示具体名单。

### 3. 转发操作是否显示开始状态

问题：当前转发是同步操作，是否直接生成“已转发”卡片；失败时生成“转发失败”卡片并记录失败原因，不额外显示“开始转发”？

回答：确认。

结论：成功直接进入完成态；失败显示失败态和原因。

### 4. 私密转发动态的可见范围

问题：是否采用最小披露原则：转发者看到真实文件名、数量和完整名单；接收者只看到自己是接收者，不看到其他接收者；房主只能看到私密文件编号和数量；其他成员看不到该动态？

回答：确认。

结论：按角色和参与关系进行字段级脱敏。

### 5. 部分接收者已存在时的结果

问题：一次选择多人转发时，只统计实际发生变化的接收者；已存在的接收关系在详情中标记为“已存在，无需重复转发”；全部无需变化时不创建动态卡片，是否确认？

回答：确认。

结论：卡片统计真实变更数量，跳过项只在详情或提示中说明；无变更不创建卡片。

### 6. 接受、拒绝是否和转发卡片合并

问题：接收者后续接受或拒绝时，是否回写原转发卡片，而不是创建独立的接受/拒绝卡片？

回答：用户确认接收者接收应和已转发卡片放在一起，因为这是一个转发文件的完整生命周期。

结论：转发卡片覆盖“转发 → 待接收 → 已接收/已拒绝”的完整生命周期。

### 7. 多人接收状态的主卡片展示

问题：多人转发时，主卡片是否显示聚合状态，例如“已转发给 3 位成员｜已接收 1｜待处理 1｜已拒绝 1”，详情按接收者展示状态时间线？

回答：确认。

结论：主卡片显示接收者状态数量；详情显示每名接收者的状态变化和时间。

### 8. 拒绝后再次转发

问题：接收者拒绝后，上传者再次转发同一文件时，是否保留原“已拒绝”卡片并创建新的转发卡片？

回答：确认，再次转发认为新的操作。

结论：再次转发使用新的操作标识，原生命周期不被覆盖。

### 9. 事件关联方式

问题：是否为每次文件操作增加独立 `operationId`；转发、接受、拒绝沿用同一个标识；再次转发生成新标识；原始事件保留并按标识聚合？

回答：确认。

结论：后端以“文件 + operationId”作为聚合边界，事件负载保存必要的接收者和状态事实。

### 10. 全局通知规则

问题：转发继续向接收者发送 `file_received` 通知；拒绝保留 `file_declined` 通知；接受不新增全局通知，只通过房间 SSE 更新卡片，是否确认？

回答：确认。

结论：全局通知保持必要提醒，接受状态只更新房间动态。

### 11. 下载与转发生命周期边界

问题：接收者接受后继续下载，是否生成独立下载卡片，不修改转发卡片？

回答：确认。

结论：转发生命周期结束于接收/拒绝；下载是独立操作，使用独立 `downloadTaskId`。

### 12. 下载中断和重试

问题：下载是否按一次 `downloadTaskId` 维护一张卡片，开始显示下载中，完成/失败/取消更新原卡片；重新点击下载创建新卡片；断点续传沿用原任务？

回答：确认。

结论：同一下载任务只维护一张卡片，新的下载任务不覆盖旧记录。

### 13. 三点详情交互

问题：是否支持桌面端悬停、点击、键盘聚焦，移动端底部抽屉；支持点击外部或 `Esc` 关闭；历史倒序；历史超过 50 条时加载更多？

回答：确认。

结论：详情只读，兼容鼠标、键盘和触摸；短历史一次加载，长历史分页。

### 14. 文件删除、恢复和永久删除

问题：文件进入回收站、恢复、永久删除后是否继续保留原卡片并更新状态？

回答：用户明确说明这些操作都属于新的独立动态，不能和上传、下载等卡片合并。

结论：删除、恢复、永久删除分别创建新的操作卡片；不修改上传、转发或下载卡片。

### 15. 文件和房间生命周期

问题：文件进入回收站、恢复、永久删除及房间失效后，动态卡片如何处理？

回答：确认采用以下规则：回收、恢复、永久删除是独立卡片；房间失效后动态停止展示并失效；原始事件保留至清理周期。

结论：文件实体消失时保留必要的“文件已永久删除”占位信息并执行隐私脱敏；房间失效后停止展示和 SSE 更新。

### 16. 模块与测试范围

问题：是否确认按后端事件写入、后端动态聚合、权限投影、SSE 更新、前端动态卡片、i18n 六个模块拆分；测试聚合状态机、多人转发状态、权限、分页排序和 SSE？

回答：确认。

结论：按上述模块实施；普通样式不单独编写测试，复杂业务状态编写行为测试。

## 最终共享理解

本次优化的核心是“按一次操作合并”，而不是按文件永久合并。后端保留 append-only 原始事件，并通过独立 `operationId` 将同一操作的状态事件聚合为一张卡片。上传、下载、转发、回收、恢复、永久删除都是不同操作；转发内部的接受/拒绝属于同一生命周期。前端展示最新状态，详情入口展示完整历史。卡片采用紧凑单行布局，移动端最多两行；私密文件按转发者、接收者、房主和其他成员进行字段级权限投影。状态变化通过 SSE 实时推送，所有面向用户的文案必须同时支持简体中文和 English。
