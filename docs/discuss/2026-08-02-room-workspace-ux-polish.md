# 房间工作区界面优化讨论记录

- 日期：2026-08-02
- 状态：已达成共识
- 讨论范围：成员栏当前用户信息、文件选择入口、文件列表拖放交互

## 原始需求

用户在人工测试房间页面后提出三个界面问题：

1. 左侧成员列表中，当前用户只通过昵称旁边较小的“（我）”标识区分，不容易第一眼确认自己的身份。用户希望参考 PC 端即时通讯软件的布局，在成员栏顶部直接展示当前用户的头像、昵称和在线状态。
2. 文件工作区顶部同时出现浏览器原生“选择文件”控件和现有“添加文件”按钮，形成重复入口。用户希望移除原生控件的可见外观，只保留现有风格的“添加文件”按钮。
3. 文件拖放只能在较小的虚线框内触发高亮，拖到共享文件或私密文件列表时没有反馈。用户希望整个文件列表内容区成为拖放目标，并在拖入文件时显示覆盖整个列表区域的接收浮层。

用户要求使用 `grill-me` 逐项确认优化设计，暂不直接修改生产代码。

## 代码核对结论

- 成员栏顶部当前只渲染“房间会话”“成员”和成员数量；当前用户身份仅在成员列表条目中通过“（我）”标识展示。
- 桌面成员侧栏和平板／移动端成员抽屉复用同一个成员面板组件，因此当前用户头部可以复用同一套结构和样式。
- 文件工作区保留了一个用于唤起系统文件选择器的原生文件输入框，并为其设置了 `visually-hidden` 类名；全局样式中没有定义该类，因此原生控件被直接显示。
- 现有“添加文件”按钮通过引用原生文件输入框触发系统文件选择器，不需要改变上传接口或文件选择流程。
- 当前拖拽状态和拖放事件只绑定在常驻虚线拖放按钮上，文件分组与文件行并不是拖放目标。
- 释放文件后，现有流程会把文件加入待发送区；用户仍需选择共享或私密范围，私密文件还需选择接收者，最后确认发送。拖放不会直接开始上传。

## 完整问答记录

### 问题 1：成员栏顶部是否增加独立的当前用户身份卡，同时保留原来的标题？

初始推荐答案：在成员标题下增加当前用户身份卡，展示头像、昵称、在线状态和“我”标签，并保留成员列表中的“（我）”标识。

用户回答：不保留“房间会话”和“成员”标题。直接在原标题所在位置显示当前用户的头像、昵称和在线状态，右侧成员数量继续保留。

### 问题 2：当前用户是否继续出现在下方成员列表中，并保留“（我）”标识？

推荐答案：保留。顶部信息用于第一眼确认身份，成员列表标识用于说明自己在成员列表中的位置。

用户回答：确认，继续保留。

### 问题 3：拖放浮层是否覆盖文件列表内容区，但不遮挡顶部标题、操作按钮、搜索和筛选栏？

推荐答案：浮层覆盖从拖放提示到共享／私密文件列表底部的整个可视内容区，顶部工具栏和筛选栏保持可见。

用户回答：提出疑问，如果这样设计，是否会与点击文件列表产生冲突。

### 问题 4：是否采用“仅外部文件拖入时激活、浮层不拦截交互”的方案？

推荐答案：仅当拖拽数据包含外部文件时显示浮层；正常状态不渲染浮层；浮层使用 `pointer-events: none`；拖放事件由外层列表容器接收；使用拖拽层级计数避免经过子元素时闪烁。普通点击、滚动、菜单和批量选择不受影响。

用户回答：确认，并补充希望移除现有虚线拖放框。文件列表顶部只显示一条提示信息；顶部“添加文件”按钮用于手动选择，下面的文件列表区域只用于拖放添加。

### 问题 5：常驻拖放提示是否使用“将文件拖放到列表区域添加”？

推荐答案：使用“添加”而不是“上传”。释放文件后仍会进入待发送区，并不会立即上传，使用“上传”容易造成错误预期。英文对应为“Drop files onto the list to add them”。

用户回答：确认。

### 问题 6：平板和移动端成员抽屉是否也显示新的当前用户头部？

推荐答案：显示。桌面成员侧栏和移动端成员抽屉复用相同的身份识别方式，并继续保留右侧成员数量。

用户回答：确认。

### 问题 7：手机窄屏是否隐藏常驻拖放提示？

推荐答案：隐藏。手机通常不支持系统文件拖放，继续保留顶部“添加文件”按钮即可，避免展示无效操作说明。

用户回答：确认。

### 问题 8：切换到“文件动态”页面后是否仍然接受拖放？

推荐答案：不接受。拖放能力明确属于文件列表区域；文件动态只负责查看操作记录，用户仍可通过顶部“添加文件”按钮选择文件。

用户回答：不接受。

### 问题 9：文件真正拖入列表区域后，浮层是否使用“释放文件以添加”文案？

推荐答案：使用该短文案，配合上传图标和浅绿色半透明背景；不展示文件名或文件数量，避免浏览器之间的拖拽数据读取差异。

用户回答：确认。

## 追加讨论：全局顶栏与房间信息层级

完成第一轮讨论和 PRD 后，用户对比首页与房间页截图，提出两个页面的顶部区域应采用统一风格。该决定覆盖第一轮“成员栏顶部显示当前用户信息”的方案。

### 问题 10：当前用户信息移到房间顶栏右侧后，左侧成员栏顶部如何处理？

初始推荐答案：成员栏只显示“成员”和成员数量，不再显示“房间会话”；当前用户继续在列表中显示“（我）”。

用户回答：进一步考虑房间页顶栏左侧也应与首页统一，保留项目 Icon、名称和 Slogan；当前房间名称应移动到左侧成员栏。

### 问题 11：顶部左侧品牌区域是否整体可点击返回首页，并取消独立返回箭头？

推荐答案：确认。统一品牌入口，同时保留返回首页能力。

用户回答：确认，并补充希望把顶栏三个点改为分享 Icon。

### 问题 12：左侧成员栏是否继续显示“成员”和成员数量？

推荐理解：顶部显示房间信息，下方进入成员列表。

用户回答：成员数量已经在顶栏中间显示，左侧不再重复；“成员”文字也去掉，用户可以直接理解下方是成员列表；成员列表必须标识当前房间的房主。

### 问题 13：分享 Icon 是否作为真正分享入口，并将原二维码能力合并？

推荐答案：分享 Icon 打开包含二维码、复制房间号、复制链接和复制邀请信息的分享区域；独立二维码 Icon 取消。原延期、解散和退出操作移入用户菜单。

用户回答：认可分享不应只有二维码，也应支持链接加入；认可推荐方向，但担心把房间操作移入个人菜单后会影响用户菜单语义。

### 问题 14：头像菜单是否使用“个人／房间操作”两个平铺分组？

初始推荐答案：通过分组区分个人能力和房间能力，危险操作固定在底部。

用户回答：不采用平铺分组。现有个人菜单继续保持一级结构；进入房间后新增一个一级菜单“房间操作”，其下包含“延期房间”和“解散房间”两个二级菜单。

### 问题 15：普通成员是否也显示一级菜单“房间操作”？

推荐答案：显示，但二级菜单只包含“退出房间”。

用户回答：确认。

### 问题 16：加入链接是否只包含房间地址，不携带密码或审批凭证？

推荐答案：链接使用当前服务地址与房间路由；打开后仍执行原有开放加入、PIN 验证或房主审批流程。

用户回答：确认。

### 问题 17：分享内容是否使用桌面浮层、移动端底部面板？

初始推荐答案：桌面在分享图标下方打开浮层，移动端使用底部面板。

用户回答：桌面端继续保持现有 Modal 弹窗形式更好。

### 问题 18：移动端是否继续沿用现有底部 Modal 形式？

推荐答案：确认。桌面居中，移动端从底部弹出。

用户回答：确认。

### 问题 19：房间顶栏右侧最终顺序是否为“分享、通知、头像、昵称、下拉箭头”？

推荐答案：从左到右依次为分享 Icon、通知 Icon、用户头像、用户昵称和下拉箭头；独立二维码、独立语言选择和三个点全部取消。

用户回答：确认。

### 问题 20：普通成员是否显示通知 Icon？

初始推荐答案：始终显示；房主可操作，普通成员禁用，以保持结构稳定。

用户回答：通知 Icon 应理解为全局通知。普通成员当前所在房间没有通知，不代表他没有自己创建的房间或收不到自己房间的审批消息；既然顶栏是全局通用顶栏，通知也应属于全局用户上下文。

### 问题 21：全局通知 Icon 是否始终可点击，无通知时显示空状态？

推荐答案：确认。现有规则限制一个用户最多拥有一个有效自建房间，因此可根据用户自建房间获取审批申请，不需要多房间聚合接口。

用户回答：确认。

### 问题 22：房主在成员列表中如何显示？

初始推荐答案：在昵称后显示独立的“房主”和“我”标签。

用户回答：房主不使用文字标识；考虑在头像左上角显示三角形区域，或使用“房主”角标。

### 问题 23：是否采用“金色三角角标＋皇冠图标”的房主标识？

推荐答案：确认。纯色三角不够明确，文字角标受中英文长度影响；皇冠提供视觉语义，同时使用 Tooltip 与无障碍标签表达“房主／Owner”。当前用户仍通过昵称旁“我”标识。

用户回答：确认。

### 问题 24：本期是否只把加入审批改为全局通知，不同时增加文件和聊天通知？

推荐答案：本期只复用现有加入审批，未来再扩展通知类型。

用户回答：完整全局通知功能放到后续实现。

### 问题 25：全局通知延期后，本期通知采用什么过渡行为？

推荐答案：首页保留现有自建房间审批通知；房间页保留当前房间审批通知，仅当前房间房主可操作；普通成员看到禁用 Icon；不提取全局查询或修改后端；在 `todo.md` 记录全局通知中心。

### 问题 26：手机窄屏的全局顶栏如何精简？

推荐答案：显示 FileDock 图标与名称，以及分享、通知和头像；隐藏 Slogan、用户昵称和下拉箭头；品牌仍可返回首页，头像仍可打开菜单。

用户回答：确认。

### 问题 27：“复制邀请信息”使用什么内容？

推荐答案：包含邀请语、房间名称、房间号和加入链接；根据界面语言生成中文或英文；不包含密码、审批状态和邀请人昵称。

用户回答：确认。

### 问题 28：房间页个人信息是否与首页使用同一个 Modal？

推荐答案：完全复用首页个人信息 Modal，包括修改昵称、注册时间、服务版本和受现有规则约束的重置身份。

用户回答：确认。

### 问题 29：左侧房间信息区如何排列？

推荐答案：主要文字显示房间名称，单行省略并通过 Tooltip 显示完整值；次要文字显示房间号和复制按钮；不显示“房间会话”“成员”和成员数量；下方直接进入成员列表；抽屉复用同一布局。

### 问题 30：首页与房间页顶栏统一到什么程度？

推荐答案：共用内容组件、品牌区、高度、头像、字体、图标、间距、菜单和响应式规则；首页保留浅灰页面背景与最大宽度，房间页保留白色固定顶栏和底部分隔线，不强行统一页面外壳。

用户回答：确认。

## 最终共享理解

### 全局顶栏

- 首页和房间页共用统一顶栏内容组件，但允许页面外壳保留各自背景和边界。
- 左侧显示 FileDock Icon、名称和 Slogan，整个品牌区域可点击返回首页，房间页取消独立返回箭头。
- 房间页中间继续显示成员人数、剩余时间和房间容量。
- 房间页右侧从左到右显示分享 Icon、通知 Icon、头像、昵称和下拉箭头。
- 房间页取消独立语言下拉框、独立二维码 Icon和三个点菜单。
- 手机窄屏保留 FileDock Icon 与名称，以及分享、通知和头像；隐藏 Slogan、昵称和下拉箭头。

### 用户菜单与房间操作

- 首页现有个人菜单结构保持不变。
- 房间页用户菜单继续提供个人信息和切换语言，并新增一级菜单“房间操作”。
- 房主的二级菜单包含可用时的“延期房间”和危险操作“解散房间”。
- 普通成员的二级菜单只包含“退出房间”。
- 房间页个人信息使用与首页相同的 Modal 和业务规则。

### 分享房间

- 分享 Icon 打开现有风格的 Modal；桌面居中，移动端从底部弹出。
- 分享 Modal 显示房间名称、房间号、二维码和加入链接。
- 提供复制房间号、复制链接和复制邀请信息。
- 加入链接不携带密码或审批凭证，打开后继续执行房间原有验证流程。
- 邀请信息根据界面语言生成，包含房间名称、房间号和加入链接。

### 通知过渡与后续

- 完整全局通知中心放到后续实现并写入 `todo.md`。
- 本期首页继续使用现有自建房间审批通知。
- 本期房间页继续使用当前房间审批通知；仅当前房间房主可以操作，普通成员显示禁用 Icon。
- 本期不新增通知类型、全局通知查询或后端通知模型。

### 房间信息与成员栏

- 左侧成员栏顶部显示房间名称，以及房间号与复制按钮。
- 不显示“房间会话”“成员”或成员数量；成员数量只保留在房间顶栏中间。
- 房间信息下方直接显示成员列表。
- 当前用户继续在昵称旁显示“我”标识。
- 房主头像左上角显示金色三角角标和皇冠图标，并提供“房主／Owner”Tooltip 与无障碍语义。
- 桌面侧栏和平板／移动端成员抽屉使用相同房间信息与成员标识。

### 文件选择与拖放

- 浏览器原生文件输入框继续作为技术入口，但必须在视觉上隐藏；只显示顶部“添加文件”按钮。
- 删除常驻大块虚线拖放框及其点击选择能力。
- 文件列表顶部显示非交互提示“将文件拖放到列表区域添加”。
- 只有外部文件拖入文件列表时才激活整区浮层，浮层显示“释放文件以添加”。
- 浮层不拦截交互；释放后进入待发送区，不直接上传。
- 文件动态不接受拖放；手机窄屏隐藏拖放提示。
