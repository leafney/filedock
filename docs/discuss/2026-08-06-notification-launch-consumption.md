# 通知导航状态一次性消费讨论记录

日期：2026-08-06

## 原始需求

用户在人工验证文件回收站时发现：房主从文件动态 Tab 切换到回收站 Tab 后反复出现“该通知已失效”提示。重复切换文件动态和回收站会重复弹出同一提示。用户要求分析相关代码并优化，并明确要求同类问题一并修复。

## 代码核查结论

通知中心点击文件或聊天通知时，会生成前端一次性导航标识 `token`。`RoomPage` 清除了路由 `location.state`，但仍长期保留本地 `fileLaunch` 和 `chatLaunch`。文件工作区把文件导航复制为 `trashLaunch`，回收站组件使用组件内 `useRef` 记录已处理 token。切换 Tab 会卸载并重新挂载回收站组件，`useRef` 被重置，同一个 token 被再次处理，因此错误地重复执行“通知已失效”判断。

`token` 只是前端导航去重标识，不是登录凭证、通知数据库 ID 或恢复申请 `requestId`，不参与权限校验。`requestId` 仍是后端审批接口使用的业务标识。

## 完整问答

### 问题 1：同一通知重复切换 Tab 时应如何处理？

**推荐答案：** 一次点击恢复申请通知后只处理一次；反复切换文件动态和回收站不再弹出“通知已失效”，也不重复打开审批 Modal。失效提示只在用户主动点击通知时触发。

**用户答案：** 确认。

### 问题 2：关闭审批 Modal 或切换 Tab 后是否自动重新打开？

**推荐答案：** 不自动重新打开，也不再次提示失效；待审批通知继续保留。用户再次点击通知时生成新 token 并重新打开审批 Modal。关闭 Modal 只表示暂不处理，不改变申请状态。

**用户答案：** 确认。

### 问题 3：修复范围是否覆盖所有文件通知导航？

**推荐答案：** 覆盖文件列表、回收站、文件动态和回收站审批四类文件导航目标；统一在文件工作区完成一次性消费，不改变搜索条件或后端业务规则。

**用户答案：** 确认，并要求同类问题一同修复。

### 问题 4：聊天通知是否也纳入同一套机制？

**推荐答案：** 文件和聊天通知统一采用一次性消费语义。消费后清除父级本地 launch state；再次点击通知生成新 token。聊天的已读和会话业务保持不变。

**用户答案：** 确认。

### 问题 5：`token` 的具体含义是什么？

**澄清说明：** `token` 是通知中心每次点击生成的前端导航实例标识。同一 token 表示同一次点击，页面重渲染或 Tab 切换不能重复处理；新 token 表示用户再次点击通知。`requestId` 才是恢复申请的后端业务 ID。

**用户答案：** 确认 token 仅作为前端一次性导航去重标识，不修改后端接口、不替代 requestId、不作为安全凭证。

### 问题 6：是否增加多标签页之间的前端锁？

**推荐答案：** 一期不增加跨标签页锁或本地广播去重。两个标签页可各自打开审批 Modal，后端事务决定哪个操作成功，另一个标签页通过状态冲突和 SSE 刷新得到最终结果。本次只修复同一标签页内 Tab 卸载重挂导致的 token 重放。

**用户答案：** 确认。

## 最终共识

1. 通知导航状态必须有明确的一次性消费生命周期，不能依赖目标组件挂载周期内的 `useRef` 去重。
2. 文件和聊天通知统一修复；文件通知覆盖列表、回收站、文件动态和审批目标。
3. `RoomPage`、`RoomWorkspace` 或文件/聊天工作区在确认接收 launch 后，必须清除父级本地 launch state；切换 Tab 不得重放旧 token。
4. 关闭审批 Modal、切换 Tab 或离开目标视图不会自动重新打开，也不会重复弹失效提示；再次点击通知才生成新 token。
5. 真实失效通知只在用户主动点击通知且服务端快照确认目标不存在或已处理时提示一次，并刷新通知查询。
6. `token` 只用于前端导航去重，`requestId` 继续用于后端恢复审批；不改后端接口和数据库。
7. 不实现跨标签页锁；继续以 REST 快照、SSE 和后端事务作为权威。
