- 补充目标：全局通知中心除房主加入审批外，房主和普通成员都需要收到当前用户在各个有效房间中的聊天消息通知。

## 代码与文档盘点结论

1. 项目已经完成匿名会话、房间生命周期、成员状态、文件传输、全局 SSE 和一对一文字聊天，一期验收也已收口。
2. 首页通知铃铛目前只查询当前用户自建房间的待处理加入申请。
3. 房间页又单独维护当前房间的加入审批查询和抽屉，普通成员的通知铃铛被禁用。
4. 聊天未读数目前只在进入对应房间后显示；首页和其他房间无法看到跨房间聊天未读。
5. 聊天消息、已读游标、用户本地删除、加入申请、房间和成员状态均已持久化在数据库中，可以作为全局通知投影的事实来源。
6. 当前全局 SSE 已按用户推送聊天、审批和房间事件，但断线期间不补发，因此仍需 REST 快照恢复完整状态。
7. 现有待办已明确记录全局通知中心，且此前聊天规划把通知 Icon 聊天记录列为后续范围。
8. 文件通知、回收站、文件预览、完整性校验、断点续传、深色主题和管理后台仍是后续候选方向，但不应与本阶段混合。

## 问答记录

### 1. 下一阶段主线

**问题：** 是否确认下一阶段以“全局通知中心”为开发主线？推荐先统一首页与房间页的通知入口和数据源，再逐步接入审批、私聊和文件事件。

**回答：** 确认。全局通知中心除房主审批外，房主和普通用户都需要收到当前用户在各个房间中的聊天消息通知。

### 2. 连续聊天消息的展示粒度

**问题：** 同一房间、同一成员连续发送多条聊天消息时，是逐条展示还是聚合展示？推荐按“房间 + 聊天成员”聚合，显示最新摘要和未读数。

**回答：** 确认。首页铃铛 Icon 显示收到的总通知条数，内部列表聚合显示同一房间、同一用户的会话通知。

### 3. 铃铛数量的计算公式

**问题：** 是否按“待处理加入审批数量 + 所有聚合会话中的未读聊天消息数量”计算铃铛总数，超过 99 显示 `99+`？

**回答：** 确认。

### 4. 聊天通知的已读时机

**问题：** 是否只在点击聊天通知、进入对应房间和会话，并满足消息已加载、页面可见、窗口聚焦等现有已读条件后才标记已读？仅打开通知面板不标记已读。

**回答：** 确认。

### 5. 已读与已处理记录的保留时间

**问题：** 已读聊天或已处理审批是否继续显示在通知中心，最初建议保留最近 30 天？

### 6. 通知的持久化位置

**问题：** 通知记录和已读状态是否保存到服务端数据库，而不是以前端 `localStorage` 作为事实来源？

**问题：** SSE 只作为实时传输，是否采用“数据库持久化业务状态 + REST 快照 + SSE 实时推送”的组合，避免离线、刷新、断线或服务重启后丢失通知？

## 最终共同理解

1. 下一阶段只建设加入审批与跨房间未读私聊组成的全局通知中心。
2. 首页和房间页共用一个用户级数据源、一个铃铛总数和一个通知面板；普通成员的铃铛不再禁用。
3. 每条待处理审批计数一条；聊天按实际未读消息条数计数，但列表按“房间唯一 ID + 对方用户 ID”聚合。
4. 聚合项展示对方信息、房间信息、最新可见未读消息摘要、未读数和时间。
5. 通知面板只显示待处理审批和未读聊天，不显示任何已读或已处理历史，也不提供全部已读。
6. 点击聊天通知后进入目标房间并打开目标成员会话；只有满足现有聊天已读条件后才清除未读。
7. 撤回、本地删除、已读、审批状态变化和房间失效都必须准确修正通知内容与总数。
8. 房间过期、解散、成员退出或被踢后，相关通知立即失效并退出展示。
9. 现有数据库业务表是唯一事实来源；REST 提供恢复快照，现有用户级 SSE 提供实时变化信号。通知服务只生成投影，不重复持久化正文、未读数或审批状态。
10. 通知数据不使用前端本地存储。通知专用投影不落表，因此不会产生额外历史；业务数据最多按既有生命周期保留，且不得让失效通知在前端继续出现。确认的 7 天是通知数据保留上限，不要求把已失效数据强行保存满 7 天。
11. 桌面使用右侧抽屉，移动端使用全屏抽屉；不新增通知页面。
12. 成员加入／退出仍只显示当前房间顶部临时提示；文件通知、系统通知、声音和顶部聊天提示均不在本阶段。
13. 自动测试只覆盖复杂业务和纯逻辑边界，不引入 Playwright、视觉快照或新测试框架。
