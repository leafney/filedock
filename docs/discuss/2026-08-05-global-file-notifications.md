# FileDock 全局文件通知一期讨论记录

日期：2026-08-05

## 原始需求

用户要求使用 `caveman` 与 `grill-me` 分析项目代码和相关文档，给出下一阶段开发规划。

在分析后，最初推荐“文件预览一期”。用户明确表示当前不需要文件预览，认为其重要性较低，希望延后实现，并要求给出其他推荐。随后双方围绕“全局文件通知一期”逐项确认范围。

## 项目分析结论

1. 当前项目已实现匿名会话、房间生命周期、成员与在线状态、共享／私密文件传输、一对一文字聊天、聊天历史上下文定位、全局加入审批与聊天通知。
2. 当前全局通知中心仅聚合待处理加入审批和未读一对一聊天，文件事件尚未进入全局铃铛。
3. 文件服务已有用户级 SSE 投影，能够在上传完成、文件复用、接收状态变化和下载完成时通知相关活动成员；下一阶段不需要新增 SSE 连接。
4. 文件接收关系已保存待接收、已接收、已拒绝、已下载状态及首次下载时间，可作为通知有效性判断依据。
5. 当前通知服务采用业务状态实时投影，没有通知明细表。文件拒绝和首次下载完成属于需要持久化未读状态的信息型结果，因此需要增加轻量通知记录。
6. 当前通知抽屉支持审批直接处理和聊天跳转。文件通知应保持简单，只负责提醒和进入房间，不在抽屉内执行文件操作。
7. `docs/first/todo.md` 仍把一对一聊天和全局通知中心列为未实现，已落后于代码现状；本次只以实际代码和后续已批准 PRD 为规划依据，不把旧待办直接当作开发事实。
8. 分析时基线验证通过：`go test ./...` 全部通过，前端 `bun test` 共 23 项通过。

## 问答记录

### 前置问题：是否把下一阶段定为文件预览一期？

**推荐答案：** 是。文件预览能补足当前只能查看元数据和下载的缺口，并为后续聊天图片与文件卡片提供基础。

**用户答案：** 不采用。文件预览当前不重要，放到后面实现；希望推荐其他下一阶段方向。

### 问题 1：是否把下一阶段定为全局文件通知一期？

**推荐答案：** 是。私密文件到达时，无论用户在首页还是其他房间都能得知；发送者也能收到拒绝或首次下载完成结果。该能力可复用现有通知中心、文件事件和用户级 SSE，范围比预览、断点续传或回收站更清晰。

**用户答案：** 确认。

### 问题 2：一期通知哪些文件事件？

**推荐答案：** 只通知三类高价值事件：接收者收到新的私密文件；发送者得知某接收者拒绝文件；发送者得知某接收者首次下载完成。不通知共享文件、上传成功、上传进度、下载开始、重复下载、当前浏览器已有反馈的传输失败、文件复用动作本身或发布为共享文件动作本身。

**用户答案：** 确认。

### 问题 3：通知何时消失？

**推荐答案：** 新私密文件保持显示，直到接收者接收或拒绝；拒绝和首次下载完成结果在点击后标记已读并移除；仅打开通知抽屉不算已读；点击新私密文件只进入房间，不自动接收或下载；房间、文件或当前用户权限失效后通知自动失效。

**用户答案：** 确认。用户补充：收到新私密文件时，通知中只显示提醒，不提供接收或拒绝操作；点击通知后打开对应房间，由用户在私密文件区域处理待接收文件。

### 问题 4：多条文件通知如何聚合？

**推荐答案：** 同一房间、同一发送者的待接收文件合并为一项；同一房间、同一接收者、同一结果类型合并为一项；列表显示最新文件名及文件数量；铃铛按实际文件数量计数；不同房间、成员或结果类型分别显示。

**用户答案：** 确认。

### 问题 5：通知内容显示多少信息？

**推荐答案：** 显示房间名称／房间号、发送者或接收者昵称、最新文件名、聚合文件数量和事件时间。不显示文件大小、MIME、私密编号、其他接收者、下载地址、内部文件 ID 或内容预览。

**用户答案：** 确认。

### 问题 6：点击聚合结果通知时，已读范围如何处理？

**推荐答案：** 点击聚合结果后，当前聚合项所代表的结果全部标记已读，角标减少实际结果数；点击期间新产生的结果保持未读；不提供全部已读；待接收文件不因点击变为已读，仍需接收或拒绝后消失。

**用户答案：** 确认。

### 问题 7：点击文件通知后的页面行为是什么？

**推荐答案：** 目标为其他房间时进入目标房间；已在目标房间时关闭抽屉并刷新文件列表；移动端正在聊天时关闭全屏聊天并回到文件区域；不切换筛选、不滚动定位、不高亮、不自动执行接收、拒绝或下载。

**用户答案：** 确认。

### 问题 8：通知列表如何排序？

**推荐答案：** 第一优先级为待处理加入审批，第二优先级为待接收私密文件，第三优先级为未读聊天与文件结果并按最新时间混排；每个优先级内部按最新活动时间倒序。

**用户答案：** 确认。

### 问题 9：除铃铛外是否增加其他提醒渠道？

**推荐答案：** 不增加顶部 `message`、浏览器系统通知、声音、震动或桌面悬浮提示；保留现有文件列表刷新和传输进度条。本阶段只扩展全局铃铛与通知抽屉。

**用户答案：** 确认。

### 问题 10：是否允许新增轻量通知记录表？

**推荐答案：** 允许。拒绝和首次下载完成属于已发生的信息型结果，仅查询当前文件状态无法区分用户是否已经看过。记录只保存通知 ID、接收用户、类型、房间、文件、相关成员、发生时间和已读时间；不保存文件内容、下载地址、文案或语言；随房间清理删除。项目处于开发阶段，不处理旧数据库兼容。

**用户答案：** 确认。

### 问题 11：何时生成收到私密文件通知？

**推荐答案：** 新上传文件只有完整上传成功并变为可用后才生成；复用已有私密文件再次发送时，在接收关系成功变为待接收后生成；创建上传批次、上传中、上传失败或取消均不生成；同一次状态变更必须幂等，不能因 SSE 重连重复生成。

**用户答案：** 确认。

### 问题 12：首次下载完成如何判定？

**推荐答案：** 只有完整字节流发送成功才算下载完成；仅接收、下载中断、浏览器取消和任务过期不通知；每个文件与接收者组合最多生成一次成功结果；重复下载只更新下载次数，不新增通知。

**用户答案：** 确认。

### 问题 13：文件结果已读状态保存在哪里？

**推荐答案：** 保存于服务端 SQLite；同一匿名身份的多个标签页通过现有 SSE 同步；不以 localStorage 为权威状态；不实现跨匿名身份或跨浏览器同步。

**用户答案：** 确认。

### 问题 14：文件通知保留多久？

**推荐答案：** 只在房间有效期间展示，最长受房间生命周期限制；房间失效立即停止展示；已读结果不进入历史列表；记录随房间清理物理删除；不额外保留七天，避免出现无法进入房间的通知。

**用户答案：** 确认。

### 问题 15：测试与验收范围是什么？

**推荐答案：** Go 测试覆盖生成幂等、权限过滤、聚合计数、已读并发、首次下载和房间清理；前端纯逻辑测试覆盖事件刷新、聚合类型、角标和导航；运行双语词典完整性测试、Go 测试、前端测试、前端构建和单二进制构建；桌面与移动交互由用户人工验证；不使用 Playwright。

**用户答案：** 确认。

### 问题 16：最终阶段边界是什么？

**推荐答案：** 只实现全局文件通知闭环。不包含文件预览、聊天图片／附件／文件卡片、共享文件通知、上传进度与失败通知、浏览器通知、声音、顶部消息、通知历史、全部已读、文件删除、回收站、哈希、秒传、去重、Range、断点续传、管理后台或主题切换。

**用户答案：** 确认。

### 问题 17：实施模块如何组织？

**推荐答案：** 在现有项目内分为通知记录与生命周期、文件状态接入、通知查询、通知接口、现有 SSE 刷新、前端通知中心和测试七部分；不拆新项目、不新增独立服务。

**用户答案：** 确认。

## 最终共识

1. 下一阶段名称为“全局文件通知一期”。
2. 通知范围只有收到新私密文件、私密文件被拒绝、私密文件被接收者首次成功下载三类。
3. 新私密文件属于待处理状态，直到接收或拒绝才消失；通知抽屉不提供接收或拒绝按钮。
4. 拒绝和首次下载完成属于信息型结果，点击聚合项后批量标记当前快照为已读，新到结果不被误读。
5. 同一房间、同一相关成员、同一类型聚合；铃铛按实际文件数量计数。
6. 文件通知只显示授权用户已知的最少信息，不暴露文件内部标识、下载地址或其他接收者。
7. 点击只负责进入对应房间；不自动执行文件操作，也不增加复杂定位交互。
8. 排序固定为审批优先、待接收文件其次、聊天与文件结果按时间混排。
9. 复用现有用户级 SSE，不新增连接；只扩展通知刷新条件与已读同步事件。
10. 新增轻量通知记录保存信息型结果的未读状态，并随房间生命周期清理。
11. 收到文件通知只在文件真正可用后生成；首次下载通知只在完整下载第一次成功后生成。
12. 所有用户可见文案同时支持简体中文与 English。
13. 只编写业务状态与纯逻辑测试；视觉与交互由用户手动验收，不使用 Playwright。
14. 文件预览和其他可靠性、聊天附件、回收站、管理、主题能力全部留待后续。
