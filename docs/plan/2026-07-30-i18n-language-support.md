# FileDock i18n 多语言支持 PRD

## Problem Statement

FileDock 当前前端页面的用户可见文案全部硬编码为简体中文，用户无法切换语言。前端请求也不会声明当前语言。后端虽然存在中英文错误 map 示例和响应翻译函数入口，但翻译内容不完整、未接入请求链路，参数校验固定返回中文，全局 HTTP 错误还可能直接向客户端返回内部技术错误。

这会导致 English 用户无法完整使用页面；未来新增房间、会话、文件、聊天和 SSE 功能时，也容易出现页面文案、接口消息和校验提示语言混杂。项目需要在业务功能大量增加前，先建立统一、严格、可扩展的双语基础设施和持续开发约束。

## Solution

为 FileDock 建立仅支持简体中文和 English 的端到端 i18n 能力。

前端使用 i18next 与 React 集成管理用户界面文案，提供语言切换器，将用户选择保存到 localStorage。无保存值时优先采用受支持的浏览器语言，否则回退简体中文。前端统一通过标准 `Accept-Language` 请求头向后端传递当前语言。

后端建立独立 i18n 核心，负责标准语言头解析、语言归一化、内嵌翻译目录加载、变量插值、严格完整性校验和安全回退。错误码只关联稳定翻译键，业务错误不再携带最终展示文案；统一响应出口根据请求语言生成 `message`，并返回实际使用的 `Content-Language`。参数校验、成功响应、业务错误及全局 HTTP 错误全部进入同一语言链路。

同步清理与 FileDock 无关的遗留错误码，更新响应契约和项目开发规则。后续所有用户可见功能必须同时提供简体中文和 English 文案。

## User Stories

1. 作为简体中文用户，我希望首次打开 FileDock 时看到中文页面，以便直接理解产品功能。
2. 作为 English 用户，我希望浏览器语言受支持时自动看到 English 页面，以便无需先理解中文界面。
3. 作为浏览器语言不受支持的用户，我希望页面稳定回退到简体中文，以便始终得到完整界面。
4. 作为用户，我希望能在页面右上角找到语言切换器，以便随时切换语言。
5. 作为键盘用户，我希望语言切换器支持键盘操作并具有清晰的无障碍名称，以便不依赖鼠标完成切换。
6. 作为用户，我希望语言选项显示“简体中文”和“English”，而不是使用国旗，以免把语言与国家错误绑定。
7. 作为用户，我希望切换语言后页面立即更新，以便无需刷新页面。
8. 作为用户，我希望刷新页面后仍保留已选择语言，以便不用重复设置。
9. 作为使用另一浏览器或清除站点数据的用户，我希望系统重新根据该浏览器语言选择界面，以便行为可预测。
10. 作为用户，我希望语言切换不改变当前 URL，以便链接保持稳定且不打断当前操作。
11. 作为用户，我希望页面标题、产品说明、加载提示、错误提示、状态标签和版本字段标签使用同一种语言，以免出现中英混杂。
12. 作为用户，我希望品牌名 `FileDock` 在两种语言中保持一致，以便识别产品。
13. 作为用户，我希望版本号、Git 分支、提交哈希和构建时间等机器数据保持原值，以免翻译破坏诊断信息。
14. 作为用户，我希望后端成功响应使用当前语言，以便成功通知与页面语言一致。
15. 作为用户，我希望后端业务错误使用当前语言，以便理解操作失败原因。
16. 作为用户，我希望请求参数错误指出首个有问题字段并使用当前语言，以便快速修正输入。
17. 作为用户，我希望未授权、禁止访问、资源不存在和资源冲突等提示使用当前语言，以便准确判断下一步操作。
18. 作为用户，我希望服务内部异常只返回安全、易懂的通用提示，以免看到无意义的技术细节。
19. 作为用户，我希望后端不可达、网络超时等客户端错误也使用当前页面语言，以便所有失败状态一致。
20. 作为 API 客户端，我希望使用标准 `Accept-Language` 声明期望语言，以便遵循通用 HTTP 语义。
21. 作为 API 客户端，我希望 `zh`、`zh-CN`、`en`、`en-US` 等常见值能被正确归一化，以便不同客户端都得到可用结果。
22. 作为 API 客户端，我希望服务能正确处理带权重的 `Accept-Language` 列表，以便按客户端偏好选择支持语言。
23. 作为 API 客户端，我希望响应包含 `Content-Language`，以便确认服务实际使用的语言。
24. 作为 API 客户端，我希望业务错误码和 HTTP 状态不因语言改变，以便程序逻辑保持稳定。
25. 作为前端开发者，我希望业务错误译文由后端维护，以免前后端重复维护同一错误目录。
26. 作为后端开发者，我希望业务层只返回错误码、插值参数和内部原因，以便响应出口统一决定展示语言。
27. 作为后端开发者，我希望语言解析和翻译模块不依赖 Fiber，以便独立测试和复用。
28. 作为后端开发者，我希望翻译目录缺键或格式错误时服务拒绝启动，以便缺译问题在发布前暴露。
29. 作为前端开发者，我希望双语资源键具有类型约束，以便构建阶段发现缺失文案。
30. 作为维护者，我希望删除与 FileDock 无关的视频和发票错误码，以便错误目录只反映当前领域。
31. 作为维护者，我希望项目开发规则明确要求新功能同步提供双语文案，以便 i18n 能力持续有效。
32. 作为测试人员，我希望能验证中文、English、缺失语言头和不支持语言四种路径，以便确认协商与回退正确。
33. 作为运维人员，我希望内部日志保持稳定且不随用户语言改变，以便检索、聚合和排障。
34. 作为安全负责人，我希望内部错误原因只进入日志、不进入客户端响应，以便减少信息泄漏。
35. 作为未来业务开发者，我希望 SSE 中面向用户的提示遵循同一语言上下文，以便实时功能不会形成第二套翻译机制。

## Implementation Decisions

### 支持语言与语言协商

- 首期且仅支持两个规范语言标识：`zh-CN` 与 `en`。
- 系统默认语言固定为 `zh-CN`，本期不增加配置项。
- 前端初始化优先级固定为：localStorage 中的有效选择、受支持的浏览器语言、`zh-CN`。
- 用户选择只保存于浏览器 localStorage；不写入 Cookie、数据库、用户资料或 URL。
- 前端所有 HTTP 请求统一发送当前规范语言值作为 `Accept-Language`。
- 后端解析标准 `Accept-Language` 列表及质量权重，选择权重最高且受支持的语言。
- `zh` 及简体中文地区变体归一化为 `zh-CN`；`en` 及 English 地区变体归一化为 `en`。
- 请求头缺失、格式无效、仅包含通配符或没有支持项时使用 `zh-CN`。
- 后端对经过语言中间件处理的 JSON 响应设置 `Content-Language` 和 `Vary: Accept-Language`，避免共享缓存混用语言版本。

### 前端 i18n

- 引入 i18next 及 React 集成库，不引入额外的自动检测插件；语言检测和持久化用少量显式代码实现，确保优先级清晰可测。
- 中文资源作为键结构基准，English 资源必须满足同一键结构；TypeScript 构建应能发现调用不存在的翻译键。
- 翻译键按页面或领域分组，不使用完整中文句子作为键。
- 当前首页的产品说明、加载状态、失败状态、版本字段标签和语言切换器无障碍文本全部迁入翻译资源。
- `FileDock` 作为品牌名保持不变；中文展示名使用“码头”，English 展示名使用 `FileDock`。
- 语言切换器位于页面右上角，使用文字下拉菜单，选项为“简体中文”和“English”，不使用国旗。
- 切换语言立即更新 React 页面、localStorage 与文档根节点的 `lang` 属性，不执行整页刷新，不修改路由。
- axios 请求拦截器在每次发送请求前读取当前已解析语言并设置请求头，避免只在客户端创建时捕获旧语言。
- 前端负责翻译浏览器网络错误、请求超时、服务不可达等本地错误；后端业务错误直接显示后端已经本地化的 `message`。
- 本期不在 API 响应中新增 `message_key`；稳定业务 `code` 继续作为程序分支依据。

### 后端 i18n 核心

- 建立不依赖 Web 框架的 i18n 深模块，公开小型稳定接口：解析语言、取得规范语言、翻译键及插值参数、校验目录。
- 后端翻译目录使用随二进制内嵌的 `zh-CN.json` 和 `en.json`，运行时不依赖外部文件。
- 翻译目录支持命名空间键和具名变量插值；插值参数只用于用户可见业务值，不直接拼接内部错误文本。
- 构造阶段解析全部目录并校验：JSON 有效、规范语言齐全、双语键集合完全一致、值非空。任一条件失败均阻止服务启动。
- 中文为首个运行时回退目录。若意外缺少当前语言键，先回退中文；中文仍缺失时返回当前响应类型对应的安全通用提示，同时记录缺键日志。
- 任何情况下都不得把裸翻译键、JSON 解析错误或内部 cause 返回给客户端。

### 请求语言上下文

- Fiber 语言中间件位于恢复中间件和请求日志中间件之后、路由注册之前，使业务响应和全局错误都能读取规范语言。
- 中间件只解析请求信息并向请求上下文注入规范语言与翻译函数，不持久化用户偏好。
- 现有统一响应翻译入口改为调用新的 i18n 核心，不允许 handler 自行解析请求头或直接读取翻译文件。
- 未来 SSE 建连时继承该请求确定的语言；连接存续期间不动态切换。用户切换语言后需要新建连接才能采用新语言。

### 错误码与错误对象

- 错误注册表保存稳定业务码、翻译键和对应 HTTP 状态，不再保存两套最终文本 map。
- 删除视频、发票等与 FileDock 无关的遗留错误码及其 HTTP 状态分支。
- 保留当前所需的通用成功、失败、参数、鉴权、权限、资源、冲突和系统错误；FileDock 房间、会话、文件、聊天等领域错误在对应功能设计中增加。
- 每个保留错误码都必须拥有中文和 English 翻译，目录完整性测试必须覆盖错误注册表引用的所有键。
- 业务错误对象保存错误码、可选具名插值参数和可选内部 cause，不保存最终用户文案。
- 错误对象的内部 cause 用于日志和错误链检查；响应层只根据错误码及安全参数生成客户端消息。
- 自定义成功或错误消息接口改为接收翻译键及插值参数。禁止新增 handler 传入已经翻译的硬编码句子。
- 业务码、HTTP 状态和响应数据结构不随语言变化。

### 统一响应与全局错误

- 统一响应结构继续使用 `code`、`message`、可选 `data`，不因 i18n 增加新 JSON 字段。
- 中文成功消息为“操作成功”，English 成功消息为 `Success`。创建成功等专用响应使用对应双语翻译键。
- 当前版本接口的成功消息契约从固定小写英文调整为按语言返回；现有测试、README 和架构响应示例同步更新。
- 参数校验失败使用参数错误业务码，`message` 只返回首个校验错误。
- 全局错误处理对 JSON API 和服务接口使用统一响应结构及语言上下文，不直接回传 Fiber 默认英文或 `error.Error()`。
- 已知 HTTP 错误映射为对应稳定业务码和安全译文；未知异常映射为服务端通用错误，内部原因仅记录日志。
- SPA 页面回退与静态资源服务保持原行为，不把前端路由误判为本地化 JSON 404。

### 参数校验

- 校验模块同时注册简体中文和 English 翻译器，不再依赖单个全局中文翻译器。
- 原始校验结果与语言翻译分离，使请求出口能按语言生成消息。
- 校验提示采用 DTO 的 JSON 字段名，不暴露 Go 类型名、结构字段名或底层校验标签。
- 多个字段失败时只返回校验器确定顺序中的首个错误，保证响应简单且可预测。
- 对缺少必填值、格式错误、数值范围等现有常用规则提供完整双语提示。

### 持续开发规则与文档

- 项目 Agent 规则增加强制条款：后续新增或修改任何用户可见页面文案、API 消息、校验提示和实时事件提示时，必须同步维护 `zh-CN` 与 `en`。
- 新增翻译键时，两种语言必须在同一变更中提交，并通过完整性检查。
- 禁止在 React 组件和 API handler 中新增硬编码用户可见文案；品牌、协议常量和机器数据除外。
- README、统一响应规范和当前架构文档同步说明语言协商、响应头、双语成功消息及前端选择规则。

### 实施顺序与确认点

1. 先实现后端 i18n 核心、内嵌目录与完整性测试；完成该主要文件组后等待用户确认。
2. 再重构错误注册表、错误对象、响应层和参数校验；完成该主要文件组后等待用户确认。
3. 接入 Fiber 语言中间件、全局错误处理和接口集成测试；完成该主要文件组后等待用户确认。
4. 引入前端依赖、初始化语言资源、持久化和请求头；完成该主要文件组后等待用户确认。
5. 改造首页并增加语言切换器；完成该主要文件组后等待用户确认。
6. 更新 Agent 规则、README、架构文档和响应示例；完成后执行全部验收。

## Testing Decisions

- 测试只验证外部可观察行为，不断言私有函数调用、内部 map 布局或 Fiber Locals 的具体键名。
- i18n 核心单元测试覆盖：规范语言、大小写与地区变体、多个语言范围、质量权重、无效权重、通配符、空请求头、不支持语言及默认回退。
- 翻译目录单元测试覆盖：两种语言键集合一致、空值拒绝、无效 JSON 拒绝、变量插值、当前语言缺键回退及安全最终回退。
- 错误注册表单元测试覆盖：所有错误码唯一、所有翻译键存在、业务码对应正确 HTTP 状态、已删除领域错误不再参与映射。
- 错误对象单元测试覆盖：错误码和参数可提取、cause 可用于错误链检查、响应消息不包含 cause 文本。
- 参数校验单元测试覆盖：必填、邮箱格式和数值范围在中文与 English 下返回对应首条提示，且字段名使用 JSON 名称。
- 服务集成测试覆盖：版本接口在 `zh-CN`、`en`、缺失请求头和不支持语言时返回正确消息、`Content-Language` 与 `Vary`。
- 服务集成测试覆盖：带地区变体及权重列表的请求得到正确语言。
- 服务集成测试覆盖：API 404、已知 HTTP 错误和未知内部错误使用统一响应；内部错误文本不得出现在客户端响应。
- 服务集成测试继续验证请求 ID、版本数据字段和静态 SPA 回退，确保中间件顺序未破坏现有能力。
- 后端测试沿用现有标准库表驱动测试、服务端请求测试和校验器测试风格。
- 前端本期不引入测试框架。自动验收为 TypeScript 编译与 Vite 生产构建成功。
- 前端手工验收覆盖：无 localStorage 的中文浏览器、无 localStorage 的 English 浏览器、不支持语言浏览器、手动切换、刷新保留、清除存储后重新检测、键盘操作、文档 `lang` 更新和请求头变化。
- 联调验收覆盖：页面语言与后端成功或错误消息一致，响应声明正确 `Content-Language`，切换后新请求立即使用新语言。

## Out of Scope

- `zh-CN` 与 `en` 之外的语言。
- 繁体中文及不同 English 地区的独立译文；这些变体只归一化到现有语言。
- 将语言偏好保存到数据库、用户账号、服务端 Session 或 Cookie。
- 在 URL 路径或查询参数中加入语言。
- 翻译日志、业务码、JSON 字段名、数据库值、用户输入、文件名、版本号、Git 信息和其他机器数据。
- 引入在线翻译平台、翻译管理后台或自动机器翻译服务。
- 本地化日期、时间、数字、文件大小和复数规则；当前页面没有需要本地化展示的对应业务数据，后续功能另行设计。
- 实现尚不存在的房间、会话、文件、聊天或 SSE 业务；本次只建立其必须遵守的语言基础设施和规则。
- 为前端新增单元测试或端到端测试框架。
- 数据库 Schema 变更或历史数据迁移。
- SEO 多语言页面及服务端渲染。

## Further Notes

- 项目处于开发阶段，本次允许直接修改现有错误与响应 API，不提供旧接口兼容层。
- 后端内嵌翻译目录保证单二进制部署方式不变；前端资源继续进入 Vite 构建产物并由 Go embed 发布。
