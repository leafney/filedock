# 通知导航状态一次性消费优化 PRD

状态：实现完成，待人工验收

日期：2026-08-06

## Problem Statement

文件回收站人工验证发现，房主从“文件动态”切换到“回收站”时会重复出现“该通知已失效”提示。重复切换两个 Tab 会继续重复弹出，造成用户误以为当前审批通知已经失效。

根因是通知中心点击后生成的前端导航 `token` 被保存在房间页面本地状态中，但目标文件工作区只在回收站组件内部使用 `useRef` 去重。回收站 Tab 卸载并重新挂载后，组件内去重状态丢失，旧 token 被再次处理。路由 state 虽然已清除，但页面本地 launch state 没有被消费和清除。

聊天通知使用类似的父级 launch state，也应统一遵循一次性消费语义，避免未来出现同类重放。

## Solution

建立统一的前端通知导航消费机制：通知目标到达房间工作区并完成视图切换后，立即由父级工作区消费并清除对应 launch state。目标组件不得把“是否处理过 token”作为跨挂载生命周期的唯一依据。

一次点击只消费一次。关闭审批 Modal、切换文件 Tab、重新渲染或组件卸载重挂都不能重放旧 token。用户再次点击通知时，通知中心生成新 token，才允许重新打开目标视图或审批 Modal。

文件通知覆盖文件列表、回收站、文件动态和恢复审批；聊天通知同步采用相同消费方式。真实失效判断仍使用服务端 REST 快照，失效提示只在用户主动点击通知且目标确认不可用时显示一次，并刷新通知查询。后端接口、数据库、通知已读规则、SSE 协议和多标签页锁策略均不改变。

## User Stories

1. 作为房主，我希望点击恢复申请通知后只处理一次，以免重复弹出误导性的失效提示。
2. 作为房主，我希望在文件动态和回收站之间切换时不重新处理旧通知，以便正常浏览文件信息。
3. 作为房主，我希望关闭审批 Modal 后申请保持待处理，以便稍后再决定。
4. 作为房主，我希望关闭 Modal 后不自动再次打开，以免打断当前操作。
5. 作为房主，我希望再次点击仍有效的恢复申请通知时重新打开审批 Modal，以便继续处理申请。
6. 作为房主，我希望已经处理或失效的申请只显示一次失效提示，以便知道通知确实不可用。
7. 作为用户，我希望点击文件被删除通知后进入回收站，但切换 Tab 不重复消费通知。
8. 作为用户，我希望点击文件恢复结果通知后进入文件列表，重新渲染不会改变目标或重复执行已读逻辑。
9. 作为用户，我希望点击永久删除通知后进入文件动态，切换其他文件视图后返回不会重放旧导航。
10. 作为用户，我希望聊天通知只打开一次目标会话，避免工作区重挂后重复切换当前聊天对象。
11. 作为用户，我希望再次点击聊天通知时生成新的导航实例并正常打开会话。
12. 作为用户，我希望 `token` 只影响前端导航去重，不影响登录、权限、通知 ID 或恢复申请 ID。
13. 作为用户，我希望恢复申请的后端 `requestId` 继续用于同意和拒绝，避免前端导航标识误当成业务标识。
14. 作为多标签页用户，我希望不同标签页仍通过后端事务和现有 SSE 得到最终状态，不引入不可预测的本地锁。
15. 作为维护者，我希望一次性导航生命周期可通过纯逻辑测试验证，防止未来新增通知目标时重新引入状态重放。

## Implementation Decisions

### 1. 导航状态模型

保留现有通知中心生成的随机前端 `token`，但明确其生命周期：

```ts
type NotificationLaunch = {
  token: string;
  target: "chat" | "file";
  view?: "list" | "timeline" | "trash";
  requestId?: string;
};
```

- `token` 只用于识别一次用户点击，不是安全凭证。
- `requestId` 只用于恢复申请后端操作。
- 同一 token 只能消费一次；新 token 才是新的导航请求。
- 消费状态必须保存在不会因目标 Tab 卸载而丢失的父级工作区状态中，或由父级明确清除 launch state。

### 2. 文件通知消费

- 文件工作区接收文件 launch 后，先按 `view` 切换到文件列表、文件动态或回收站。
- 回收站审批目标在进入回收站后查询目标 `requestId`，找到待处理申请则打开审批 Modal。
- 找到申请、确认申请已处理，或确认目标不存在后，都必须向父级报告“该 token 已消费”。
- 父级清除 launch state 后，回收站卸载再挂载不会再次处理旧 token。
- 申请仍待处理但 Modal 被关闭时，申请不被标记已读、不被修改；再次点击通知会产生新 token并重新打开。
- 用户主动点击失效通知时只显示一次 `notification.unavailable`，随后刷新通知快照。
- 普通 Tab 点击、文件列表刷新、SSE 刷新和 React 重渲染不得触发失效提示。

### 3. 聊天通知消费

- 聊天工作区使用同一父级消费语义，不依赖聊天组件挂载周期内的 token ref。
- 进入有效成员会话后立即消费 token并清除父级 launch state。
- 目标成员不存在或已无权访问时消费 token、提示一次不可用并刷新通知。
- 不改变聊天通知已读、未读计数、草稿和会话加载规则。

### 4. 父子组件接口

父级工作区向文件和聊天工作区提供一次性 launch 以及消费回调。消费回调必须幂等：重复调用同一 token 不得产生额外提示或状态变化。目标组件不再把本地 `useRef` 作为跨 Tab 生命周期的权威去重机制。

### 5. 数据和后端边界

- 不增加数据库表、字段或迁移。
- 不增加或修改文件回收站、恢复审批、聊天和通知 REST 接口。
- 不修改 SSE 事件格式；继续使用现有通知变化和文件/聊天事件触发查询失效。
- 不实现跨标签页广播锁；多个标签页的并发审批继续由后端事务裁决。

### 6. 文案与可访问性

- 复用现有中英文“通知已失效”文案，不新增硬编码用户文案。
- 如果需要新增错误或状态提示，必须同时补齐 `zh-CN` 与 `en` 翻译键。
- Modal 和通知目标保持现有焦点管理、键盘关闭和可见焦点样式。

## Testing Decisions

测试只验证外部行为和状态转换，不绑定具体 React 内部实现：

1. 增加通知导航纯逻辑测试：同一 token 只能消费一次，新 token 可以再次消费。
2. 测试文件列表、回收站、文件动态和审批四种目标均能生成正确视图，不改变搜索条件。
3. 测试审批 Modal 关闭后不会改变申请状态，再次点击新 token 可以重新打开。
4. 测试已处理、失效和不存在目标只产生一次不可用结果，并允许通知查询刷新。
5. 测试聊天通知有效目标和无效目标的一次性消费行为。
6. 测试父级消费后目标组件卸载并重新挂载不会再次处理旧 token。
7. 回归现有通知逻辑、文件权限、聊天历史和双语词典测试。
8. 按项目现有方式运行 `frontend bun test`、`frontend bun run build`、`go test ./...` 和 `git diff --check`。

## Out of Scope

- 不调整通知聚合、已读水位、通知类型或通知排序。
- 不调整文件回收站权限、删除原因、恢复审批业务规则。
- 不新增跨标签页锁、BroadcastChannel 或 localStorage 同步协议。
- 不改变 SSE 连接、事件名称或服务端通知有效性算法。
- 不重做文件动态、回收站或聊天界面视觉样式。
- 不新增后端 token 校验或持久化前端 token。

## Further Notes

- 本次问题属于前端一次性导航状态生命周期缺失，不是回收站后端数据错误。
- 实现后应优先手动验证：点击恢复申请通知、关闭 Modal、切换文件动态/回收站多次、再次点击通知、再验证聊天通知切换。
- 阶段完成后使用 Conventional Commits 提交，并在提交正文引用本 PRD。
