# FileDock 首页视觉细节优化 PRD

## Problem Statement

正式首页已经完成浅色雷达布局与真实业务接入，但人工验证暴露出若干影响可读性和操作层级的问题：五个装饰房间头像尺寸与颜色重复度较高；当前碰撞算法按固定距离计算，无法安全支持不同大小的头像；Footer Tooltip 的位置和信息密度不符合预期；右侧存在多组重复的创建和加入入口；房间项仍用角色文字作为辅助信息，无法为未来自定义房间标题提供自然承载位置；个人中心缺少随机昵称能力，注册时间格式也不够精确统一。

人工长时间停留首页后还发现一个明确缺陷：装饰房间头像会不断累积，最终远超规定的五个。现有替换流程由轮询定时器和未受完整管理的延迟回调共同驱动，缺少失效回调保护、目标节点存在性校验和节点总数硬约束。这个缺陷会随着页面停留时间持续放大，必须在引入随机尺寸前先修复。

这些问题不会改变房间或会话业务规则，但会使首页显得机械、入口冗余，并造成桌面端与移动端行为不一致。本项目后续还计划提供深色主题，因此本次新增的随机颜色和视觉样式不能只适配当前浅色背景。

## Solution

在不修改后端接口、数据库结构和既有业务流程的前提下，对正式首页做一次边界明确的视觉细节优化：先把雷达替换逻辑改为数量恒定、可取消且能拒绝陈旧回调的状态更新；再为装饰房间生成受约束的随机尺寸与随机颜色，并基于实际半径重新计算碰撞；精简右侧创建／加入入口；让两类房间卡片统一显示现有房间标题；统一桌面悬停浮层与移动端操作面板的“进入房间”语义；增强个人中心的随机昵称与精确注册时间展示；调整 Footer 在桌面和移动端的不同交互。

本轮继续交付浅色主题，但新增和调整的颜色、边框、阴影及文字样式要使用可覆盖的主题语义变量。完整深色主题不在本轮实现，只增加项目待办。

## User Stories

1. 作为首页用户，我希望五个装饰房间头像大小有明显但协调的差异，以便雷达画面更自然。
2. 作为首页用户，我希望装饰房间头像不会大于中心用户头像，以便中心身份保持最强视觉层级。
3. 作为首页用户，我希望小头像中的房间号尾数仍然清晰，以便节点缩小后不会难以辨认。
4. 作为首页用户，我希望房间标签与头像尺寸协调，以便画面不会出现文字压住头像或间距失衡。
5. 作为首页用户，我希望不同大小的装饰节点不会互相覆盖，以便所有节点保持清楚。
6. 作为首页用户，我希望装饰节点不会覆盖中心头像及昵称，以便当前身份始终可读。
7. 作为首页用户，我希望装饰节点不会越过雷达区域边界或裁切房间标题，以便布局完整。
8. 作为首页用户，我希望装饰头像具有丰富的随机颜色，以便节点变化不显得机械重复。
9. 作为首页用户，我希望同一时刻的五个节点颜色有足够差异，以便快速区分。
10. 作为浅色主题用户，我希望随机头像上的白色数字保持清晰，以便颜色不会损害对比度。
11. 作为未来深色主题用户，我希望本次新增的节点视觉可被主题变量覆盖，以便以后无需重写算法。
12. 作为减少动态效果的用户，我希望尺寸和颜色随机化不破坏现有减少动画规则，以免产生不适。
13. 作为桌面用户，我希望 Footer 的版本 Tooltip 整体显示在版本按钮右侧，以便位置符合页面底部布局预期。
14. 作为桌面用户，我希望 Footer Tooltip 只显示版本和构建时间，以便快速获取最有用的信息。
15. 作为键盘用户，我希望聚焦 Footer 版本按钮时也能查看相同 Tooltip，以便无需鼠标。
16. 作为移动端用户，我希望 Footer 版本只是一段普通文本且没有 Tooltip，以免触摸后出现遮挡页面的浮层。
17. 作为移动端用户，我希望仍可从个人中心查看完整版本信息，以便信息没有丢失。
18. 作为已建立身份的用户，我希望右侧不再重复显示顶部创建和加入大按钮，以便页面更简洁。
19. 作为没有自建房间的用户，我希望点击固定的虚线房间槽即可创建房间，以便保留唯一且直观的创建入口。
20. 作为已有自建房间的用户，我希望“我的房间”区域只显示该房间，不再显示无效的第二个创建入口。
21. 作为希望加入房间的用户，我希望在“参与房间”标题右侧看到唯一的“加入房间”入口，以便明确从哪里输入房间号。
22. 作为尚未参与其他房间的用户，我希望空状态只描述当前没有房间，不再重复显示加入按钮，以便操作层级单一。
23. 作为用户，我希望下方区域命名为“参与房间”，以便比“成员”更准确地表达列表含义。
24. 作为房主，我希望自建房间卡片右侧显示房间标题，以便理解该字段以后可用于辨认自定义房间。
25. 作为房间成员，我希望参与房间卡片右侧也显示房间标题，以便两类卡片结构一致。
26. 作为当前版本用户，我希望房间标题显示默认的“房间 四位房间号”，以便即使尚未支持修改标题也有明确名称。
27. 作为未来使用自定义标题的用户，我希望卡片直接读取房间摘要中的真实标题，以便功能上线后无需再次重构卡片。
28. 作为长标题房间的用户，我希望卡片不会被长文本撑破，以便侧栏布局稳定。
29. 作为桌面用户，我希望悬停被省略的房间标题时看到完整标题，以便仍能辨认房间。
30. 作为已属于房间的用户，我希望操作按钮显示“进入房间”而不是“加入房间”，以便动作语义准确。
31. 作为桌面用户，我希望房间悬停浮层中的进入操作使用正确文案，以便不会误以为需要再次加入。
32. 作为移动端用户，我希望房间底部操作面板也使用“进入房间”，以便跨设备保持一致。
33. 作为通过房间号加入的新用户，我希望真正的加入入口仍显示“加入房间”，以便区分新加入与进入已有房间。
34. 作为已建立身份的用户，我希望头像菜单第一项显示“个人中心”，以便菜单命名直接清晰。
35. 作为已建立身份的用户，我希望弹窗标题也显示“个人中心”，以便菜单和弹窗名称一致。
36. 作为修改昵称的用户，我希望在个人中心输入框旁点击骰子获得新的随机昵称，以便快速选择名称。
37. 作为修改昵称的用户，我希望随机昵称来自现有服务端候选接口，以便继续遵守全局唯一和保留词规则。
38. 作为修改昵称的用户，我希望随机结果只填入输入框而不立即保存，以便先确认或继续编辑。
39. 作为修改昵称的用户，我希望可以连续随机或手动修改候选名称，以便选择满意的结果。
40. 作为修改昵称的用户，我希望只有点击“保存名称”才更新真实会话，以免误操作。
41. 作为网络异常用户，我希望随机昵称失败时保留当前输入并看到本地化错误，以便可以继续手动编辑。
42. 作为已建立身份的用户，我希望注册时间精确显示到秒，以便清楚知道身份创建时间。
43. 作为中文界面用户，我希望注册时间显示为 `YYYY-MM-DD HH:mm:ss`，以便格式稳定易读。
44. 作为英文界面用户，我希望注册时间使用同样的数字格式，以便切换语言时信息位置不跳动。
45. 作为在不同时区使用服务的用户，我希望注册时间按浏览器本地时区展示，以便时间符合当前设备认知。
46. 作为中英文界面用户，我希望所有调整后的按钮、分区、Tooltip 和提示都完整翻译，以便切换语言后不会出现缺失文案。
47. 作为项目维护者，我希望本轮不引入 Playwright、Vitest 或快照基础设施，以便验收方式符合当前人工测试决定。
48. 作为项目维护者，我希望前端生产构建和现有 Go 测试继续通过，以便视觉优化不破坏编译或后端行为。
49. 作为长时间停留首页的用户，我希望装饰房间始终只有五个，以免页面逐渐被头像填满。
50. 作为首页用户，我希望节点淡入淡出期间也不会短暂出现第六个节点，以便“五个”是严格上限而非稳定状态近似值。
51. 作为切换页面的用户，我希望离开首页后尚未完成的雷达回调立即失效，以免返回首页时出现旧节点或状态更新警告。
52. 作为切换系统动画偏好的用户，我希望旧替换任务不会与新任务同时执行，以免重复追加节点。
53. 作为项目维护者，我希望雷达节点状态、渲染元素和实际 DOM 数量保持一致，以便可以直接检查不变量。

## Implementation Decisions

### 1. 范围与兼容原则

- 本 PRD 是正式首页重构后的增量优化，不重做页面架构，也不恢复任何临时预览页面。
- 不修改 HTTP 接口、统一响应结构、数据库表、房间状态、会话 Cookie、JWT、SSE 或权限逻辑。
- 房间摘要已经包含真实 `title`，卡片直接消费该字段；禁止为了显示标题新增请求或扩展后端 DTO。
- 现有创建房间、加入房间、进入房间、退出房间、解散房间和账户重置流程保持不变。
- 所有用户可见文案必须使用 i18n 翻译键，同时补齐 `zh-CN` 与 `en`；React 组件内禁止硬编码中文或英文业务文案。

### 2. 雷达节点数据模型

- 装饰房间总数继续固定为五个，不包含中心用户头像。这是状态数组、React 渲染结果和实际 DOM 的硬性不变量，不只是平均数量或稳定状态目标。
- 每个雷达节点在现有唯一标识、房间号、颜色、坐标、创建时间、过期时间和阶段之外，增加稳定的随机直径。
- 直径在节点创建时生成一次，闭区间为 `40～88px`；节点整个生命周期内尺寸不得跳变。
- 中心用户头像继续固定为 `112px`，不得纳入随机范围。
- 节点替换时，新节点重新生成房间号、尺寸、颜色、位置和生命周期；已有节点不得因另一个节点更新而重新随机。
- 现有每个节点独立显示 `10～30` 秒、逐个退出和补入、最多五个、不可点击、不可被屏幕阅读器反复播报等规则保持不变。

### 3. 雷达节点数量不变量与替换生命周期

- 修复长时间运行后节点不断累积的缺陷是本轮第一优先级。不能只在渲染时截取前五个来掩盖状态数组持续增长。
- 初始化必须一次生成恰好五个固定槽位。每次替换只选中一个已过期槽位，在同一槽位内完成 `visible → exiting → entering/visible` 状态变化。
- 退出动画期间，旧节点仍占用自己的槽位；退出完成时以新节点原子替换该槽位，数组长度前后都必须为五。
- 禁止使用“过滤旧节点后无条件向数组末尾追加新节点”的更新方式。若目标节点或目标槽位已不存在，回调必须直接结束，不得创建新节点。
- 任意时刻最多只能有一个槽位处于替换流程。其他已过期节点按顺序等待下一轮处理，不得并发启动多个延迟回调。
- 组件必须持有正在等待的延迟任务标识，并在组件卸载、替换流程重启、减少动画偏好发生变化或相关 Effect 清理时取消任务。
- 除取消定时任务外，还必须使用组件生命周期标记或替换世代标识拒绝已经失效但仍到达的回调。仅调用 `clearTimeout` 不能代替回调身份校验。
- 延迟回调执行前必须同时校验：组件仍挂载、当前替换世代仍有效、目标槽位仍是预期节点、当前节点总数仍为五。任何一项不满足都不得写入状态。
- 状态更新函数结束时应通过明确的不变量检查保证长度为五。开发环境可报告不变量异常，但生产逻辑不能静默追加第六个节点。
- 节点 `key` 必须在当前五个节点中唯一。新节点标识不能仅依赖可能相同的毫秒时间；应结合单调序号或等效稳定机制，避免快速替换时发生键冲突。
- 节点引用必须与最新状态同步。定时轮询不能长期读取已经失效的旧数组快照。
- `prefers-reduced-motion` 只把动画等待时间缩短为零，不改变固定槽位替换与五节点不变量。
- 页面从前台切到后台后，浏览器可能合并或延迟定时任务；恢复前台时仍只能串行替换过期节点，不得一次并发补入所有过期节点。
- 本次人工验收可在浏览器开发者工具中执行只读 DOM 查询，确认 `.radar-node` 数量始终为 `5`；这不属于 Playwright 自动化测试。

### 4. 雷达节点尺寸与文字

- 头像圆的 CSS 尺寸必须来自节点数据，不得用随机 CSS 动画反复计算。
- 节点内显示房间号后两位的现有规则保持不变。
- 节点数字字号随直径线性或分段变化，最小节点也必须完整显示两位数字；不得通过隐藏数字解决空间问题。
- 边框粗细、阴影扩散和头像下方标签间距应随尺寸适度调整，视觉上不能出现小节点边框过粗或大节点阴影过弱。
- 房间标签继续显示完整四位编号，标签文字大小保持可读，但不能因头像大小随机而改变房间号语义。
- 尺寸变化不得造成布局抖动；节点使用绝对定位并以头像中心作为位置基准。

### 5. 基于实际半径的碰撞与边界

- 节点位置计算必须以像素尺寸和雷达容器实际宽高为依据，或在百分比算法中正确把像素半径换算为对应轴百分比；不能继续只比较固定百分比距离。
- 两个节点之间的最小中心距离至少为：节点 A 半径 + 节点 B 半径 + 视觉安全间距。视觉安全间距应覆盖边框、阴影和标签，不允许圆形不相交但标签互相覆盖。
- 节点与中心用户之间的最小中心距离至少为：节点半径 + 中心头像半径 `56px` + 中心名称区域和安全间距。
- 节点中心的可选范围必须根据自身半径内缩，保证头像、边框和标签都留在雷达可见区域内。
- 节点标签位于头像下方，因此底部边界需要额外预留标签高度，不能只按圆形半径判断。
- 随机坐标仍允许限定最大尝试次数。若没有完全满足条件的候选点，回退结果必须选择与中心、其他节点和边界的最小净空最大者，而不是返回固定槽位。
- 窗口尺寸改变后若现有节点超出安全区域，应重新布局现有节点的位置，但不得同时替换其房间号、尺寸、颜色或生命周期。
- 小屏布局若无法容纳五个最大节点，应优先使用节点已生成的真实尺寸参与重新排布；不得通过把节点总数减到四个规避碰撞。

### 6. 受约束的随机颜色

- 删除当前固定颜色数组，改为通过 HSL 生成头像背景色。
- 色相取值范围为 `0～359`，饱和度范围为 `55%～75%`，亮度范围为 `38%～52%`。
- 同一时刻五个节点之间必须避免非常接近的色相。实现应计算圆形色相距离，即同时考虑 `0` 与 `359` 相邻；不能直接使用普通绝对差。
- 若多次随机仍无法达到期望色相距离，可选择与现有颜色最远的候选色；不得退回固定颜色数组。
- 节点数字默认使用白色，并确保上述亮度范围不会生成白字难以识别的浅色背景。
- 随机源继续允许注入或集中封装，使尺寸、颜色、房间号和位置由同一个节点创建逻辑产生，避免组件层零散调用随机函数。
- 颜色的随机结果属于节点状态，重渲染、昵称修改或语言切换不得改变现有节点颜色。

### 7. 主题兼容性与后续待办

- 本轮保持现有浅色主题，不增加主题切换按钮，不实现深色 Token，也不持久化主题偏好。
- 雷达节点的边框、外层光晕、阴影、标签背景、标签文字以及 Footer 交互色改用页面级语义 CSS 变量。
- 变量提供当前浅色默认值，后续深色主题可以只覆盖变量而不修改节点生成算法。
- 随机 HSL 背景色可继续由内联变量传递，但组件不能硬编码与浅色背景绑定的边框和阴影值。
- 在项目待办文档新增“前端主题”事项：后续实现全站浅色／深色模式、主题切换入口、偏好持久化、Ant Design Token、雷达与房间页适配。本 PRD 只记录待办，不实现该功能。

### 8. Footer 桌面端行为

- Footer 的简短标签选择规则保持不变：精确 Tag 构建显示 Tag，非 Tag 构建显示短提交标识，元数据缺失显示 `dev`。
- 桌面端继续使用可聚焦的版本按钮作为 Tooltip 触发器。
- Tooltip 整体定位在版本按钮右侧，采用右侧 placement；不是仅改变箭头方向。
- Tooltip 内容严格只有两行：版本、构建时间。删除状态、分支和提交标识三项。
- Tooltip 中的版本使用完整版本值；构建时间使用版本接口返回并由现有格式化逻辑处理，无值时显示统一占位符。
- Tooltip 支持鼠标悬停和键盘聚焦，不再需要点击触发。
- Tooltip 的箭头由组件定位自动生成，不通过自定义绝对坐标硬移箭头。

### 9. Footer 移动端行为

- 以项目现有移动端断点判定 Footer 形态，保持和首页响应式断点一致。
- 移动端不渲染 Tooltip，也不允许点击后打开悬浮层。
- 移动端版本标签渲染为普通文本或非交互元素，不能保留按钮角色、点击手势、焦点或“查看完整版本信息”的无效可访问名称。
- Footer 在移动端仍显示同一简短版本标签，完整信息继续在个人中心展示。
- 桌面与移动端共享版本 Query 和标签格式化结果，不能因条件渲染额外请求一次版本接口。
- 断点变化时组件应正确切换交互形态，不能留下已打开的 Tooltip。

### 10. 右侧房间区域入口精简

- 删除房间列表上方的“创建房间”和“加入房间”两个大按钮及其占位区域。
- “我的房间”标题右侧不再渲染“创建房间”按钮。
- 没有自建房间时，既有固定高度虚线空卡片是唯一创建入口，点击后打开现有创建房间 Modal。
- 有自建房间时显示真实自建房间卡片，不再在“我的房间”区域提供额外创建入口。一个匿名用户只能创建一个有效房间的业务限制不变。
- 下方分区标题从“成员”改为“参与房间”，英文使用含义明确的对应翻译。
- “参与房间”标题右侧显示唯一“加入房间”操作，点击后打开现有四位房间号 Modal。
- “参与房间”没有数据时显示简洁空状态，空状态内不再出现第二个加入入口。
- 桌面和移动端都使用相同入口结构；不得仅通过 CSS 隐藏重复按钮而把其保留在键盘焦点顺序中。

### 11. 房间卡片内容

- 自建房间与参与房间使用同一张房间卡片结构。
- 左侧继续突出显示四位 `roomCode`，不得用标题取代房间号。
- 右侧读取并显示 `room.title`。当前默认值形如“房间 5369”，不得在前端重新拼接默认标题。
- 删除普通状态下的“房主”和“成员”角色文案；角色仍用于决定所属分区及可用操作，不能从业务模型中删除。
- 房间标题占用单行，超出卡片可用宽度时使用省略号；不得撑宽侧栏或换行增加卡片高度。
- 桌面端对被省略的标题提供完整文本 Tooltip。未溢出时可以不显示 Tooltip，避免无意义浮层。
- 移动端不依赖标题 Tooltip；完整标题应在后续房间详情中可见，卡片保持单行省略。
- `destroying` 状态标签、禁用样式和不可操作规则保持不变；房间标题仍可显示。

### 12. 房间操作文案

- 对已经出现在“我的房间”或“参与房间”列表中的房间，主操作翻译键改为独立的“进入房间”，不得复用“加入房间”键。
- 桌面悬停／键盘聚焦浮层中的主按钮显示“进入房间”。
- 移动端底部 Drawer 中的主按钮同步显示“进入房间”。
- “参与房间”标题右侧和输入房间号 Modal 继续显示“加入房间”，因为该动作会建立新的成员关系。
- 点击进入后的路由、权限检查与 `destroying` 禁用行为不变。

### 13. 头像菜单与个人中心标题

- 已建立身份后的头像下拉菜单第一项中文改为“个人中心”，英文改为 `Profile` 或项目现有一致表达。
- 点击后打开的 Modal 标题使用相同翻译键，确保菜单名称与弹窗名称一致。
- 首次建立身份前仍不显示个人中心入口，只显示语言切换；该行为不变。
- 不修改通知图标、语言切换文案和头像首字生成规则。

### 14. 个人中心随机昵称

- 个人中心显示名称区域使用“输入框 + 随机按钮”的组合，再保留独立的“保存名称”动作；不得把随机按钮替代保存按钮。
- 随机按钮使用骰子或现有随机语义图标，并提供本地化的可访问名称和 Tooltip。
- 点击随机按钮调用现有随机昵称接口。禁止在前端维护重复的人名列表或用纯客户端随机字符串替代。
- 请求成功后只把返回名称写入个人中心的本地草稿输入框，不自动调用更新会话接口，不自动关闭 Modal。
- 用户可对候选名称继续手动编辑，也可再次点击随机。
- 只有用户点击“保存名称”时才调用现有昵称更新接口。成功后更新会话 Query，使个人中心头像、首页中心头像、中心昵称和右上角头像统一更新。
- 随机请求期间禁用随机按钮或显示加载状态，防止连续重复请求；保存请求期间遵循现有保存加载和禁用规则。
- 随机请求失败时保留当前草稿，显示统一 API 错误翻译；失败不得影响保存手动输入的能力。
- Modal 每次打开时仍以当前真实会话昵称初始化草稿；关闭且未保存的随机或手动结果不得泄漏到真实会话。

### 15. 注册时间格式

- 会话 `createdAt` 继续按 Unix 秒解释，不修改接口单位。
- 使用浏览器本地时区构造日期，不强制转为 UTC，也不使用服务端时区。
- 输出固定为 `YYYY-MM-DD HH:mm:ss`，例如 `2026-07-30 20:05:50`。
- 月、日、时、分、秒始终补齐两位；年份显示四位。
- 简体中文与 English 使用完全相同的数字格式，不使用浏览器的 `dateStyle` 或语言相关月份名称。
- 不显示时区名称、时区缩写、毫秒或相对时间。
- `createdAt` 缺失、为零或无法解析时继续显示统一占位符，不抛出渲染异常。

### 16. 中英文文案

- 至少补充或调整以下语义的中英文翻译：个人中心、参与房间、进入房间、随机生成名称，以及因布局变化受到影响的空状态和可访问名称。
- Footer 的“版本”和“构建时间”继续使用已有字段翻译；删除 Tooltip 字段不代表删除个人中心的完整版本翻译。
- “加入房间”与“进入房间”必须是两个不同翻译键，禁止靠组件拼接或上下文猜测。
- 中英文切换后，房间标题来自后端业务数据，不进行前端翻译；默认标题仍按数据库当前内容原样显示。

### 17. 实施顺序与提交边界

1. 先修复雷达节点长期累积问题，再调整节点模型、随机尺寸、HSL 颜色和实际半径碰撞算法；同步完成样式变量及响应式边界，运行自动检查后独立提交。
2. 再调整 Footer 桌面／移动端形态、右侧房间入口、分区名称、房间标题和进入文案；同步补齐中英文，运行自动检查后独立提交。
3. 最后增强个人中心随机昵称和注册时间格式，并把深色主题加入待办；运行完整自动检查后独立提交。
4. 三个阶段完成后按人工验收清单由用户验证。人工发现的问题作为同一 PRD 的修正继续处理，除非需要改变本 PRD 已确认的范围或接口。

- 每次提交只暂存本阶段相关文件，不得包含静态构建产物、临时预览文件或用户无关改动。
- Git 提交信息必须使用 Conventional Commits：英文 `type`、英文 `scope`、简体中文 `description`，description 禁止中英混合。
- 提交正文引用本 PRD 的仓库相对路径 `docs/plan/2026-07-30-homepage-visual-polish.md`；不得把路径放进必须为纯简体中文的 description。

## Testing Decisions

- 本轮不引入 Playwright、Vitest、Jest、视觉快照或新的测试依赖。
- 不编写普通展示组件测试。测试重点遵循项目规则，只覆盖已有业务边界、鉴权与复杂状态；本轮未改变这些逻辑，因此不新增自动化业务测试。
- 每个实施阶段运行 `bun run build`，验证 TypeScript 类型检查和 Vite 生产构建成功。
- 每个实施阶段运行 `go test ./...`，确认前端优化没有通过共享类型或嵌入流程破坏现有 Go 工程。
- 最终运行 `git diff --check`，确保没有空白错误。
- 不把 Playwright 截图、浏览器快照、人工测试产物或 `static/dist` 编译文件提交到 Git。

### 人工验收：桌面端

1. 使用约 `1440×900` 视口打开首页，确认中心头像为 `112px`，周围恰好有五个装饰房间。

3. 连续观察至少三十一秒，确认节点逐个替换而非同时消失；已有节点在替换其他节点时不改变尺寸和颜色。
4. 继续让页面在前台运行至少十分钟，每隔一段时间目视确认只有五个节点，并通过开发者工具查询 `.radar-node`，结果必须始终为 `5`。
5. 在一次节点退出动画期间查询 DOM，确认数量仍为 `5`，不得短暂出现第六个节点。

## Further Notes

- 低智能编码模型实施时必须先区分“加入房间”和“进入房间”：前者通过四位房间号建立新关系，后者打开用户已经拥有或参与的房间。两者不能共用显示文案。
- 房间卡片显示标题不代表本轮支持修改标题。必须直接显示接口现有字段，不能在前端临时构造，也不能因为默认标题包含房间号而删掉左侧大号房间号。
- 随机色的目标不是覆盖一千六百万种 RGB，而是在足够丰富的颜色空间内保证可读性和同屏辨识度。实现不得退回固定六色数组。
- 不同尺寸碰撞是本轮风险最高的纯视觉状态。计算时必须同时考虑圆形、标签、中心名称和容器尺寸；只把 CSS 宽高改为随机值而不修改位置算法不算完成。
- 五节点数量是严格不变量。通过 CSS 隐藏多余节点、渲染时临时截取前五项或刷新页面清空累积状态，都不算修复长时间运行缺陷。
- 移动端“无 Tooltip”是结构性要求，不是只通过隐藏浮层内容实现。移动端不应保留无效按钮语义。
- 个人中心随机昵称是草稿操作。不得在随机接口成功后自动保存、自动关闭 Modal 或提前更新全局会话缓存。
- 若实施发现必须修改后端接口、数据库、房间业务规则或本 PRD 的验收口径，应先更新本 PRD 并获得用户明确批准后继续。
