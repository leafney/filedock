# FileDock 首页雷达布局 HTML 原型 PRD

## Problem Statement

FileDock 当前首页采用深色背景和多张卡片平铺的双栏布局。匿名身份、房间列表、创建房间、加入房间和服务信息同时占据主页面，视觉层级不够集中。随着后续文件传输、聊天、上传进度和下载队列加入，继续沿用当前布局会使页面更加拥挤，并扩大后续重构成本。

用户希望先通过一个不影响现有业务代码的首页视觉原型，验证新的信息架构：左侧以当前用户为中心营造局域网房间发现氛围，右侧通过渐进式操作栏承载身份、创建、加入和房间列表。确认视觉方向后，再为正式 React 首页重构制定开发计划。

## Solution

制作一个独立、可在浏览器直接访问的首页 HTML 原型。原型采用 React 与 Ant Design 组件，但只使用本地模拟状态，不调用 FileDock API，也不替换现有首页路由。

页面使用浅色视觉系统。桌面端由左侧动态雷达区域和右侧操作区域组成；左侧约占可用宽度的 80%，右侧保持适合表单操作的固定宽度。中心用户头像由昵称首字生成，周围以随机房间节点和信号波纹表现局域网活跃氛围。右侧根据“首次访问”和“已建立身份”两种模拟状态切换内容，复杂操作通过 Ant Design Modal 展示。

原型完成后，使用 `playwright-cli` 的持久化可见浏览器打开页面，在桌面和移动尺寸下检查布局、动画、交互和控制台错误，并输出截图供用户评审。

## User Stories

1. 作为首次访问者，我希望首页是明亮、轻量的视觉风格，以便快速理解这是一个易用的局域网分享工具。
2. 作为首次访问者，我希望右侧首先展示昵称选择流程，以便完成匿名身份初始化。
3. 作为首次访问者，我希望能够看到一个随机建议昵称，以便不必自己构思名称。
4. 作为首次访问者，我希望昵称确认后进入已建立身份状态，以便预览后续首页结构。
5. 作为中文昵称用户，我希望头像显示昵称的第一个汉字，以便快速识别自己的身份。
6. 作为英文昵称用户，我希望头像显示昵称的首字母，以便头像规则保持直观。
7. 作为已建立身份的用户，我希望在页面中心看到自己的彩色圆形头像和昵称，以便明确当前匿名身份。
8. 作为用户，我希望中心头像周围显示持续扩散的信号波纹，以便感受到局域网连接和发现的概念。
9. 作为用户，我希望周围房间节点能够随机出现和消失，以便页面呈现持续活跃的效果。
10. 作为用户，我希望房间节点的位置随机变化，以便动画不会机械重复。
11. 作为用户，我希望房间节点数量在合理范围内随机变化，以便表现局域网活跃程度的变化。
12. 作为用户，我希望房间号为随机四位数字，以便节点看起来像 FileDock 房间。
13. 作为用户，我希望装饰房间节点不可点击，以免误以为它们是真实可加入房间。
14. 作为用户，我希望房间节点使用柔和彩色圆形头像，并在下方显示房间号，以便视觉结构与中心头像一致。
15. 作为减少动态效果的用户，我希望系统尊重操作系统的动画偏好，以免持续动画造成不适。
16. 作为已建立身份的用户，我希望右侧顶部显示通知图标，以便未来查看房间申请通知。
17. 作为已建立身份的用户，我希望右侧顶部显示用户小头像，以便访问个人相关功能。
18. 作为用户，我希望点击用户头像打开下拉菜单，以便首页保持简洁。
19. 作为用户，我希望下拉菜单第一项是个人中心，以便查看和维护身份。
20. 作为用户，我希望下拉菜单第二项是切换语言，以便在简体中文和 English 之间切换。
21. 作为用户，我希望个人中心在 Modal 中打开，以便不离开首页即可管理身份。
22. 作为用户，我希望个人中心展示当前昵称，以便确认正在使用的身份。
23. 作为用户，我希望个人中心允许修改昵称，以便后续调整显示名称。
24. 作为用户，我希望个人中心展示模拟注册时间，以便验证未来信息布局。
25. 作为用户，我希望个人中心提供账户重置入口，并使用危险操作样式，以便理解其影响。
26. 作为用户，我希望右侧主体只显示创建房间、加入房间和我的房间，以便主要任务足够突出。
27. 作为用户，我希望点击创建房间后打开 Modal，以便配置验证方式而不挤占首页空间。
28. 作为用户，我希望点击加入房间后打开 Modal，以便输入房间号而不展开常驻表单。
29. 作为用户，我希望我的房间以紧凑列表展示，以便快速进入已有房间。
30. 作为没有房间的用户，我希望看到简洁空状态，以便理解下一步可以创建或加入。
31. 作为桌面用户，我希望左侧视觉区约占 80%，右侧操作区约占 20%，以便动画成为视觉主体。
32. 作为平板用户，我希望右侧仍有足够宽度容纳表单，以便操作不会拥挤。
33. 作为手机用户，我希望页面自动改为上下布局，以便动态区域和操作区都能正常使用。
34. 作为键盘用户，我希望按钮、菜单、输入框和 Modal 都具有清晰焦点，以便完成全部交互。
35. 作为评审者，我希望通过可见浏览器查看原型并获得桌面与移动截图，以便判断是否进入正式重构。

## Implementation Decisions

- 本 PRD 只交付独立首页视觉原型，不修改现有生产首页、路由、服务端接口、数据库或 SSE。
- 原型使用现有前端技术栈中的 React，并新增 Ant Design 作为组件库；图标使用 Ant Design Icons 或现有一致图标集，不使用 Emoji 充当功能图标。
- 原型提供独立 HTML 入口，由 Vite 开发服务器直接访问；入口不得被现有生产页面自动引用。
- 所有状态均为前端模拟状态，包括匿名身份、注册时间、通知数量、我的房间、创建结果和加入结果。
- 动态房间不读取真实房间数据，不请求 API，不保存到 localStorage，不与“我的房间”列表混用。
- 动态房间节点不包含中心当前用户；除中心用户外，页面始终维护 5 个其他房间节点，不得只显示 3 个或 4 个。节点必须逐个进入、逐个退出，每次只替换一个节点，禁止整批同时出现或消失，以形成自然的错落感。
- 房间号生成范围为 `0001`～`9999`，必须保留前导零；仅用于装饰，不得绑定点击事件。
- 每个房间节点包含彩色圆形头像和下方的“房间 1234”标签。节点颜色从预设的低饱和蓝、绿、紫、橙、粉色中选择。
- 节点位置不得使用固定槽位；每次出现时均重新生成随机百分比坐标，并通过中心禁入区、页面边界和节点最小间距校验避免遮挡中心用户、主要标题、其他房间和页面边缘。
- 节点生命周期包括淡入、轻微漂浮、停留和淡出。单次过渡控制在 200～500ms，每个节点独立停留 10～30 秒；生命周期结束后逐个淡出，新节点在新的随机位置逐个出现。
- 中心区域使用 CSS 或 SVG 绘制三至四层半圆/同心波纹。波纹动画只改变透明度和缩放，不触发布局重排。
- 系统启用 `prefers-reduced-motion: reduce` 时，停止节点漂浮和波纹扩散，仅定期以无动画方式更新少量节点，或保持静态。
- 中心用户头像使用昵称首字。中文及其他非拉丁文字取第一个可见 Unicode 字符；英文取去除首尾空白后的首字母并转为大写。
- 首页雷达中心不显示在线状态圆点，也不在昵称下方显示“在线”状态文案。
- 头像背景色根据昵称计算稳定颜色，同一昵称在当前原型会话中保持一致。
- 页面采用明亮中性背景、清晰深色正文和蓝绿色主强调色。避免当前深色 `slate` 背景、霓虹高光和大面积渐变。
- 桌面布局采用主区域加固定侧栏：左侧占剩余空间，右侧建议宽度 300～340px，整体在常见宽屏上接近 80/20。
- 平板保持双栏，但缩小间距和右栏宽度；手机断点改为上下布局，视觉区域高度建议为 45～55vh。
- 右侧顶部固定菜单区依次展示通知按钮和用户头像。首次身份建立前，用户头像可使用候选昵称生成，并保持菜单功能可预览。
- 用户头像菜单使用 Ant Design Dropdown，菜单项依次为个人中心和切换语言。语言菜单直接显示目标语言名称 `English` 或 `简体中文`，不得添加“更改为”“切换为”等动作前缀。
- 个人中心使用 Ant Design Modal，展示头像、昵称编辑、模拟注册时间和账户重置。重置按钮使用危险操作样式并增加确认步骤。
- 初始状态右侧主体只展示品牌说明、昵称输入、随机昵称按钮和确认按钮。昵称输入值必须实时驱动左侧中心头像、左侧昵称和右上角头像；手动输入及随机昵称均应使三个位置同步变化，无需等待确认。
- 确认昵称后，右侧主体切换为创建房间、加入房间和我的房间，不再展示首页昵称输入框。
- 创建房间使用 Modal，至少演示免验证、PIN 验证和房主审批三种选择；PIN 模式显示四位 PIN 输入效果。
- 加入房间使用 Modal，演示四位房间号输入和确认按钮。
- 我的房间使用紧凑列表，展示少量模拟房间、角色和状态；列表与左侧装饰节点必须有明显语义区别。
- 所有用户可见文字同时提供 `zh-CN` 与 `en`。原型可以使用本地字典，但不得在正式 React 组件迁移时硬编码文案。
- 原型不使用真实 ShareDrop 标志、头像或版权素材，只参考中心辐射式构图。
- `ui-ux-pro-max` 建议的最小对比度、稳定 Hover、150～300ms 交互过渡、可见焦点和响应式检查均为交付要求。

## Testing Decisions

- 本原型不包含业务逻辑、鉴权、支付或复杂状态机，因此不编写后端或业务单元测试。
- 运行 TypeScript 检查和 Vite 构建，确保新增原型入口能够编译。
- 使用 `playwright-cli` 的默认持久化可见浏览器和固定 profile 打开原型。
- 在约 1440×900 桌面尺寸检查：主次分栏、中心头像、波纹、随机节点、顶部菜单、右侧按钮和房间列表。
- 在约 390×844 移动尺寸检查：上下布局、无横向滚动、操作区可见、Modal 不溢出视口。
- 通过浏览器快照操作：确认昵称、打开头像下拉菜单、打开个人中心、切换语言、打开创建房间 Modal、打开加入房间 Modal。
- 观察多个时间点，确认房间节点的位置、编号和数量发生变化，且不会覆盖中心用户或右侧区域。
- 使用浏览器控制台检查运行错误和资源加载错误。
- 使用可见浏览器截图输出至少一张桌面效果图；如移动布局存在明显差异，再输出一张移动效果图。
- 测试只验证用户可观察行为和视觉结构，不依赖组件内部状态名称或定时器实现细节。

## Out of Scope

- 不替换或重构现有生产首页。
- 不接入真实匿名会话、房间列表、通知、创建房间或加入房间 API。
- 不改变现有后端数据模型、路由、错误码、Cookie 或 SSE。
- 不实现真实局域网房间发现，也不公开真实房间号。
- 不实现头像上传、头像数据库字段或动物头像资源。
- 不实现正式的设计令牌迁移、全站 Ant Design 改造或房间详情页重构。
- 不将原型中的模拟注册时间、通知数量或我的房间写入本地存储。
- 不在本 PRD 中决定文件上传、聊天和下载队列的最终页面布局。

## Further Notes

- 该原型的目标是快速验证首页信息架构和视觉方向。用户确认后，应另建正式首页重构 PRD，将通过的设计拆分为可复用布局、头像、雷达背景、顶部菜单、个人中心、房间操作 Modal 和真实房间列表组件。
- 当前原型文件仅供临时评审，不属于正式首页实现。正式首页重构开始时，必须迁移已确认的视觉规则后删除 `frontend/homepage-prototype.html`、`frontend/src/prototype/`、原型截图与 Vite 原型多入口配置，不得让正式页面依赖原型入口或原型组件。
- 原型阶段新增的共享依赖应在正式重构时逐项复核：正式页面实际使用的 Ant Design 依赖可以保留；仅由原型使用的依赖必须从 `frontend/package.json` 与锁文件中移除。
- 正式重构时需要重新审查 Ant Design 与现有 Tailwind 的边界，避免两套样式系统在同一组件中无规则混用。
- 左侧装饰房间可能让用户误以为可以点击，因此必须通过弱化 Hover、默认光标和清晰的右侧加入入口表达其装饰属性。
- 设计原型通过后，再讨论通知图标在正式产品中的聚合规则和未读数量来源。
