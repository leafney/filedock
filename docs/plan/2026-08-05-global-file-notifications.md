# FileDock 全局文件通知一期 PRD

状态：已批准，实施中

日期：2026-08-05

## Problem Statement

FileDock 已有全局通知中心，但目前只显示房主待处理的加入审批和当前用户跨房间未读的一对一聊天。私密文件是项目核心协作对象，接收者在首页或其他房间时，却无法从全局铃铛得知新文件已经可用；发送者也无法在离开原房间页面后得知文件被拒绝或首次成功下载。

现有文件 SSE 会刷新正在打开的房间文件列表，但它不是跨页面可回看的未读通知。若直接把每个文件事件都显示为通知，上传进度、下载开始和重复下载会迅速制造噪声；若只从当前文件状态临时推导拒绝和下载结果，又无法判断发送者是否已经看过。

下一阶段需要在现有全局通知中心内加入范围克制的文件通知：只提醒收到可用的私密文件、私密文件被拒绝、私密文件被接收者首次成功下载。通知必须遵守当前房间与文件权限，支持聚合、真实数量角标、跨标签页已读同步和房间生命周期自动失效，同时不能在通知抽屉中复制文件接收、拒绝或下载操作。

## Solution

扩展现有全局通知中心，增加三类文件通知：待接收私密文件、私密文件被拒绝、私密文件首次下载完成。

待接收私密文件属于仍需用户处理的业务状态。只有文件完整上传成功并可用，或已有私密文件成功再次发送后才出现；通知保持显示，直到接收者在房间私密文件区域接收或拒绝。点击通知只打开对应房间，不在抽屉内提供接收、拒绝或下载按钮。

拒绝与首次下载完成属于信息型结果。新增轻量通知记录保存结果的接收用户、业务来源和已读状态。同一房间、同一相关成员、同一结果类型聚合显示；点击聚合项后只把当前快照中的结果标记已读，点击期间新到结果仍保持未读。

铃铛总数继续表示实际未处理数量：待审批请求数、未读聊天消息数、待接收私密文件数、未读文件结果数之和。列表固定按“审批、待接收文件、聊天与文件结果”的优先级展示。复用现有用户级 SSE 连接刷新 REST 通知快照，不新增 SSE 连接、轮询通道、浏览器系统通知或顶部消息。

## User Stories

1. 作为私密文件接收者，我希望文件完整上传成功后在全局铃铛看到提醒，以便我不在原房间页面时仍能发现新文件。
2. 作为私密文件接收者，我希望上传中的文件不产生通知，以免进入房间后看到尚不可用的文件。
3. 作为私密文件接收者，我希望上传失败或取消的文件不产生通知，以免收到无法处理的提醒。
4. 作为私密文件接收者，我希望别人再次向我发送已有私密文件时收到新提醒，以便我知道该文件重新进入待接收状态。
5. 作为私密文件接收者，我希望通知显示发送者昵称、房间、最新文件名和数量，以便判断提醒来源。
6. 作为隐私敏感用户，我希望通知不显示其他接收者、私密编号、下载地址、内部 ID 或文件内容，以免泄露不必要信息。
7. 作为私密文件接收者，我希望通知抽屉不提供接收和拒绝按钮，以便所有文件决策仍在完整房间上下文中完成。
8. 作为私密文件接收者，我希望点击通知只打开对应房间，以便在私密文件区域查看并处理文件。
9. 作为私密文件接收者，我希望仅打开通知抽屉不会清除待接收提醒，以免尚未处理时丢失入口。
10. 作为私密文件接收者，我希望点击待接收通知也不会把它标记已读，以便它持续提醒到接收或拒绝为止。
11. 作为私密文件接收者，我希望接收文件后待接收通知自动消失，以便铃铛反映真实待办。
12. 作为私密文件接收者，我希望拒绝文件后待接收通知自动消失，以便不再看到已处理项目。
13. 作为私密文件发送者，我希望接收者拒绝文件后收到全局结果通知，以便我决定是否重新发送或改用其他方式。
14. 作为私密文件发送者，我希望接收者首次完整下载后收到全局结果通知，以便我确认交付成功。
15. 作为私密文件发送者，我希望接收动作本身不产生结果通知，以免下载尚未完成时误以为文件已经交付。
16. 作为私密文件发送者，我希望下载中断、取消或过期不产生完成通知，以免成功状态失真。
17. 作为私密文件发送者，我希望同一接收者重复下载同一文件时不再产生通知，以免被重复结果打扰。
18. 作为私密文件发送者，我希望一份文件发给多名成员时按每名成员分别记录结果，以便知道各自处理情况。
19. 作为通知中心用户，我希望同一房间同一发送者的多个待接收文件聚合，以便列表保持紧凑。
20. 作为通知中心用户，我希望同一房间同一接收者的同类结果聚合，以便不会为每个文件占用一行。
21. 作为通知中心用户，我希望拒绝和下载完成分开聚合，以便两种结果不会混淆。
22. 作为通知中心用户，我希望不同房间或不同成员的文件通知分开显示，以便点击后进入正确上下文。
23. 作为通知中心用户，我希望聚合项显示最新文件名和实际文件数量，以便快速理解该组最近活动。
24. 作为通知中心用户，我希望铃铛按实际文件数量计数，而不是按聚合行数计数，以便角标准确。
25. 作为通知中心用户，我希望点击聚合结果后当前包含的全部结果一起变为已读，以便不必逐个点击。
26. 作为通知中心用户，我希望点击期间新产生的结果仍保持未读，以免并发消息被错误清除。
27. 作为通知中心用户，我希望只打开抽屉不会把任何文件结果标记已读，以便已读代表主动点击。
28. 作为通知中心用户，我希望没有“全部已读”操作，以便不会一次清除尚未理解的审批、聊天或文件提醒。
29. 作为通知中心用户，我希望待审批请求始终排在最前，以便房主优先处理准入事项。
30. 作为通知中心用户，我希望待接收私密文件排在审批之后，以便文件待办优先于普通信息。
31. 作为通知中心用户，我希望未读聊天和文件结果按最新时间混排，以便最近活动更容易发现。
32. 作为在其他房间工作的用户，我希望点击文件通知进入目标房间，以便继续处理对应文件。
33. 作为已经位于目标房间的用户，我希望点击文件通知只关闭抽屉并刷新文件列表，以便页面不发生无意义跳转。
34. 作为移动端正在聊天的用户，我希望点击文件通知后退出聊天全屏并回到文件区域，以便能看到房间文件。
35. 作为用户，我希望点击文件通知不自动改变文件筛选、滚动位置或高亮状态，以便交互保持简单可预测。
36. 作为用户，我希望点击文件通知不自动接收、拒绝或下载，以免通知点击触发有副作用的文件操作。
37. 作为多标签页用户，我希望一个标签页读取文件结果后，其他标签页的铃铛也及时更新，以便状态一致。
38. 作为多标签页用户，我希望文件通知继续使用现有用户级 SSE，以免浏览器建立额外长连接。
39. 作为网络恢复后的用户，我希望 REST 通知快照仍是权威状态，以便 SSE 丢失或重连不会永久漏通知。
40. 作为房间成员，我希望离开房间后立即看不到该房间文件通知，以便权限失效同步生效。
41. 作为重新加入的同一匿名身份，我希望仍待接收且仍有效的文件提醒可以重新出现，以便恢复可访问业务状态。
42. 作为房间成员，我希望房间失效后相关文件通知立即消失，以免点击进入无法访问的房间。
43. 作为系统维护者，我希望房间清理时删除关联通知记录，以免留下孤立数据。
44. 作为系统维护者，我希望已读结果不进入历史列表，以便通知中心继续只展示待办和未读信息。
45. 作为系统维护者，我希望通知记录不保存文件内容、文案或用户语言，以便减小数据范围并遵守本地化边界。
46. 作为系统维护者，我希望同一文件投递代次的通知生成保持幂等，以免 API 重试或事件刷新制造重复角标。
47. 作为系统维护者，我希望文件再次发送具有新的投递代次，以便旧拒绝结果不会在新投递后错误复活。
48. 作为系统维护者，我希望首次下载完成使用服务端完整字节流结果判定，以便通知不依赖前端猜测。
49. 作为简体中文用户，我希望所有文件通知标题、说明、数量和错误都有中文文案，以便完整使用功能。
50. 作为 English 用户，我希望所有新增通知文案都有对应英文翻译，以便切换语言后不出现缺失键或中文硬编码。
51. 作为键盘与辅助技术用户，我希望文件通知项具有可读名称、可聚焦并能通过键盘激活，以便无需鼠标完成导航。
52. 作为移动端用户，我希望文件通知在现有抽屉宽度与触控区域内正常显示，以便窄屏仍可使用。
53. 作为项目维护者，我希望核心状态转换、权限、聚合和已读并发有自动化测试，以便后续扩展通知类型时不破坏现有行为。

## Implementation Decisions

### 1. 阶段范围与权威关系

- 本 PRD 是现有全局通知中心的文件通知增量规格；与早期总 PRD或旧待办冲突时，以本 PRD 和已经批准的后续通知、文件 PRD 为准。
- 只增加三种通知类型：`file_received`、`file_declined`、`file_downloaded`。
- `file_received` 表示当前用户仍待处理的私密文件。
- `file_declined` 表示当前用户发送的私密文件被指定接收者拒绝。
- `file_downloaded` 表示当前用户发送的私密文件被指定接收者第一次完整下载成功。
- 不改变共享／私密文件可见性、接收、拒绝、下载、复用或发布为共享文件的既有权限规则。
- 不把通知记录当作文件状态事实来源。文件、接收关系、房间和成员状态仍是业务事实；通知记录只保存一次通知发生及信息型结果的已读状态。

### 2. 深模块划分

实施仍位于现有单服务和现有前端应用内，不拆新工程或独立服务。

1. 通知记录模块封装文件通知生成、幂等键、投递代次、已读水位和清理，不由 API 或前端直接操作数据库。
2. 文件服务继续负责上传完成、再次发送、拒绝和下载完成状态转换，并在同一数据库事务内调用通知记录模块。
3. 通知查询模块统一聚合审批、聊天和文件通知，计算排序、分页及铃铛总数。
4. 通知 API 继续提供快照查询，并增加文件结果聚合项已读命令。
5. 现有用户级 SSE 只负责提示客户端刷新通知快照，不携带最终展示文案。
6. 前端通知中心负责类型渲染、数量、读操作、导航和移动端退出聊天；不重复文件业务按钮。

### 3. 数据模型

#### 3.1 文件接收关系投递代次

- 为每个文件与接收者关系增加正整数投递代次，初始值为 1。
- 已拒绝文件再次发送给同一接收者时，投递代次原子加 1，并把状态重置为待接收、刷新发送时间、清空接收／拒绝／首次下载／最后下载时间和下载次数。
- 其他已经待接收、已接收或已下载关系继续沿用现有跳过规则，不增加投递代次。
- 每条文件通知记录保存生成时的投递代次。查询时必须与接收关系当前代次相等，防止旧拒绝或旧待接收通知在再次发送后复活。

#### 3.2 轻量通知记录

新增通知记录，至少保存：

- ULID 通知 ID。
- 接收通知的用户 ID。
- 通知类型。
- 房间 ID、文件 ID。
- 相关成员 ID：收到文件时为发送者，结果通知时为接收者。
- 文件接收关系 ID和投递代次。
- 来源文件事件 ID，用于诊断和幂等。
- 发生时间，使用足以支持已读水位的毫秒精度 UTC 时间。
- 可空已读时间。待接收类型不通过点击写已读；结果类型点击后写入。

约束：

- 同一通知接收用户、类型、文件接收关系、投递代次最多一条记录。
- 所有外键业务有效性由查询显式验证，不能因存在通知记录而恢复文件权限。
- 不保存文件名、成员昵称、房间标题等展示快照；查询时从当前授权业务数据投影。
- 不保存翻译后的通知文案、用户语言、文件内容、私密编号、MIME、大小、存储名或下载地址。
- 项目处于开发阶段，直接调整自动建表结构；不实现旧数据迁移、回填或专用清理脚本。

### 4. 通知生成状态转换

#### 4.1 新上传的私密文件

- 创建上传批次、容量预留、文件处于保留或上传中时不得生成通知记录。
- 只有文件内容完整写入、大小校验通过、文件状态在事务中变为可用时，才为当前投递代次下仍为待接收的每个接收者生成一条 `file_received` 记录。
- 通知记录与文件完成状态必须在同一事务提交。任一通知记录失败时整个完成事务失败，避免文件已可用但通知缺失。
- 共享文件不生成记录。
- 上传失败、取消、过期或服务启动恢复为失败时不生成记录。

#### 4.2 再次发送已有私密文件

- 只对从已拒绝成功恢复为待接收的关系增加投递代次并生成新的 `file_received` 记录。
- 原本不存在的文件与接收者关系以投递代次 1 创建，并生成 `file_received` 记录。
- 被现有规则跳过的关系不生成通知。
- 文件关系状态、文件事件和通知记录必须在同一事务提交。

#### 4.3 拒绝私密文件

- 接收关系从当前投递代次的待接收原子变为已拒绝。
- 原 `file_received` 记录无需标记已读；因为关系不再待接收，查询自然不再展示。
- 同一事务为文件上传者生成一条 `file_declined` 记录，相关成员为执行拒绝的接收者。
- 重复拒绝或状态不匹配继续返回现有状态错误，且不得生成重复记录。

#### 4.4 接收私密文件

- 接收关系从待接收变为已接收后，`file_received` 通知因业务状态变化自动消失。
- 接收动作本身不为上传者创建信息型通知。
- 自动创建下载任务失败不恢复待接收通知；文件仍保持已接收，用户可沿用现有下载入口重试。

#### 4.5 首次完整下载

- 只有下载流完成全部预期字节、写入响应成功并进入现有下载完成事务后，才允许生成结果通知。
- 在同一事务内原子判断该文件与接收者关系的首次下载时间是否为空。
- 首次为空时：写入首次／最后下载时间、增加下载次数、状态变为已下载，并为上传者生成一条 `file_downloaded` 记录。
- 已有首次下载时间时：只更新最后下载时间和下载次数，不生成新通知。
- 下载中断、客户端取消、流写入失败、任务过期、文件大小不匹配或并发限制失败均不生成完成通知。
- 上传者下载自己的私密文件、任意成员下载共享文件均不生成本阶段通知。

### 5. 文件通知有效性与权限过滤

通知查询必须同时满足以下条件：

- 房间状态为活动，尚未过期。
- 当前通知用户仍是该房间活动成员。
- 文件仍存在、状态为可用且范围仍为私密。
- 当前文件接收关系存在，且记录投递代次等于关系当前投递代次。
- `file_received`：当前通知用户就是该关系接收者，关系状态严格为待接收，相关成员就是文件上传者。
- `file_declined`：当前通知用户就是文件上传者，关系状态严格为已拒绝，相关成员就是关系接收者，记录尚未已读。
- `file_downloaded`：当前通知用户就是文件上传者，关系状态为已下载，首次下载时间存在，相关成员就是关系接收者，记录尚未已读。

补充规则：

- 当前用户离开、被踢或身份失效后立即失去相关文件通知。
- 同一匿名身份重新成为活动成员后，仍处于当前投递代次且待接收的文件通知可以再次出现。
- 相关发送者或接收者后来离开房间，不应抹去当前用户仍有权限查看的历史结果；昵称可从房间成员记录读取，但不得因此授予相关成员任何新权限。
- 文件发布为共享文件、文件失效或房间进入销毁流程后，相关文件通知立即不再展示。
- API 不得因通知记录存在而返回当前用户无权看到的文件名或成员关系。

### 6. 聚合键、内容与计数

聚合规则：

- `file_received`：按通知用户、房间、文件上传者聚合。
- `file_declined`：按通知用户、房间、执行拒绝的接收者聚合。
- `file_downloaded`：按通知用户、房间、首次下载的接收者聚合。
- 不同通知类型永不合并。

每个聚合项返回：

- 稳定聚合键和通知类型。
- 房间号与房间标题。
- 相关成员 ID与当前显示昵称。
- 最新一条记录对应的文件名。
- 当前有效且未处理／未读的实际文件数量。
- 最新活动时间。
- 结果通知使用的服务端已读水位；待接收通知不返回可执行已读水位。

铃铛总数计算为：

- 每条待审批请求计 1。
- 每条未读聊天消息计 1。
- 每个当前待接收私密文件计 1。
- 每条未读拒绝结果计 1。
- 每条未读首次下载完成结果计 1。

聚合只改变列表行数，不改变总数。前端角标继续在超过 99 时显示 `99+`，内部保留真实数量。

### 7. 排序与分页

- 第一优先级：`join_request`。
- 第二优先级：`file_received`。
- 第三优先级：`chat_conversation`、`file_declined`、`file_downloaded`，按最新活动时间共同混排。
- 同一优先级先按活动时间倒序，再按稳定聚合键倒序，保证分页结果稳定。
- 扩展现有通知游标的优先级取值范围，旧的非法游标仍返回统一参数错误。
- 继续使用现有默认 30、最大 50 的聚合项分页限制。
- `totalCount` 必须基于完整有效集合计算，不受当前页、聚合数或分页游标影响。
- 分页期间业务状态变化允许下一次 REST 快照重新计算；客户端刷新第一页时必须替换旧分页缓存，不能把失效项继续保留。

### 8. 通知查询接口

继续扩展现有通知查询接口，不新建第二套文件通知列表。

文件聚合项新增字段必须采用可判别联合结构，前端按 `type` 缩小类型。聊天与审批现有字段和语义保持不变。

接口不得返回：

- 文件内部 ID、文件接收关系 ID、来源事件 ID。
- 私密编号、大小、MIME、存储名或下载地址。
- 其他接收者列表。
- 已读通知历史。

待接收与结果通知都可返回稳定前端键；只有结果通知返回不透明的已读水位。前端不得解析水位内容或自行推导数据库条件。

### 9. 聚合结果已读接口

新增当前用户聚合结果已读命令，采用 `POST /api/v1/notifications/read`。

请求至少包含：

- 聚合键。
- 查询接口为该聚合项返回的不透明已读水位。

规则：

- 只允许 `file_declined` 和 `file_downloaded` 使用；审批、聊天和 `file_received` 继续使用各自业务状态，不接受此命令。
- 服务端从会话获得用户 ID，不接受客户端指定目标用户。
- 服务端验证聚合键、水位格式、通知归属和当前有效业务权限。
- 只把该聚合组中不晚于水位的当前未读记录标记为已读。
- 查询响应生成之后产生的新记录不得被本次命令标记。
- 已读更新必须幂等；重复提交返回成功，不得产生错误角标或重复 SSE。
- 成功响应返回实际更新数量，便于前端调试，但前端仍以重新查询通知快照为权威。
- 无效水位、类型不支持或格式错误返回统一参数错误；越权或已失效目标不得泄露记录是否存在。

### 10. SSE 与跨标签页同步

- 继续只使用现有 `/api/v1/stream` 用户级连接。
- 文件变为可用、文件再次发送、接收关系变更和下载完成的既有 SSE 事件触发通知快照刷新。
- 前端只对会影响通知的文件事件刷新通知；上传进度和下载进度不得触发通知查询风暴。
- 连续相关事件沿用通知中心现有短时间合并刷新策略，避免一个批次多个文件导致多次并发查询。
- 已读命令成功后发布用户级 `notification.changed` 事件，使同一身份的其他标签页刷新。
- `notification.changed` 只携带安全机器事实，不携带翻译文案、文件名、私密编号或通知明细。
- SSE 是刷新提示，不是权威存储。断线、重连或丢事件后，REST 快照必须恢复正确状态。

### 11. 前端通知类型与展示

新增三个文件通知视图：

- 待接收文件：文件类图标、相关发送者头像／昵称、房间、最新文件名、待接收数量和最新时间。
- 已拒绝结果：结果状态图标、相关接收者头像／昵称、房间、最新文件名、拒绝数量和最新时间。
- 已下载结果：完成状态图标、相关接收者头像／昵称、房间、最新文件名、完成数量和最新时间。

展示规则：

- 整行使用可聚焦按钮语义，并提供完整双语无障碍名称。
- 不显示接收、拒绝、下载、全部已读或单独关闭按钮。
- 不复用审批按钮布局。
- 数量徽标显示聚合文件数，超过 99 使用现有 `99+` 规则。
- 长文件名使用现有抽屉宽度内的单行或双行省略，不扩张抽屉宽度。
- 桌面端沿用 420 像素抽屉；移动端沿用现有响应式抽屉规则。
- 只打开抽屉不得调用已读接口。

### 12. 点击与导航

#### 12.1 待接收文件

- 点击后关闭通知抽屉并进入对应房间。
- 不调用已读接口；通知继续存在，直到文件接收或拒绝。

#### 12.2 文件结果

- 点击时先使用该聚合项水位提交已读命令，再关闭抽屉并进入对应房间。
- 已读命令成功后立即刷新通知第一页及铃铛。
- 已读命令失败时保留抽屉并显示双语错误，不导航，避免用户以为结果已处理。
- 重复点击期间禁用该聚合项，防止并发提交。

#### 12.3 房间页面行为

- 目标为其他房间时导航到对应房间路由。
- 已在目标房间时不重新挂载整个页面，只关闭抽屉并刷新房间文件查询。
- 移动端若正在一对一聊天全屏，消费一次性文件通知导航状态后关闭聊天并显示文件区域。
- 一次性导航状态消费后从路由历史状态清除，刷新页面不得重复触发。
- 不自动切换共享／私密筛选，不自动展开、滚动、定位或高亮某个文件。
- 不自动执行接收、拒绝、创建下载任务或下载。

### 13. 本地化与错误边界

- 所有新增前端可见标题、预览、数量、按钮无障碍名称、加载与错误文案同时增加 `zh-CN` 和 `en` 翻译键。
- React 组件不得硬编码中文或英文通知文案。
- SSE 事件不携带最终用户文案。
- 后端新增错误只返回错误码、参数和内部原因；统一响应层根据 `Accept-Language` 翻译。
- 如需新增错误码，必须同步更新两种后端词典并通过词典完整性测试。
- 文件名、用户昵称、房间标题、JSON 字段、事件类型和数据库状态值不翻译。

### 14. 生命周期清理

- 房间进入销毁状态后，通知查询立即排除该房间记录，不等待物理清理完成。
- 房间关系清理事务必须显式删除该房间通知记录，删除顺序早于文件和成员记录。
- 清理任务统计增加通知记录总数和已清理数，保证失败重试时可诊断且幂等。
- 清理失败沿用现有房间清理重试状态，不增加独立通知清理调度器。
- 已读记录不提前单独归档；它们和未读记录一起随房间清理。
- 本阶段不提供七天文件通知历史。房间失效后，无论记录已读与否都不再展示。

### 15. 实施任务顺序

## Testing Decisions

### 测试原则

- 测试外部业务结果，不断言私有函数调用次数、具体 SQL 字符串、React 内部状态名或 CSS 像素。
- 状态机、权限、幂等、并发已读和生命周期属于复杂业务逻辑，必须有自动化测试。
- 视觉、抽屉宽度、移动端手感和真实导航由人工验收，不引入 Playwright。
- 复用现有通知服务、文件服务、生命周期服务和前端纯逻辑测试风格。

### 后端业务测试

至少覆盖：

1. 私密文件在保留、上传中不产生通知，完整上传可用后为每个待接收者各生成一次。
2. 共享文件上传完成不生成文件通知。
3. 上传失败、取消和过期不生成通知。
4. 已拒绝关系再次发送时投递代次增加，旧通知不复活，新待接收通知出现。
5. 被跳过的再次发送关系不增加代次、不生成重复通知。
6. 接收后待接收通知消失，但不生成上传者结果。
7. 拒绝后接收者待接收通知消失，上传者出现一条拒绝结果。
8. 重复拒绝不生成重复结果。
9. 下载流未完整写出、客户端中断、任务过期不生成完成结果。
10. 首次完整下载生成一条结果；重复完整下载只更新次数，不新增结果。
11. 上传者下载自己的私密文件和成员下载共享文件不生成结果。
12. 多文件、多接收者按约定聚合，列表行数与 `totalCount` 口径不同但都准确。
13. 不同房间、成员和结果类型不错误合并。
14. 排序严格为审批、待接收文件、聊天与结果，并在组内按活动时间倒序。
15. 通知游标跨三个优先级分页稳定，无重复或遗漏。
16. 非活动房间、过期房间、非活动当前成员、失效文件和旧投递代次不返回。
17. 文件相关成员离开不泄露额外权限，也不错误删除当前上传者仍可见的有效结果。
18. 聚合结果已读只更新当前用户、当前类型、当前房间和当前相关成员对应的水位范围。
19. 已读重复提交幂等。
20. 查询快照后新建的结果不被旧水位标记已读。
21. 待接收、聊天和审批类型不能调用文件结果已读命令。
22. 已读后同一用户收到 `notification.changed`，其他用户不收到。
23. 房间清理显式删除通知记录并更新清理统计；重复清理安全。
24. DTO 不返回文件内部 ID、私密编号、其他接收者、存储名或下载地址。

### 前端纯逻辑测试

至少覆盖：

1. 三种文件通知能被类型安全地区分。
2. 文件可用、再次发送、接收关系变化、下载完成和 `notification.changed` 会刷新通知。
3. 上传进度、下载进度与无关文件事件不刷新通知。
4. 文件聚合数量进入总角标并继续遵守 `99+`。
5. 待接收点击不调用已读；结果点击使用服务端水位调用已读。
6. 已读失败不导航，成功后刷新通知并导航。
7. 文件通知导航状态只消费一次，且不能被不完整路由状态伪造。
8. 移动端消费文件通知导航时关闭聊天，桌面端不改变当前聊天选择。
9. 简体中文和英文翻译键集合完全一致且无空文案。

### 构建验证

- `go test ./...`
- 前端目录运行 `bun test`
- 前端目录运行 `bun run build`
- 项目根目录运行 `make build`
- `git diff --check`

### 人工验收清单

1. 首页与任意房间页铃铛数量一致。
2. 私密文件上传中无通知，完成后接收者出现通知。
3. 多文件批次聚合一行，但角标按文件数增加。
4. 多接收者分别收到自己的待接收通知，不看到其他接收者。
5. 点击待接收通知只进入房间，不自动接收或下载，通知仍保留。
6. 在私密文件区域接收后，待接收通知消失。
7. 拒绝后接收者通知消失，发送者出现拒绝结果。
8. 首次完整下载后发送者出现下载完成结果，重复下载不增加通知。
9. 点击聚合结果后该组角标按实际数量减少，新到结果仍保留。
10. 同房间点击只刷新文件区；跨房间点击进入正确房间。
11. 移动端从聊天全屏点击文件通知后回到文件区域。
12. 房间失效或当前用户离开后相关通知消失。
13. 两个标签页中一处读取结果，另一处铃铛及时同步。
14. 审批排最前，待接收文件其次，聊天和结果按时间混排。
15. 切换简体中文和 English 后所有新增文案完整。

## Out of Scope

- 文件预览、缩略图、文本预览、PDF 或媒体播放。
- 聊天图片、附件、文件卡片和共享文件引用。
- 共享文件新增通知。
- 上传成功、上传进度、上传失败、下载开始、下载失败或重复下载通知。

- 通知抽屉内接收、拒绝、下载或其他文件业务按钮。
- 顶部 `message`、浏览器系统通知、声音、震动或桌面悬浮通知。
- 通知历史、已读历史、全部已读、七天文件通知归档。
- 文件删除、撤回、回收站、恢复申请与审批。
- 文件哈希、完整性校验、秒传、物理去重、HTTP Range、分块上传或断点续传。
- 管理后台、部署能力、深色主题或房间标题修改。
- 新 SSE 连接、WebSocket、轮询或外部消息队列。
- 旧开发数据库迁移、回填或专用清理脚本。

## Further Notes

- 本阶段的价值是补全私密文件协作的跨页面提醒，不是建设通用事件审计系统。
- 通知记录应保持最少数据；展示字段必须从当前权限下的房间、成员、文件和接收关系投影。
- 已读水位必须由服务端生成并视为不透明值。前端只能原样回传，不能解析或自行拼装。
- 如果实施中发现必须扩大到共享文件通知、文件定位、通知历史或新的文件状态，必须先更新本 PRD 并取得用户批准，不能顺手实现。
- 用户会自行删除现有 `data` 目录，因此实现只需保证新数据库结构正确，不需要兼容旧表数据。
