# 下载 Range、HEAD 与短时重放

## Problem Statement

下载接口当前将下载任务设计为一次性消费：任务从 pending 进入 streaming，完成后进入 completed，重复请求返回 409。浏览器和 NeatDownloadManager 同时捕获同一个下载 URL 时，前一个请求已经完成，后一个请求收到 409。当前接口还不解析 Range，无法兼容下载器的断点重试和区间请求，也没有 HEAD 探测能力。

## Solution

升级下载 HTTP 接口，支持单区间 Range、HEAD 和同一任务的 2 秒短时重放。无 Range 的完整下载返回 200；有效单区间返回 206；无效或多区间返回 416。相同 taskId 在传输开始后 2 秒内或完成后 2 秒内可以建立有限重放流，重放不重复下载计数和通知，新的 taskId 仍是新的下载操作。抽取后端内部区间读取能力，为未来断点续传扩展预留，不改变上传协议。

## User Stories

1. 作为浏览器用户，我希望浏览器和外部下载器重复请求同一 URL 时不立即失败，以便文件可以正常保存。
2. 作为下载器用户，我希望同一下载任务的短时重复请求只计一次下载，以便下载记录和通知准确。
3. 作为下载器用户，我希望请求文件前可以通过 HEAD 获取文件大小和类型，以便正确创建本地文件。
4. 作为下载器用户，我希望服务端声明支持 bytes Range，以便下载器决定是否启用断点能力。
5. 作为下载器用户，我希望请求 `bytes=0-`、`bytes=100-199` 或 `bytes=-500` 时得到正确区间数据。
6. 作为下载器用户，我希望有效区间响应使用 206 和正确的 Content-Range，以便客户端正确合并数据。
7. 作为下载器用户，我希望无效区间得到 416 和总长度提示，以便客户端重新计算区间。
8. 作为下载器用户，我希望多区间请求得到明确的不支持响应，而不是收到错误格式的完整文件。
9. 作为文件所有者，我希望 Range 重放不重复增加下载次数，以便动态记录准确。
10. 作为文件上传者，我希望首次私密文件下载通知只发送一次，以便通知中心不重复提示。
11. 作为房主，我希望文件移入回收站后旧下载任务立即失效，以便删除规则不被重放绕过。
12. 作为房间用户，我希望房间失效、成员失去权限或任务过期后无法继续重放文件。
13. 作为系统维护者，我希望重放流继续受全局、房间和用户并发限制，以便防止单个任务耗尽资源。
14. 作为系统维护者，我希望 Range 传输与文件存储读取解耦，以便未来扩展上传和下载断点续传。
15. 作为现有前端用户，我希望普通下载行为和下载进度通知保持不变。
16. 作为 API 调用者，我希望错误状态码、响应头和错误消息保持明确且可国际化。
17. 作为测试人员，我希望能够验证普通下载、Range、HEAD、重放、取消、过期和回收站边界。

## Implementation Decisions

- 只对同一个 `taskId + userId + roomId + fileId` 开启重放；新的下载任务不去重，仍然独立计数。
- 重放窗口固定为 2 秒：任务处于 streaming 时从首次 `startedAt` 计算；任务进入 completed 后从 `completedAt` 计算。重放不会刷新或延长窗口。
- 任务处于 pending 时，首个 GET/满足权限的下载请求负责原子地领取任务；streaming/completed 仅在重放窗口内允许重放；cancelled、failed、expired、文件不可用、回收站版本变化和房间失效均拒绝。
- 重放流必须进入现有下载并发注册表，继续遵守全局 50、房间 10、用户 2 的现有限制；同一 taskId 不再因为已有主流而无条件冲突，而是按独立传输流计数。
- 无 Range 的 GET 返回 200、完整文件内容和完整 `Content-Length`。
- 解析单个 `Range: bytes=start-end`：支持开放结束区间、前缀区间和后缀区间；正常化到文件大小范围后返回 206、`Content-Range: bytes start-end/total`、区间 `Content-Length` 和 `Accept-Ranges: bytes`。
- 多区间、语法非法、起点超出文件大小或无法归一化的 Range 返回 416，并返回 `Content-Range: bytes */total`；新增对应错误码和 zh-CN/en 翻译。
- GET/HEAD 都执行身份、房间成员、任务归属、文件状态和重放窗口校验。HEAD 只返回响应头，不打开内容流、不领取 pending 任务、不改变任务状态、不发送下载事件。
- 文件名、MIME、Content-Disposition、nosniff 等现有响应头继续保留；Range 响应只改变状态码、Content-Range 和 Content-Length。
- 区间传输流只读取请求范围，不能使用当前从文件起点读取到 EOF 的固定逻辑；存储层提供安全的区间读取/seek 能力，HTTP 层不直接依赖具体存储实现。
- 无 Range 完整流完成时标记任务完成；Range 流只有在区间结束于文件末尾时才允许完成任务。中间 Range 完成只结束该传输流，不重复完成任务、下载统计或通知。
- 重放流不重复记录 FileEventDownloaded、不重复更新私密文件首次下载通知、不重复改变接收状态；主流已有完成记录时重放只传输数据。
- 文件回收、取消下载和房间生命周期清理继续取消/失效所有相关活动流和任务。
- 为 Range 解析、区间响应和传输流抽取可测试的后端内部模块；该抽象只服务于本次下载和未来断点续传准备，不新增上传接口。
- 不实现跨进程/跨重启的区间完成集合，不新增上传分片协议，不改变当前前端上传行为。
- 不修改数据库表结构；优先复用现有 startedAt、completedAt、transferredSize、trashVersion 和任务状态字段。若实现需要新增字段，必须先更新本 PRD并重新确认。

## Testing Decisions

- Range 解析纯逻辑测试覆盖：无 Range、前缀、开放结束、后缀、边界值、空文件、多区间、非法语法和越界。
- 下载服务测试覆盖：主流领取、streaming 重放、completed 重放、2 秒窗口边界、重放不重复计数、重放不重复通知、取消/回收站/过期拒绝和并发上限。
- API 测试覆盖：GET 200、GET 206、HEAD 200、HEAD Range、416、Content-Range、Content-Length、Accept-Ranges、Content-Disposition 和过期错误。
- 文件内容测试必须验证区间字节准确，不能只验证状态码。
- 复用现有 Go 服务测试、API 测试和错误码词典测试风格；保留前端 Bun 单元测试和构建验证。
- 手动验证浏览器原生下载、NeatDownloadManager 重复捕获、Range 重试、文件删除/回收站期间请求和浅色/深色页面下载行为。
- 不引入 Playwright 或新的端到端框架。

## Out of Scope

- 不实现上传断点续传、上传分片协议或上传恢复 API。
- 不实现跨重启的分段完成集合、断点元数据持久化或客户端恢复记录。
- 不支持 multipart/byteranges 多区间响应。
- 不改变下载按钮、下载队列 UI 和现有业务权限规则。
- 不允许新的 taskId 在服务端自动合并或去重。
- 不修改文件内容、通知聚合规则或回收站业务规则。

## Further Notes

- 2 秒重放解决的是浏览器与外部下载器短时间重复请求，不是无限期复用下载 URL。
- `Range` 只解决 HTTP 传输区间能力；真正可靠的跨重启断点续传需要后续增加客户端和服务端区间状态模型。
- 需要特别关注 NeatDownloadManager 的并发 Range 请求；它们必须受现有并发限制，并且不能重复触发业务完成事件。
- 所有新增错误码需要同时补齐 zh-CN/en 翻译和词典测试。
