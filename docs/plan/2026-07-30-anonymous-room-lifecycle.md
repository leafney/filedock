# FileDock 匿名会话与房间生命周期 PRD

## Problem Statement

FileDock 当前只完成单服务基础架构、SQLite 连接、统一响应、多语言和版本页面，尚未形成可供用户实际使用的匿名身份与房间协作流程。浏览器无法建立可恢复的匿名身份，用户刷新或重新打开页面后没有稳定身份；房间也没有创建、加入、准入审批、成员管理、延期、解散、过期和清理状态。

原始 `LanShare_PRD` 将房间、文件、SSE 和聊天分散在多个阶段，其中按房间建立 SSE、事件持久化、Bearer Token 等设计已经不符合本轮确认结果。当前房间需求又依赖实时审批、在线状态和销毁通知，如果继续采用轮询，会产生两套临时实现并增加后续重构成本。

本阶段需要先交付安全、可恢复、可实时同步的匿名会话与完整房间生命周期，使用户能够通过浏览器创建或加入房间，并为下一阶段文件传输和聊天建立稳定业务边界。同时，规格必须足够具体，使不了解上下文的编码模型也能按任务顺序实现，不自行补充相互冲突的规则。

## Solution

建立以 SQLite 为唯一事实来源的匿名用户、会话、房间、成员、准入申请和清理任务模型，并在服务启动、业务事务、后台调度和 HTTP API 中统一维护状态。

浏览器首次使用时选择随机昵称或手工输入昵称，服务端创建全局唯一匿名用户和 30 天会话，并通过 `session_token` HttpOnly Cookie 下发 HS256 JWT。所有受保护 API 和全局 SSE 都同时校验 JWT 与数据库会话。刷新页面、重新打开浏览器和同一浏览器多个标签页均恢复同一匿名身份。

房间支持免验证、四位 PIN 和房主审批三种创建时确定的准入方式。用户可以拥有一个有效房间并加入最多五个其他有效房间；房间最多包含五十名有效成员。房主可以延期、踢人和解散，普通成员可以退出。解散或自然过期均进入十秒 `destroying` 窗口，再进入 `destroyed` 和持久化异步清理流程。

前端每个标签页只建立一条 `/api/v1/stream` SSE 连接。服务端按用户和房间定向推送审批、成员、在线状态、延期和销毁事件；不持久化事件，断线后通过 REST 快照恢复。SSE 只携带稳定机器字段，最终提示由前端当前语言的 i18n 资源生成。

本阶段同步把现有四位错误码一次性迁移为五位分类，并保持成功码 `200`。普通 HTTP 消息仍由后端根据 `Accept-Language` 本地化，SSE 提示由前端本地化。服务可选择加载用户证书直接监听 HTTPS，但首版仍允许 HTTP。

## User Stories

1. 作为首次访问者，我希望页面自动给出一个可用随机昵称，以便无需注册账号即可开始使用。
2. 作为首次访问者，我希望点击骰子更换随机昵称，以便选择更喜欢的代称。
3. 作为首次访问者，我希望手工输入昵称，以便使用自己容易识别的名称。
4. 作为用户，我希望昵称在整个服务的有效匿名用户中唯一，以便跨房间识别同一个人。
5. 作为用户，我希望系统拒绝视觉混淆、不可见控制字符和系统保留昵称，以减少冒充和恶意展示。
6. 作为用户，我希望修改昵称后所有当前有效房间立即显示新昵称，以便身份展示保持一致。
7. 作为用户，我希望刷新页面或关闭后重新打开浏览器时恢复原匿名身份，以便不中断房间关系。
8. 作为用户，我希望同一浏览器多个标签页共享匿名身份，以免每个标签页被识别成不同成员。
9. 作为用户，我希望会话默认保持三十天，以便局域网日常使用时不用频繁重新建立身份。
10. 作为用户，我希望接近过期的会话自动续期，以便持续使用时不会突然失效。
11. 作为用户，我希望可以重置匿名身份，以便清除当前身份并重新选择昵称。
12. 作为房主，我希望身份重置不能绕过解散房间规则，以免产生没有房主的有效房间。
13. 作为用户，我希望首页显示自己创建的有效房间，以便关闭页面后快速返回。
14. 作为用户，我希望首页显示自己加入的其他有效房间，以便在多个协作房间之间切换。
15. 作为用户，我希望最多拥有一个有效房间，以减少四位房间号被滥用。
16. 作为用户，我希望最多加入五个其他有效房间，以兼顾多房间使用和资源限制。
17. 作为房主，我希望创建房间时选择免验证、四位 PIN 或房主审批，以便控制谁能进入。
18. 作为房主，我希望房间默认采用免验证，以便最快完成局域网分享。
19. 作为房主，我希望创建后的验证方式保持不变，以免成员对准入规则产生误解。
20. 作为房主，我希望房间标题默认保存为“房间 + 四位房间号”，以便页面始终有明确标题。
21. 作为邀请者，我希望二维码只包含房间访问地址，不包含 PIN 或身份凭证，以免泄露验证信息。
22. 作为受邀用户，我希望打开链接后先看到房间标题和验证方式，再确认是否加入。
23. 作为受邀用户，我希望访问链接本身不会自动加入房间，以免误操作建立成员关系。
24. 作为已加入成员，我希望再次访问房间链接时直接恢复房间快照，以便快速回到房间。
25. 作为免验证房间的访客，我希望点击确认即可加入，以便减少操作步骤。
26. 作为 PIN 房间的访客，我希望使用四个数字输入格，并在输入第四位后自动验证，以便快速完成加入。
27. 作为 PIN 房间的房主，我希望 PIN 只保存为哈希且不会出现在 URL、二维码或日志中，以降低泄露风险。
28. 作为安全负责人，我希望连续错误 PIN 尝试被暂停，并按 IP 限速，以减少暴力猜测。
29. 作为审批房间的访客，我希望房主离线时仍能提交申请，以便房主稍后处理。
30. 作为申请人，我希望看到申请仍在等待、已批准、已拒绝、已取消或已超时，以便理解当前状态。
31. 作为申请人，我希望批准后自动成为成员并进入房间，以便无需重复提交加入操作。
32. 作为申请人，我希望拒绝、取消或超时后遵守明确冷却时间，以免误触造成重复请求。
33. 作为房主，我希望右上角通知图标显示待处理申请数，以便及时发现申请。
34. 作为房主，我希望点击通知图标查看申请列表并选择批准或拒绝，以便不被强制弹窗打断。
35. 作为房主，我希望房间最多五十名有效成员，以便服务资源保持可控。
36. 作为普通成员，我希望可以主动退出房间，以便结束自己的成员关系。
37. 作为房主，我希望不能通过普通退出留下无主房间，而只能明确解散房间。
38. 作为房主，我希望可以踢出成员，以便处理误加入或恶意用户。
39. 作为被踢成员，我希望先看到只能确认的明确提示，再返回首页，以便理解发生了什么。
40. 作为房主，我希望被踢用户在该房间生命周期内不能重新加入，以免反复干扰。
41. 作为房主，我希望一个房间只能延期一次且每次增加十二小时，以便生命周期可预测。
42. 作为房间成员，我希望房主延期后立即看到新的到期时间，以便不用刷新页面。
43. 作为房主，我希望解散成功后立即回到首页，以便明确操作已经完成。
44. 作为其他成员，我希望房间解散后页面立即锁定并显示十秒倒计时，以便知道房间即将释放。
45. 作为其他成员，我希望倒计时期间不能执行新操作，以免产生注定失败的数据变更。
46. 作为其他成员，我希望十秒结束后自动回首页，以便不继续停留在失效页面。
47. 作为成员，我希望房间自然过期与房主解散具有一致的页面体验，以便行为可预测。
48. 作为用户，我希望已经销毁的房间号短期内不立即分配给新房间，以免旧链接误入新房间。
49. 作为用户，我希望任一标签页打开时在所有有效房间显示在线，以便成员状态符合实际使用情况。
50. 作为用户，我希望全部标签页关闭后先显示暂离，六十秒后显示离线，以便短暂刷新不会立即被视为离线。
51. 作为房间成员，我希望成员状态通过绿、黄、灰圆点和文字表达，以便同时获得直观和可访问的信息。
52. 作为用户，我希望每个标签页只建立一条 SSE 连接，以便多房间状态复用同一实时通道。
53. 作为用户，我希望断线重连后页面重新获取权威快照，以便不依赖可能丢失的实时事件。
54. 作为简体中文用户，我希望房间、审批、踢出和销毁提示都使用简体中文。
55. 作为 English 用户，我希望相同场景显示完整 English 提示，而不是中英混杂。
56. 作为用户，我希望切换语言后新的 SSE 提示立即采用新语言，以便无需重建服务端会话。
57. 作为用户，我希望未知 SSE 事件或缺少翻译时看到安全通用提示，而不是翻译键或技术错误。
58. 作为 API 客户端，我希望业务成功码继续固定为 `200`，以便成功判断保持稳定。
59. 作为 API 客户端，我希望错误码前三位对应 HTTP 状态，后两位区分业务原因，以便快速分类。
60. 作为 API 客户端，我希望错误码和机器状态不随语言改变，以便程序分支稳定。
61. 作为运维人员，我希望 SQLite 连接或自动建表失败时服务拒绝启动，以免对外提供不完整功能。
62. 作为运维人员，我希望已有有效会话但 JWT 密钥丢失时服务拒绝启动，以免所有身份被静默重置。
63. 作为运维人员，我希望清理任务在服务重启后恢复，以免房间长期停留在中间状态。
64. 作为运维人员，我希望房间清理最多自动重试一次，以免故障任务无限消耗资源。
65. 作为未来管理员，我希望清理失败的状态和进度被持久化，以便后续页面查看和人工处理。
66. 作为部署人员，我希望可以给 FileDock 配置已有 TLS 证书直接提供 HTTPS，以便无需强制依赖反向代理。
67. 作为局域网首版用户，我希望没有证书时仍能使用 HTTP，以便低门槛部署。
68. 作为安全负责人，我希望文档明确 HTTP 无法防止同网段监听，以便部署者了解风险。

## Implementation Decisions

### 1. 范围与权威规则

- 本 PRD 是下一阶段的正式开发规格。它对本阶段匿名会话、房间和 SSE 的约定优先于早期 `LanShare_PRD` 中冲突的接口和阶段描述。
- 保留现有单服务架构、Fiber、GORM、SQLite、Wire、zlogx、统一响应、React、TanStack Query、i18next 和前端嵌入构建方式。
- 后端继续遵守 `api → biz → service → dal/model` 分层。API 只解析和返回，业务规则放在 biz，跨业务或基础能力放在 service，数据库读写放在 dal，持久化结构放在 model。
- 内部文件命名继续采用参考项目约定的后缀：接口层 `.api.go`、业务层 `.biz.go`、服务层 `.svc.go`、数据访问层 `.dal.go`、数据模型 `.model.go`、传输对象 `.dto.go`。不得把多个领域的大量逻辑塞入一个通用文件。
- SQLite 只通过现有 GORM 服务访问，不新增独立 SQLite 业务 service。
- 所有模型在 HTTP 服务监听前统一执行 GORM `AutoMigrate`。建表、索引或约束创建失败必须中止启动。
- 当前是开发阶段，不编写旧表结构或旧四位错误码的兼容迁移。

### 2. 深模块划分

- 会话安全模块：密钥加载与生成、JWT 签发解析、Cookie、数据库会话校验、滑动续期、撤销和身份重置。
- 昵称模块：候选池、随机分配、Unicode 规范化、合法性校验、全局唯一占用和释放。
- 房间领域模块：房间号分配、创建限制、快照、成员关系、延期、退出、踢人和权限判断。
- 房间准入模块：公开加入信息、免验证、PIN 验证、房主审批、申请状态和冷却规则。
- SSE 模块：连接注册、按用户和房间定向投递、心跳、慢连接处理和安全关闭。
- 在线状态模块：同一用户多连接计数、`online/away/offline` 状态机和延迟离线任务。
- 生命周期模块：自然过期扫描、十秒销毁状态机、清理任务调度、一次重试、启动恢复和房间号释放。
- 内存限速模块：按真实连接 IP 和动作维度计数、窗口过期和后台回收。
- 前端会话与房间模块：匿名身份引导、首页快照、房间准入、房间快照、SSE 分发和销毁/踢出交互。
- 各深模块向上暴露小而稳定的接口；业务层不能直接操作 SSE 连接 map、JWT 原始库调用或 GORM 查询细节。

### 3. 数据模型与约束

所有 ID 使用 26 位 ULID 字符串；所有持久化时间使用 UTC Unix 秒；所有状态字段使用稳定 English 机器值，不翻译。

#### 匿名用户

匿名用户至少包含：ID、显示昵称、昵称规范值、状态、设备提示、创建时间、更新时间、最后活动时间和身份失效时间。

- 用户状态至少包括 `active`、`revoked`、`expired`。
- 昵称规范值允许在身份释放后置空，并对非空值建立唯一索引。
- 昵称展示值用于当前界面；历史业务记录未来通过各自快照字段保留旧昵称。
- 会话过期清理、主动身份重置或撤销最后有效会话时，必须释放昵称规范值。

#### 会话

会话至少包含：ID、用户 ID、当前 JWT ID、创建时间、更新时间、最后活动时间、过期时间和撤销时间。

- JWT 声明至少包含用户 ID、会话 ID、JWT ID、签发时间、生效时间、过期时间、签发者和用途。
- 用途固定为匿名用户会话；不生成 Refresh Token。
- 数据库会话与 JWT 的用户 ID、会话 ID、JWT ID 必须完全一致。
- 会话撤销或续期更换 JWT ID 后，旧 JWT 不再通过数据库校验。

#### 房间

房间至少包含：ID、四位代码、标题、房主用户 ID、验证方式、PIN 哈希、业务状态、创建时间、到期时间、延期时间、开始销毁时间、计划销毁完成时间、销毁完成时间和房间号可复用时间。

- 业务状态固定为 `active`、`destroying`、`destroyed`。
- 验证方式固定为 `open`、`password`、`owner_approval`。
- 只有 `password` 房间允许存在 PIN 哈希；其他模式必须为空。
- 标题当前固定为 `房间 <code>`，真实持久化但无修改接口。
- 一个用户同时最多拥有一个 `active` 或 `destroying` 的房间；`destroyed` 不再计入拥有上限。
- 同一房间号在 `active`、`destroying`、冷却中的 `destroyed` 或清理失败状态下均不可分配。

#### 房间成员

成员至少包含：ID、房间 ID、用户 ID、角色、当前昵称快照、状态、加入时间、最后活动时间、离开时间、踢出时间和操作人 ID。

- 角色固定为 `owner`、`member`。
- 状态固定为 `active`、`left`、`kicked`、`destroyed`。
- 每个房间和用户只保留一条成员关系记录；普通成员退出后再次加入时重新激活该记录并更新时间。
- `kicked` 在同一房间生命周期内不可重新激活。
- 房主成员关系从创建到销毁始终存在，不能进入 `left`。
- 房间有效成员数只统计 `active`；最大值五十，包含房主。

#### 房主审批申请

申请至少包含：ID、房间 ID、申请用户 ID、申请昵称快照、状态、创建时间、过期时间、处理时间、处理房主 ID、取消时间和下一次允许申请时间。

- 状态固定为 `pending`、`approved`、`rejected`、`cancelled`、`expired`。
- 同一房间和用户最多一条 `pending`，由数据库部分唯一索引与事务检查共同保证。
- `approved` 必须与成员加入在同一事务完成；房间已满、已销毁、用户加入上限变化时不得批准。
- `rejected` 后十分钟可重试；`cancelled` 或 `expired` 后一分钟可重试。
- 每用户全局最多五条 `pending`，每房间最多五十条 `pending`。

#### 清理任务

每个被销毁房间建立一条持久清理任务，至少包含：房间 ID、状态、当前阶段、自动尝试次数、计划执行时间、开始时间、完成时间、最后错误、安全错误摘要，以及当前可统计关联数据的总量与已清理量。

- 状态固定为 `cleanup_pending`、`cleanup_running`、`cleanup_retry_waiting`、`cleanup_succeeded`、`cleanup_failed`。
- 自动尝试次数最大为二：首次和一次重试。
- 错误详情只写服务日志；持久字段保存可供管理员诊断且不包含密钥、PIN、JWT 或用户文件内容的摘要。
- 当前阶段清理成员关系和准入申请等已存在关联数据；未来文件、消息功能接入时扩展同一幂等清理流程。

### 4. 启动顺序与恢复

服务启动顺序固定为：加载配置、初始化日志、连接 SQLite、执行 AutoMigrate、校验或加载 JWT 密钥、构造业务模块、恢复生命周期任务、构造 HTTP/SSE 服务、开始监听。

- 任一必需步骤失败，进程记录错误并退出，不对外监听。
- 启动时将过期但仍标记有效的会话更新为过期并释放对应昵称。
- 启动时把已经到期的 `active` 房间转入新的十秒 `destroying` 窗口，使重新连接的成员仍能收到一致状态。
- 启动时把超过计划完成时间的 `destroying` 房间转为 `destroyed` 并创建或恢复清理任务。
- 启动时把异常中断的 `cleanup_running` 恢复为可执行状态，但不能重置已使用的尝试次数。
- 所有恢复操作必须幂等，连续重启不能重复增加延期、重复建立房主成员或突破清理重试上限。

### 5. JWT 密钥与 Cookie

- 签名算法固定 HS256，密钥必须是密码学安全随机生成的 32 字节内容。
- 默认密钥位置位于数据目录下的密钥子目录，文件名固定为 `jwt_signing.key`；目录权限建议为 `0700`，文件权限建议为 `0600`。
- 首次生成使用排他创建或等价原子方式，禁止两个并发启动进程互相覆盖。
- 密钥文件不存在时，先查询是否存在未撤销且未过期会话：存在则启动失败；不存在才生成新密钥。
- 密钥为空、长度不符或无法读取时启动失败，不自动替换。
- Cookie 名固定 `session_token`，属性固定包含 `Path=/`、`HttpOnly`、`SameSite=Lax`。
- HTTP 模式不设置 `Secure`；HTTPS 模式必须设置 `Secure`。
- Cookie 过期时间与数据库会话及 JWT 过期时间一致；撤销身份时发送立即过期的同名 Cookie。
- 用户 API 不接受 Bearer Token 作为 Cookie 的替代输入；未来管理员鉴权与用户会话保持独立。

### 6. 会话生命周期

- 创建会话前验证和规范化昵称，并在一个数据库事务中占用昵称、创建用户和创建会话。
- 如果 `POST /api/v1/sessions` 已携带有效会话，则幂等返回当前用户，不创建第二身份，也不使用请求体覆盖现有昵称。
- 任何受保护请求校验成功后更新最后活动时间；为避免每个请求写库，可按至少一分钟的时间粒度合并更新，但不能影响正确过期判断。
- 剩余有效期大于七天时不续期；不超过七天时生成新的 JWT ID，将数据库过期时间延长到当前时间加三十天，并重新设置 Cookie。
- 会话恢复返回用户 ID、昵称、会话过期时间、自己创建的有效房间摘要和最多五个已加入有效房间摘要。
- 改名在一个事务中检查新昵称、占用新规范值、释放旧规范值，并更新所有有效成员昵称快照；事务提交后向相关房间广播成员资料变化事件。
- 重置身份前检查是否拥有 `active` 或 `destroying` 房间；存在时返回业务冲突，不执行部分重置。
- 允许重置时，在事务中把普通成员关系变为 `left`、取消待审批申请、撤销该用户全部会话、释放昵称并把用户标记为 `revoked`。
- 重置事务提交后广播成员退出和申请变化事件，关闭该用户所有 SSE 连接并清除 Cookie。

### 7. 昵称规则

- 昵称输入先去除首尾普通空白，再执行 NFKC 规范化；规范化结果为空时拒绝。
- 长度按 Unicode 字符而非 UTF-8 字节计算，范围为二至二十。
- 唯一比较值在 NFKC 后执行 Unicode 大小写折叠；展示值保留用户规范化后的大小写。
- 禁止 C0/C1 控制字符、换行、制表、零宽字符、双向控制字符和其他会改变视觉顺序的格式控制字符。
- 当前系统保留名称至少覆盖 FileDock、system、admin、administrator、root，以及对应容易误解的中文名称；匹配同样使用规范值。
- 随机池由《水浒传》一百零八将和《三国演义》常用人物组成，候选数据只保存名称，不包含重复项。
- 随机接口不得返回已被有效用户占用或系统保留的名称。
- 候选耗尽时先生成 `<人物名>-<四位数字>`，极端情况下生成 `访客-<六位大写字母数字>`；每次都必须再次查重。
- 随机生成尝试达到内部上限仍无法取得唯一值时，返回稳定冲突错误，不死循环。

### 8. 房间创建与房间号

- 四位房间号是字符串，范围 `0001`～`9999`；必须保留前导零，`0000` 不分配。
- 使用密码学安全随机数选择候选，先随机尝试最多二十次；仍冲突时从随机起点扫描完整可用集合。
- 判断冲突时同时排除 `active`、`destroying`、未结束冷却、清理未成功和清理失败房间。
- 可用编号耗尽时返回稳定业务冲突，不降级为五位编号。
- 创建房间在单个事务中检查拥有上限、分配房间号、保存房间并创建房主成员关系。
- 默认到期时间为创建时间加十二小时；延期字段为空。
- 创建请求必须明确提交验证方式；缺失时使用 `open`。
- `password` 模式必须提交两次完全相同的四位数字 PIN，允许前导零；服务端使用 bcrypt 默认安全成本生成哈希。
- 非密码模式如果提交 PIN 字段应返回参数错误，避免调用方误以为已启用密码。
- 创建后本阶段没有修改标题、验证方式或 PIN 的接口。

### 9. 房间加入与准入

- 加入信息查询是公开接口，只返回 `roomCode`、`title`、`joinMode`；房间不存在、已进入销毁或已销毁时按不存在处理。
- 查询时如果请求附带有效会话，可额外返回当前用户是否已是有效成员，但不得返回其他成员信息。
- 所有实际加入操作必须具有有效会话。
- 加入事务统一检查：房间仍为 `active`、用户未被踢、用户不是房主、用户加入其他房间数未达五、房间成员数未达五十。
- 已是有效成员时所有加入方式均幂等返回房间快照，不重复新增成员或计数。
- 退出后重新加入必须重新经过当前房间验证方式。
- 免验证加入要求请求体携带用户明确确认值；缺少确认不得创建成员。
- PIN 验证使用常量时间语义的 bcrypt 比较。失败不泄露哈希信息，也不区分格式正确但密码错误之外的内部原因。
- PIN 连续失败计数按用户与房间组合保存在内存中；第五次失败后从该次失败时间起暂停一分钟，成功后清零。
- IP 限速独立于用户失败计数，两者任一触发都拒绝请求。
- 房主审批申请创建时保存十分钟过期时间并执行用户、房间 pending 上限和冷却检查。
- 房主批准必须在一个事务中锁定或重新校验申请、房间、成员容量与用户加入上限，写入成员后把申请改为 `approved`。
- 房主拒绝将申请改为 `rejected` 并设置十分钟后可再次申请。
- 申请人取消将申请改为 `cancelled` 并设置一分钟后可再次申请。
- 到期扫描将 `pending` 改为 `expired` 并设置一分钟后可再次申请。
- 对已经不是 `pending` 的申请重复处理返回稳定冲突，不能重复广播或重复加入。

### 10. 房间成员与权限

- 房间快照、成员列表、延期、退出、踢人、解散和二维码接口都要求有效会话。
- 房间快照和成员列表要求当前用户是有效成员；公开加入信息是唯一例外。
- 房间快照至少返回房间号、标题、状态、验证方式、到期时间、是否还能延期、当前用户角色、成员列表、当前在线状态、待处理申请数量（仅房主）和销毁截止时间（销毁中）。
- 房主延期仅允许在 `active` 且从未延期时执行；到期时间在原到期时间基础上增加十二小时，不是从当前时间重新计算。
- 普通成员退出在事务中将状态变为 `left`；房主调用同一接口返回冲突错误。
- 只有房主可以踢出当前有效普通成员；不能踢自己、不能踢非成员、不能重复踢。
- 踢出事务提交后，向被踢用户全部标签页发送私有事件，并向房间其他有效成员广播成员离开事件。
- 被踢用户仍可确认提示，但从事务提交时起已无权获取房间快照或执行房间操作。
- 二维码内容只包含当前请求可访问的页面地址 `/rooms/<code>`；不得包含 JWT、PIN、用户 ID 或内部房间 ID。

### 11. 房间销毁状态机

- 房主解散和自然过期复用同一状态机，原因分别为 `owner_dissolved` 和 `expired`。
- 从 `active` 进入 `destroying` 的事务必须记录开始时间和十秒后的销毁截止时间；重复触发不得延长截止时间。
- `destroying` 房间拒绝创建、加入、审批、批准、延期、成员退出、踢人以及未来的新上传或新下载。
- 房主解散接口在事务提交和事件发布成功排队后立即返回；前端使用历史替换返回首页，不等待十秒。
- 其他成员收到 `room.destroying` 后立即显示全页不可操作蒙层、本地化原因和服务端给出的绝对截止时间；倒计时根据服务端时间计算，不能只依赖收到事件后的本地十秒。
- 到截止时间时后台将房间变为 `destroyed`，把全部有效成员关系标记为 `destroyed`，将 pending 申请标记为 `expired`，并发送 `room.destroyed`。
- 其他成员收到事件或本地倒计时到期后停止房间查询、关闭房间相关操作并使用历史替换回首页。
- 当前阶段没有文件流，因此只实现业务状态和页面锁定；未来文件阶段必须在 `destroying` 时取消上传、允许已开始下载继续，并在 `destroyed` 时强制停止未完成下载。
- 房间进入 `destroyed` 时把房间号可复用时间设为该时刻加十分钟，并建立随机延迟十秒至五分钟的清理任务。

### 12. 清理任务与房间号释放

- 只有一个清理 worker 串行获取到期任务，避免多个房间同时清理造成 CPU 和 SQLite 写竞争。
- 领取任务时原子地从等待状态改为运行状态并增加尝试次数。
- 清理操作按阶段幂等执行；记录不存在视为已完成，不能因为部分数据上次已删除而失败。
- 当前阶段清理房间审批申请和成员等可销毁关联数据；房间主记录和清理任务记录保留到冷却结束。
- 首次失败后记录安全错误摘要，并重新随机安排十秒至五分钟后的唯一一次自动重试。
- 第二次失败后进入 `cleanup_failed`，不再被自动 worker 领取，房间号继续锁定。
- 清理成功进入 `cleanup_succeeded`。只有当前时间不早于房间号可复用时间时，才硬删除房间占号记录；否则由轻量释放扫描在冷却结束后删除。
- 服务关闭时停止领取新任务，允许当前短事务结束；不能把任务错误标记为成功。
- 后续管理员人工重试和安全释放失败房间号不在本阶段，但当前数据必须足以展示进度和错误状态。

### 13. 全局 SSE 协议

- 唯一入口为 `GET /api/v1/stream`，通过 `session_token` Cookie 鉴权。
- 每个浏览器标签页建立一条连接；前端使用已经引入的 `@microsoft/fetch-event-source`，请求携带同源 Cookie。
- 响应必须包含 `Content-Type: text/event-stream`、`Cache-Control: no-cache`、`Connection: keep-alive` 和 `X-Accel-Buffering: no`。
- 服务端每二十秒发送 SSE 注释心跳；心跳不作为用户提示事件。
- 事件 envelope 固定包含协议版本、事件 ID、`type`、发生时间和 `payload`。目标用户、目标房间和内部过滤字段不得序列化给客户端。
- 本阶段不写 `room_events` 表，不发送持久 sequence，不接受 `lastSeq`，不补发历史事件。
- 私有事件投递给目标用户当前全部连接；房间事件在发布时根据数据库中的有效成员确定目标用户，再投递到这些用户全部连接。
- 客户端不能通过查询参数订阅任意房间，服务端也不能信任客户端提交的角色或成员列表。
- 每连接使用有界缓冲。连接消费过慢导致缓冲写满时，服务端关闭该慢连接，使客户端重连并重新拉取快照；不得静默丢弃改变状态的事件后继续维持连接。
- 服务优雅关闭时停止接收新连接，通知连接结束并释放 Hub、在线状态和延迟任务资源。
- 会话撤销或过期时关闭该用户全部连接；重连鉴权失败后前端回到身份建立页。

### 14. 本阶段 SSE 事件

事件机器值至少包括：

| 事件类型 | 接收者 | 关键 payload |
|---|---|---|
| `session.revoked` | 当前用户全部标签页 | `reason` |
| `user.profile_changed` | 当前用户及其有效房间成员 | `userId`, `displayName` |
| `room.member_joined` | 房间有效成员 | `roomCode`, `userId`, `displayName`, `role` |
| `room.member_left` | 房间有效成员 | `roomCode`, `userId`, `displayName`, `reason` |
| `room.member_kicked` | 被踢用户全部标签页 | `roomCode`, `reason` |
| `room.member_presence_changed` | 房间有效成员 | `roomCode`, `userId`, `status` |
| `room.extended` | 房间有效成员 | `roomCode`, `expiresAt`, `extendedBy` |
| `room.join_request_changed` | 房主或对应申请人 | `roomCode`, `requestId`, `status`, `pendingCount`, `expiresAt` |
| `room.destroying` | 房间有效成员 | `roomCode`, `reason`, `destroyAt` |
| `room.destroyed` | 原房间成员的用户连接 | `roomCode`, `reason` |

- `reason` 和 `status` 都是稳定 English 机器值，不是最终提示语。
- 前端根据 `type`、`reason` 和动态参数选择翻译键；服务端不得在 SSE payload 中硬编码中文或 English 句子。
- 收到成员、审批、延期等事件时，前端对相关 TanStack Query key 做短防抖失效并重新获取快照，避免依赖事件 payload 拼出完整权威状态。
- 收到未知事件类型时不修改业务状态；记录开发诊断信息并重新获取当前会话或房间快照。

### 15. 在线状态

- 在线状态仅存在 Go 内存，不持久化为数据库权威值。
- Hub 为每个用户维护当前连接集合和最后一次全部断开时间。
- 第一条连接建立时状态变为 `online` 并向该用户所有有效房间广播统一状态变化事件。
- 多连接状态下关闭其中一条，剩余连接数大于零时不广播变化。
- 最后一条连接关闭时立即变为 `away` 并广播，同时创建六十秒延迟离线任务。
- 六十秒内任一连接恢复时取消对应离线任务并广播 `online`。
- 六十秒后仍无连接才变为 `offline` 并广播。
- 同一状态不得重复广播；延迟任务必须校验代次或断开时间，防止旧定时器把已重新上线的用户改成离线。
- 房间快照组装成员列表时，从在线状态模块读取三态；服务重启后所有用户初始为 `offline`，连接建立后恢复真实状态。

### 16. HTTP API 契约

所有 JSON API 使用现有统一响应结构：成功 `code=200`，失败为稳定五位错误码；`message` 由后端根据 `Accept-Language` 生成；`data` 使用 DTO，不直接序列化 GORM model。

#### 会话与昵称

| 方法与路径 | 鉴权 | 行为 |
|---|---|---|
| `GET /api/v1/nicknames/random` | 否 | 返回当前未占用随机昵称 |
| `POST /api/v1/sessions` | 可选 | 创建会话；已有有效会话时幂等返回当前身份 |
| `GET /api/v1/sessions/me` | 是 | 恢复身份、会话期限和首页房间摘要 |
| `PUT /api/v1/sessions/me` | 是 | 修改全局昵称并同步有效成员快照 |
| `DELETE /api/v1/sessions/me` | 是 | 重置匿名身份；拥有有效房间时拒绝 |

创建会话请求只接受 `displayName` 和可选 `deviceHint`。会话响应至少返回 `userId`、`displayName`、`sessionExpiresAt`。

#### 房间与成员

| 方法与路径 | 鉴权 | 行为 |
|---|---|---|
| `GET /api/v1/rooms` | 是 | 返回一个自建房间和最多五个已加入房间摘要 |
| `POST /api/v1/rooms` | 是 | 创建房间并成为房主 |
| `GET /api/v1/rooms/:code/join-info` | 否，可选识别会话 | 返回最小公开加入信息 |
| `POST /api/v1/rooms/:code/join` | 是 | 免验证或 PIN 加入；模式必须匹配 |
| `GET /api/v1/rooms/:code` | 是且为成员 | 返回权威房间快照 |
| `GET /api/v1/rooms/:code/members` | 是且为成员 | 返回成员及在线状态 |
| `POST /api/v1/rooms/:code/extend` | 房主 | 延期十二小时且仅一次 |
| `DELETE /api/v1/rooms/:code` | 房主 | 发起十秒销毁流程 |
| `POST /api/v1/rooms/:code/leave` | 普通成员 | 退出房间 |
| `DELETE /api/v1/rooms/:code/members/:userId` | 房主 | 踢出普通成员 |
| `GET /api/v1/rooms/:code/qrcode` | 是且为成员 | 返回不含秘密的 SVG 二维码 |

创建房间请求接受 `joinMode`，密码模式额外接受 `pin` 和 `pinConfirmation`。加入请求在 `open` 模式接受明确的 `confirmed=true`，在 `password` 模式接受四位 `pin`。不得用一个可选字段组合隐式猜测模式。

#### 审批

| 方法与路径 | 鉴权 | 行为 |
|---|---|---|
| `POST /api/v1/rooms/:code/join-requests` | 是 | 创建房主审批申请 |
| `GET /api/v1/rooms/:code/join-requests` | 房主 | 返回 pending 申请列表和数量 |
| `DELETE /api/v1/rooms/:code/join-requests/me` | 申请人 | 取消自己的 pending 申请 |
| `POST /api/v1/rooms/:code/join-requests/:requestId/approve` | 房主 | 原子批准并加入成员 |
| `POST /api/v1/rooms/:code/join-requests/:requestId/reject` | 房主 | 拒绝并设置冷却 |

申请人通过会话恢复、加入信息或房间相关查询取得自己当前申请状态；不增加第二条 SSE 或轮询专用协议。

### 17. 五位错误码与多语言

- 成功码是唯一例外，固定为 `200`。
- 所有错误码为五位整数，整数除以一百必须等于 HTTP 状态。
- 基础分类为：`400xx` 参数、`401xx` 身份/PIN、`403xx` 权限、`404xx` 资源、`405xx` 方法、`408xx` 超时、`409xx` 业务冲突、`429xx` 限速、`500xx` 内部错误。
- 删除现有 `3000`、`4000`、`4001` 等四位定义和兼容分支；调用点、测试、文档和翻译目录一次性同步替换。
- 错误注册表继续使用错误码、翻译键、HTTP 状态三元定义；业务逻辑返回错误码、插值参数和内部原因，不生成最终文案。

- 普通 API 响应不新增 `message_key`，浏览器直接显示后端已经本地化的 `message`。

### 18. IP 限速

- 限速器使用 Fiber 连接层得到的远端 IP，不解析或信任 `X-Forwarded-For`、`X-Real-IP` 等代理头。
- 使用内存固定窗口或等价可测试算法，键由动作和 IP 组成；重启后计数清空。
- 返回 `42901` 和 HTTP 429，并可返回标准 `Retry-After` 秒数。
- 默认规则固定为：

| 动作 | 限制 |
|---|---|
| 创建匿名会话 | 每 IP 每分钟 10 次 |
| 查询加入信息 | 每 IP 每分钟 30 次 |
| 创建房间 | 每 IP 每小时 5 次 |
| 免验证加入 | 每 IP 每分钟 20 次 |
| 创建房主审批申请 | 每 IP 每分钟 20 次 |
| PIN 验证 | 每 IP 每分钟 20 次 |
| 获取随机昵称 | 每 IP 每分钟 30 次 |

- 限速只保护对应入口，不能误伤版本接口、已有成员获取快照或 SSE 心跳。
- 限速 map 需要周期删除过期窗口，避免长时间运行后无限增长。

### 19. HTTPS/TLS

- HTTP 配置增加证书文件和私钥文件两个可选值。
- 两者都为空时在现有默认地址 `:8195` 提供 HTTP。
- 两者都非空时在同一地址提供 HTTPS，并启用 Cookie `Secure`。
- 只配置其中一个、文件不存在、证书不匹配或加载失败时启动失败。
- 不自动生成自签名证书，不自动跳转 HTTP 到 HTTPS，不同时监听两个端口。
- 文档必须提示：HTTP 只适合用户接受局域网明文风险的场景，不能防止同网段监听 PIN、Cookie 和未来文件内容。

### 20. 前端信息架构

- 保留 React Router，至少提供首页 `/` 和房间页 `/rooms/:code`。
- 未恢复有效会话时，首页显示昵称建立区域：随机默认昵称、骰子按钮、手工输入和确认按钮。
- 已恢复会话时，首页显示当前昵称、修改昵称、重置身份、创建房间、加入房间、自建房间摘要和已加入房间列表。
- 创建房间表单提供三种验证方式；密码方式显示两个四位 PIN 输入；其他方式不显示 PIN。
- 访问房间页时先查询加入信息：已是成员则加载快照；否则根据验证方式显示确认、四格 PIN 或申请界面。
- 房间基础页显示标题、四位房间号、当前用户角色、到期倒计时、成员列表、在线状态、二维码、延期、退出或解散操作。
- 房主右上角显示通知图标和待申请数量，点击后展示申请列表及批准/拒绝操作。
- 被踢用户显示不可关闭且只有确认按钮的本地化弹窗，确认后执行 `window.location.replace("/")` 或等价历史替换。
- 非房主收到销毁事件后显示全页蒙层、原因、不可下载/不可继续操作提示和十秒倒计时；到期后历史替换回首页。
- 房主发起解散成功后立即历史替换回首页，不显示十秒停留蒙层。
- 本阶段页面以功能完整、响应式和可访问为目标，不要求最终视觉稿；按钮、输入、弹窗和状态不能只靠颜色传达含义。

### 21. 前端状态与 SSE 处理

- TanStack Query 保存会话、首页房间列表、加入信息、房间快照、成员和审批列表等服务端状态。
- 表单、弹窗、倒计时和通知面板使用局部 React 状态；不得把 SQLite 权威状态长期复制到多个全局 store。
- 全局 SSE 客户端在有效会话存在时启动，在会话清除时停止；路由切换不创建第二条连接。
- 每个事件处理器只做必要的即时交互和 Query 失效：销毁、被踢、会话撤销立即处理；成员和审批列表通过短防抖重新拉取。
- SSE 自动重连采用有上限退避；每次连接成功或重连后重新获取会话快照，当前位于房间页时再获取房间快照。
- 页面卸载和用户重置身份时必须显式中止 fetch-event-source 请求，避免幽灵连接。
- 当前阶段不使用 IndexedDB 保存事件、身份或房间权威数据；已经引入的 `idb` 保留给后续聊天和缓存阶段。

### 22. 前端 i18n

- 将现有单一资源文件中的内容拆为独立简体中文文件和 English 文件；资源入口只组合语言、导出支持语言类型并执行结构约束。
- 简体中文资源是键结构基准，English 资源通过递归字符串形状类型约束保证键完全一致。
- React 组件禁止硬编码用户可见中文或 English；房间标题来自服务端用户数据，协议状态和代码属于机器值，不翻译存储。
- SSE 根据 `type`、`reason` 和 `params` 映射前端翻译键。动态时间、昵称等使用 i18next 插值，不通过字符串拼接形成整句。
- 开发环境缺少翻译键时在控制台给出键名和事件类型；生产环境显示当前语言的通用状态更新提示，不向用户显示裸键。
- 未知事件不得猜测执行逻辑；先失效并重新获取对应快照。
- 由于 SSE 不携带最终语言文案，切换页面语言不需要重建 SSE 连接，后续提示直接使用新语言。
- 普通 HTTP 业务错误继续展示后端本地化 `message`；浏览器网络、超时和 SSE 连接错误由前端翻译资源负责。

### 23. 日志和敏感信息

- 使用 zlogx 记录结构化启动、会话、房间状态转换、审批、SSE 连接计数和清理任务日志。
- 日志允许记录用户 ID、会话 ID、房间内部 ID、房间号、事件类型和错误码；禁止记录 JWT、Cookie、JWT 密钥、PIN 明文、PIN 哈希和完整敏感请求体。
- 鉴权失败日志不能回显原始令牌；PIN 失败只记录限速所需维度和结果。
- 内部错误 cause 只进入服务日志，统一响应只返回安全双语消息。
- SSE payload 中不得携带内部错误文本或清理失败详情。

### 24. 配置和待办边界

- 当前会话期限、续期窗口、房间人数、房间数量、审批等待、冷却、限速和清理延迟使用本 PRD 固定值，不在本阶段实现管理员动态配置。
- 现有 `todo.md` 继续记录管理员调整会话期限、重置 JWT 密钥、生成自签名证书、调整传输并发、调整限速、维护昵称候选和黑名单、自定义房间标题，以及查看和人工处理清理任务。
- 本阶段不得因为未来管理员需求提前建立无鉴权的管理接口。

## Testing Decisions

### 测试原则

- 按项目规则不采用全量 TDD；完成模块后为鉴权、安全边界、业务边界、并发事务和复杂状态转换补充自动化测试。
- 测试外部可观察行为和持久状态，不断言私有函数调用次数或具体 GORM SQL 文本。
- 时间、随机数、ID、密码比较和任务调度通过可替换依赖或可控时钟测试，禁止用真实十分钟等待。
- 数据库业务测试使用独立临时 SQLite，启用与生产一致的外键、WAL 相关必要设置和单连接约束。
- 测试不得依赖执行顺序，不复用真实数据目录或开发 JWT 密钥。

### 必须测试的后端模块

1. 五位错误码：每个定义除以一百等于 HTTP 状态；成功为 `200`；中英文键均存在；未知码安全回退。
2. 昵称：NFKC、大小写折叠、字符长度、控制/零宽/双向字符、保留词、并发唯一占用、释放与随机候选耗尽兜底。
3. JWT 密钥：首次生成、权限、已有有效会话但文件缺失、无有效会话重新生成、损坏文件启动失败。
4. 会话：创建、幂等创建、Cookie 属性、JWT/数据库双校验、JWT ID 不匹配、撤销、过期、七天边界续期和不使用 Refresh Token。
5. 身份重置：拥有房间时完全拒绝；允许时退出多个房间、取消申请、释放昵称、撤销会话和防止部分提交。
6. 房间号：前导零、随机冲突重试、扫描兜底、冷却占用、清理失败占用和全部耗尽。
7. 房间限制：一个自建房间、五个加入房间、五十名成员，并发加入时也不得超限。
8. 三种准入：模式匹配、明确确认、PIN 哈希、错误暂停、审批上限、重复申请、各类冷却、超时、批准事务和状态幂等。
9. 成员权限：房主不能退出、普通成员退出再加入、踢人、不能踢房主、被踢禁止重新加入、非成员禁止快照与二维码。
10. 延期：只有房主、只允许一次、基于原到期时间增加十二小时、销毁中拒绝。
11. 销毁状态机：手动和过期原因、固定十秒、不被重复请求延长、截止后成员和申请状态、冷却开始时间。
12. 清理任务：随机计划范围、单 worker 领取、崩溃恢复、幂等部分清理、首次失败重排、第二次失败停止、冷却前后释放。
13. SSE Hub：用户定向、房间成员过滤、多标签全投递、非成员不可收到、慢连接关闭、取消订阅无死锁、优雅关闭。
14. 在线状态：首连接上线、多连接关闭一条不变化、最后断开暂离、六十秒离线、旧定时器不能覆盖重连状态。
15. IP 限速：每条默认阈值、动作隔离、IP 隔离、窗口重置、过期回收、忽略代理头和 `Retry-After`。
16. TLS：无证书使用 HTTP、双文件使用 HTTPS、只配置一个或证书错误时启动失败、Cookie Secure 跟随模式。

## Further Notes

### 后续文件阶段必须继承的边界

- 下载授权必须同时满足“当前仍是房间有效成员”和“当前用户是文件发送者或指定接收者”；仅知道下载 URL 不构成授权。
- 服务端落盘采用 XChaCha20-Poly1305、每文件独立数据密钥和一 MiB 独立认证块；物理存储仍是一个密文文件，上传和下载均流式处理，不把完整大文件读入内存。
- 服务主密钥首次自动生成并保护每文件密钥；该方案是服务端静态加密，不得宣称为端到端加密。
- 上传默认并发为全局四、单房间二、单用户二；下载默认并发为全局五十、单房间十、单用户二。
- 下载名额不足时使用本 PRD 建立的全局 SSE 发送排队和名额可用事件；前端收到名额后尝试自动下载，浏览器阻止时显示本地化确认按钮。
- 以上内容只作为未来兼容边界，本阶段不得创建空文件接口、伪加密占位实现或文件专用第二条 SSE。

### 实施任务顺序

编码模型必须按以下顺序实施。每个任务完成后运行相关测试；进入下一个主要文件变更前，按照协作规则等待用户确认。

1. 迁移五位错误码和双语目录，拆分前端双语资源文件，确保现有版本接口继续通过。
2. 定义当前阶段数据模型、索引和 AutoMigrate 启动步骤，补充迁移启动测试。
3. 实现昵称规范化、候选池和唯一占用模块。
