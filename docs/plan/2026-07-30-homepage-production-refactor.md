# FileDock 正式首页重构 PRD

## Problem Statement

FileDock 当前前端已经实现匿名身份、房间创建与加入、房间生命周期、加入申请、SSE 和版本展示，但首页仍采用暗色卡片平铺布局。身份、房间列表、创建表单、加入表单和服务信息同时展开，视觉层级拥挤，无法承载后续文件、聊天、进度和队列功能。

已批准的首页雷达原型验证了新的视觉方向，但原型只使用模拟状态，并通过独立入口、独立源码、额外构建入口和截图文件存在于前端工程中。它不能作为正式功能继续保留，也不能让正式首页依赖原型代码。

当前前端还把路由、首页、房间页、共享组件和大量业务交互集中在单个应用文件中。继续直接修改会导致正式首页与房间详情逻辑互相影响，使低智能编码模型难以识别边界，也不利于测试和后续页面演进。

## Solution

将已批准的浅色雷达布局迁移为正式首页，并接入现有真实会话、房间、通知、SSE 和版本接口。正式首页左侧以当前匿名用户为中心，展示五个不可点击的装饰房间；右侧通过渐进式操作栏承载首次昵称、创建房间、加入房间、房间分区列表、通知和个人中心。

正式实现不复用模拟状态。首次昵称提交创建真实匿名会话；房间列表、创建、加入、解散、退出、申请审批、昵称修改、账户重置和版本信息均调用现有接口。会话响应补充真实用户创建时间，加入的房间由服务端按加入时间倒序返回。

同时重构前端模块边界：应用入口只负责路由、全局会话、SSE 和全局页脚；首页、房间详情页、通知中心、个人中心、房间操作、共享异步状态和纯逻辑工具分别实现。房间详情页本阶段只移动代码，不改变现有视觉或业务行为。

正式开发开始时删除全部临时原型入口、原型源码、预览截图和原型构建配置。Ant Design 因正式首页继续使用而保留，正式页面不使用的原型专属依赖必须移除。

## User Stories

1. 作为首次访问者，我希望看到明亮、清晰的首页，以便快速理解 FileDock 的主要用途。
2. 作为首次访问者，我希望右侧首先显示昵称选择，而不是全部房间操作，以便按顺序建立匿名身份。
3. 作为首次访问者，我希望系统自动提供真实随机昵称建议，以便不必自行构思名称。
4. 作为首次访问者，我希望点击骰子后获得新的真实随机昵称建议，以便快速选择合适名称。
5. 作为首次访问者，我希望手动输入昵称时左侧中心头像、中心昵称和右上角头像同步变化，以便确认最终显示效果。
6. 作为中文昵称用户，我希望头像显示第一个可见字符，以便快速识别身份。
7. 作为英文昵称用户，我希望头像显示大写首字母，以便头像规则直观一致。
8. 作为昵称为空的用户，我希望不能提交身份，并看到清楚的输入要求，以免发送无效请求。
9. 作为昵称已被使用的用户，我希望看到本地化错误提示并保留当前输入，以便修改后重试。
10. 作为未建立身份的用户，我希望右上角头像菜单只显示目标语言，以免打开依赖真实身份的个人中心。
11. 作为已建立身份的用户，我希望刷新或重新打开网页后恢复真实匿名身份，以便继续访问已有房间。
12. 作为已建立身份的用户，我希望左侧中心显示真实昵称，但不显示在线圆点和“在线”文案，以便画面保持简洁。
13. 作为用户，我希望中心周围始终看到五个装饰房间，以便感受到局域网分享空间的活跃氛围。
14. 作为用户，我希望装饰房间的位置、颜色和四位编号持续变化，以便雷达效果不显得机械。
15. 作为用户，我希望装饰房间不会公开或读取任何真实房间号，以免破坏房间访问安全模型。
16. 作为用户，我希望装饰房间不可点击，以免把视觉元素误认为真实入口。
17. 作为用户，我希望装饰房间逐个出现和消失，以免全部节点同时闪烁。
18. 作为用户，我希望每个装饰房间独立显示十至三十秒，以便变化自然且不过于频繁。
19. 作为用户，我希望随机节点避开中心用户、标题、边缘和其他节点，以便所有文字保持可读。
20. 作为减少动态效果的用户，我希望雷达波纹和节点漂浮尊重系统动画偏好，以免产生不适。
21. 作为已建立身份的用户，我希望通过右侧主按钮打开创建房间弹窗，以便首页不平铺复杂表单。
22. 作为房主，我希望创建免验证房间，以便知道房间号的用户直接加入。
23. 作为房主，我希望创建房主审批房间，以便逐个决定申请人是否可以加入。
24. 作为房主，我希望创建密码房间时输入两次四位密码，以便避免因输入错误创建不可用密码。
25. 作为房主，我希望两次密码不一致时立即看到提示，且创建按钮不可用，以免提交错误配置。
26. 作为安全关注者，我希望房间密码继续只保存 bcrypt 哈希，不能由房主、管理员或接口读取原密码。
27. 作为房主，我希望创建成功后直接进入新房间，以便继续邀请和管理成员。
28. 作为用户，我希望通过加入房间弹窗输入四位房间号，以便不在首页常驻显示输入表单。
29. 作为用户，我希望提交有效房间号后进入现有房间访问流程，以便由房间页继续处理免验证、密码或房主审批。
30. 作为用户，我希望无效房间号不能提交，以免进入错误页面。
31. 作为用户，我希望右侧房间列表明确分为“我的房间”和“加入的房间”，以便一眼区分房主与成员关系。
32. 作为没有自建房间的用户，我希望“我的房间”仍保留固定位置，以便页面结构不会跳动。
33. 作为没有自建房间的用户，我希望点击虚线空状态直接打开创建房间弹窗，以便快速创建。
34. 作为房主，我希望自己创建的房间始终显示在上方固定区域，以便快速找到和管理。
35. 作为加入多个房间的成员，我希望房间按加入时间倒序显示，以便最近使用的房间在最上方。
36. 作为用户，我希望普通房间项默认只显示房间号和身份，以便列表保持简洁。
37. 作为桌面用户，我希望鼠标移入房间项后看到操作浮层，以便按需显示进一步操作。
38. 作为房主，我希望悬停浮层提供进入和解散，以便从首页直接管理自建房间。
39. 作为成员，我希望悬停浮层提供进入和退出，以便从首页直接管理加入关系。
40. 作为手机用户，我希望点击房间项后从底部显示操作面板，以便在没有悬停能力时完成相同操作。
41. 作为用户，我希望解散或退出前必须二次确认，以免误操作。
42. 作为房主，我希望解散成功后留在首页，并看到房间正在释放，以便确认操作已生效。
43. 作为成员，我希望退出成功后房间从“加入的房间”移除，以便列表反映真实关系。
44. 作为用户，我希望 `destroying` 房间显示“正在释放”且禁用全部操作，以免进入已不可操作的房间。
45. 作为用户，我希望 `destroyed` 房间在 SSE 或查询更新后自动移除，以便列表无需手动刷新。
46. 作为房主，我希望右上角通知数量来自真实待处理加入申请，以便及时处理访问请求。
47. 作为房主，我希望点击通知图标后看到申请人昵称、房间号和申请过期时间，以便判断申请上下文。
48. 作为房主，我希望在通知面板直接同意或拒绝申请，以便无需先进入房间详情页。
49. 作为房主，我希望处理申请后未读数量和列表立即更新，以便避免重复操作。
50. 作为房主，我希望 SSE 收到申请变化后自动刷新通知，以便不依赖轮询。
51. 作为没有自建房间或没有申请的用户，我希望通知面板显示真实空状态且不显示虚假数量。
52. 作为已建立身份的用户，我希望头像菜单包含个人中心和目标语言，以便集中管理次要设置。
53. 作为用户，我希望语言菜单直接显示 `English` 或 `简体中文`，以便文字简洁。
54. 作为用户，我希望语言选择继续保存在前端本地存储，以便下次打开时保持偏好。
55. 作为用户，我希望个人中心展示真实昵称和头像，以便确认当前身份。
56. 作为用户，我希望个人中心允许修改真实昵称，以便更新自己在全部有效房间中的名称。
57. 作为用户，我希望个人中心展示真实注册时间，并按当前语言格式化，以便了解身份创建时间。
58. 作为用户，我希望个人中心完整展示服务状态、版本、分支、提交标识和构建时间，以便诊断当前实例。
59. 作为没有自建有效房间的用户，我希望账户重置前看到危险操作确认，以便理解身份和成员关系会被清除。
60. 作为仍拥有有效或正在释放房间的房主，我希望账户重置按钮被禁用并提示先解散房间，以免提交必然失败的操作。
61. 作为完成账户重置的用户，我希望页面回到首次昵称流程，以便创建新的匿名身份。
62. 作为所有页面的用户，我希望页面底部看到紧凑版本标识，以便快速识别部署版本。
63. 作为 Tag 构建的用户，我希望 Footer 只显示 Tag，例如 `v0.1.2`，以便版本表达清晰。
64. 作为非 Tag 构建的用户，我希望 Footer 只显示短提交标识，以便识别具体开发构建。
65. 作为版本元数据不可用的用户，我希望 Footer 显示 `dev`，以便不出现空白或误导信息。
66. 作为桌面用户，我希望悬停或聚焦 Footer 时看到完整版本 Tooltip，以便无需进入个人中心。
67. 作为移动用户，我希望点击 Footer 时看到完整版本 Tooltip，并能在个人中心再次查看，以便没有鼠标也能访问详情。
68. 作为房间页用户，我希望也能看到全局版本 Footer，但房间页其他布局和行为不发生变化。
69. 作为键盘用户，我希望按钮、房间项、菜单、Tooltip 触发器、Modal 和 Drawer 都有清晰焦点与正确焦点返回，以便完整操作首页。
70. 作为手机用户，我希望页面没有横向滚动，雷达、右侧内容、底部操作面板和 Footer 都不遮挡彼此。
71. 作为开发者，我希望正式首页不依赖临时原型入口或模拟字典，以便生产代码只有一套真实实现。
72. 作为开发者，我希望应用入口、首页、房间页、共享组件、业务 Hook 和纯工具分离，以便后续功能不会继续堆积到单文件。
73. 作为维护者，我希望房间详情页迁移模块后保持原有可观察行为，以便本阶段不会引入无关回归。

## Implementation Decisions

### 1. 交付边界

- 本阶段正式替换首页路由的视觉和交互；房间详情页只做模块迁移，不调整其暗色视觉、业务流程或接口调用。
- 所有页面新增共用版本 Footer。它是本阶段对房间页唯一允许的可见变化。
- 不新增数据库表，不执行数据库迁移。用户创建时间已经存在于用户记录中。
- 不新增全局通知接口。当前用户最多拥有一个有效自建房间，通知中心根据真实房间列表找到自建房间，再调用现有房间申请列表接口。

### 2. 临时原型清理

- 正式开发的第一项任务是删除独立原型 HTML 入口、原型 React 源码、原型本地文案、预览截图与浏览器快照。
- 恢复 Vite 为单一正式应用入口，删除仅用于原型构建的多入口配置。
- 正式组件不得导入、复制后再遗留或运行时依赖任何原型模块。已确认设计必须根据本 PRD 在正式模块中重新组织。
- Ant Design 和图标依赖因正式首页使用而保留。其他只由原型引用的依赖必须通过依赖搜索确认后删除，并更新锁文件。
- 清理时不得覆盖用户已有的忽略规则修改或旧静态构建产物删除；这些改动不属于本 PRD。

### 3. 前端模块边界

- 应用入口只负责路由组合、全局会话查询、全局 SSE 连接和全局版本 Footer，不直接实现首页或房间业务 UI。
- 首页页面模块负责组合雷达区域和操作侧栏，不直接实现请求细节。
- 房间详情页面及其成员、加入、审批、二维码、倒计时等组件从单文件迁移到房间功能模块；迁移前后 DOM 文案、请求、状态转换和导航行为必须保持一致。
- 共享模块包含错误提示、加载状态、PIN 四格输入、日期格式化和其他确实被首页与房间页共同使用的组件。不得为了“看起来模块化”创建只转发一层参数的无价值文件。
- 首页业务 Hook 负责会话、房间、通知和版本查询／Mutation 的组合。视图组件接收明确状态和回调，不直接散落 Query Key。
- 纯工具模块负责头像首字与稳定颜色、版本 Footer 标识选择、房间分组与排序映射、随机节点位置和生命周期计算。这些函数不得依赖 React，便于独立测试。
- 正式首页使用现有项目 i18n 资源。禁止保留原型本地字典，也禁止在 React 组件中硬编码中英文用户文案。

### 4. 样式与组件边界

- 正式首页使用 Ant Design 的 Button、Input、Avatar、Badge、Dropdown、Modal、Drawer、Tooltip、Form、Radio、Tag、Divider 和反馈组件。
- Ant Design 主题只作用于正式首页及共享新组件，不得无意改变现有房间详情页样式。
- 首页专用 CSS 必须使用页面根类或等效作用域隔离，不能用无前缀的全局选择器覆盖房间页。
- 桌面宽屏使用左侧自适应区域与约 300～340 像素右栏；平板压缩间距；手机改为上下布局。
- 页面使用浅色中性背景、深色正文和蓝绿色主强调色。交互动效使用 150～300 毫秒，节点淡入淡出可使用 200～500 毫秒。
- 所有交互元素必须具有可见焦点；悬停不得通过缩放造成布局位移。

### 5. 雷达与装饰房间状态机

- 中心用户使用真实会话昵称；未建立身份时使用当前昵称输入草稿。昵称草稿变化必须同步更新中心头像、中心昵称和右上角头像。
- 中心用户不显示在线圆点或在线文案。
- 装饰房间严格固定为五个，不包含中心用户。任意稳定时刻不得出现少于五个或多于五个节点；单个节点退出与补入的过渡期间允许短暂淡出，但状态数组仍保持五个记录。
- 装饰房间号在 `0001`～`9999` 之间随机生成并保留前导零，只用于视觉，不绑定导航或真实查询。
- 每个节点独立保存稳定唯一标识、随机颜色、百分比坐标、创建时间、到期时间和进入／退出阶段。
- 每个节点的可见生命周期随机为十至三十秒。一次只允许一个节点进入退出阶段；退出完成后立即在新坐标补入一个新节点。
- 坐标生成必须使用页面边界、中心椭圆禁入区和节点最小距离校验。达到最大尝试次数时选择候选中安全分数最高的位置，不能退回固定槽位。
- `prefers-reduced-motion: reduce` 下取消漂浮与波纹扩散，节点仍可无动画地按生命周期更新。
- 动态装饰内容标记为不可交互且不应反复打断屏幕阅读器；状态变化不使用 `aria-live` 广播。

### 6. 会话与首次昵称流程

- 应用继续使用 Cookie 会话和现有当前会话查询。加载期间显示匹配浅色布局的骨架或加载状态，不能闪回旧暗色首页。
- 当前会话返回未授权时进入首次昵称流程；其他错误显示统一本地化错误并提供重试。
- 首次进入时调用真实随机昵称接口；骰子按钮每次重新请求，不在前端使用硬编码人物数组。
- 建立身份前，通知按钮显示无数量的禁用状态；头像菜单只包含目标语言。
- 昵称确认调用真实创建会话接口。成功后更新会话缓存并启用房间、通知和全局 SSE 查询，不整页刷新。
- 会话响应增加 `createdAt` Unix 秒字段。创建、当前会话和修改昵称响应必须一致返回该字段。
- 会话服务加载用户时把真实创建时间传入会话视图；不得由前端推算、使用当前时间或保存在本地存储。

### 7. 创建与加入房间

- 建立身份后显示创建与加入两个主操作，完整表单只在 Modal 中呈现。
- 创建模式值继续使用现有 `open`、`password`、`owner_approval`，不得在前端定义不一致的替代机器值。
- 密码模式显示两组四格数字输入，允许前导零。只有两组都满四位且完全相同时才启用创建按钮。
- 服务端继续验证 `pin` 与 `pinConfirmation` 并只保存 bcrypt 哈希。不得新增返回 PIN、可逆 PIN、重设 PIN 或本地存储 PIN 的逻辑。
- 创建成功后刷新房间列表并导航到新房间；失败时 Modal 保持打开并使用统一错误翻译。
- 加入 Modal 只收集四位房间号。提交后导航到房间地址，由现有房间页继续查询加入信息并处理免验证、PIN 或房主审批，不在首页复制房间加入状态机。

### 8. 房间分区列表与操作

- 房间列表先按角色分为一个房主房间和多个成员房间，不依赖接口返回顺序决定分区。
- 上方“我的房间”始终保留一个固定位置。没有房主房间时显示固定高度虚线空状态，点击打开创建 Modal。
- 中间使用带本地化标题的 Divider 明确区分“我的房间”和“加入的房间”。
- 下方成员房间由服务端按成员加入时间倒序返回。房主房间无论创建时间如何都只显示在上方。
- 普通有效房间项默认仅显示房间号和“房主／成员”身份，不常驻显示操作按钮。
- 桌面端鼠标进入或键盘聚焦房间项后显示操作覆盖层。覆盖层不能改变房间项尺寸。
- 房主操作为进入和解散；成员操作为进入和退出。解散与退出使用明确的二次确认。
- 手机与其他无悬停环境点击房间项后打开底部 Drawer。Drawer 提供与桌面相同操作，并在关闭后把焦点返回触发项。
- 解散成功后房主保持首页，刷新房间与通知查询。退出成功后刷新房间查询。
- `destroying` 房间保留在原分区和原排序位置，显示“正在释放”，禁用点击、悬停覆盖层和底部操作。
- SSE 引起房间状态变化时刷新房间列表；房间不再返回后自动移除。

### 9. 通知中心

- 通知查询仅在存在真实会话且存在有效房主房间时启用。没有房主房间时数量为零，不发送无效申请列表请求。
- 通知 Badge 使用真实 `pendingCount`，不得使用固定模拟数字。
- 点击通知图标打开通知面板，展示申请人昵称、房间号、申请过期时间和同意／拒绝操作。
- 同意或拒绝期间只禁用正在处理的申请，防止重复提交；其他申请保持可操作。
- 操作成功后立即失效申请 Query 和房间 Query；错误使用统一本地化错误提示，不能乐观删除失败申请。
- 全局 SSE 已有 `room.join_request_changed` 处理，继续统一失效申请 Query。不得增加第二条 SSE 或通知轮询。
- 通知面板在桌面使用适合窄侧栏的弹层，在手机使用不溢出视口的 Drawer 或等效布局。

### 10. 个人中心

- 个人中心只对已经建立真实身份的用户开放。
- 显示真实头像、昵称、注册时间和完整版本信息。注册时间使用当前 i18n 语言格式化。
- 修改昵称调用现有更新会话接口。成功后更新会话缓存；其他房间中的昵称同步继续依赖后端已有 SSE。
- 账户重置使用危险按钮和二次确认。存在角色为房主且状态为 `active` 或 `destroying` 的房间时禁用按钮，并显示必须先解散房间的提示。
- 普通成员允许重置。成功后清理会话、房间和申请缓存，返回首次昵称状态；后端继续负责退出成员关系、取消申请和撤销身份。
- 完整版本区域展示服务状态、版本、Git 分支、完整提交标识和构建时间。加载失败显示本地化不可用状态，不影响个人信息操作。

### 11. 全局版本 Footer

- Footer 位于路由内容之后并使用普通文档流，不固定悬浮。应用容器使用最小视口高度，使短页面 Footer 靠近底部，长页面在内容之后自然出现。
- Footer 出现在首页、房间详情页和兜底路由页面。房间详情页只对 Footer 做暗色背景可读性适配。
- 构建元数据必须区分“HEAD 精确对应 Tag”和“非 Tag 构建”。精确 Tag 存在时简短标签只显示 Tag；否则只显示短 Git 提交标识；两者都不可用时显示 `dev`。
- Footer 不得把 Tag 和提交标识拼接成一个字符串。
- 桌面悬停或键盘聚焦 Footer 触发 Tooltip；移动端点击触发。Tooltip 展示服务状态、完整版本、分支、完整提交标识和构建时间。
- 版本接口失败时 Footer 显示 `--`，Tooltip 显示本地化“版本信息暂不可用”。如果接口成功但构建元数据缺失，则按 `dev` 回退。
- 全局 Footer 与个人中心复用同一个版本 Query 和同一套格式化工具，不重复请求或实现不同选择规则。

### 12. 后端小调整

- 会话 DTO 增加 `createdAt`，单位继续使用 Unix 秒并采用前端现有时间约定。
- 会话主体在创建、鉴权加载和昵称更新路径中携带真实用户创建时间，确保三个会话响应一致。
- 房间列表服务查询成员关系时按 `joined_at DESC` 排序。前端仍必须按角色分区，不能假设房主记录一定是第一条。
- 版本构建变量调整为只在 HEAD 精确匹配 Tag 时提供正式 Tag；非 Tag 构建依赖现有 Git 提交字段。命令行版本输出和版本接口必须保持字段完整。
- 所有接口继续使用统一响应层和现有五位错误码；新增响应字段不创建新成功结构。

### 13. 加载、错误与缓存

- 会话、房间、申请和版本使用稳定且集中定义的 Query Key。
- 当前会话是首页其他真实查询的启用条件；不得在未授权状态反复请求房间或申请。
- 房间操作成功后按数据影响失效房间、申请或会话 Query；不得通过整页刷新掩盖缓存问题。
- API 错误继续通过现有错误转换和 i18n 键显示。不得直接展示后端内部错误、英文异常对象或硬编码提示。
- 页面加载、空状态、错误、按钮处理中和禁用状态都必须同时实现简体中文与 English。

### 14. 实施顺序与提交边界

1. 更新并批准本 PRD 后，先删除临时原型文件和构建入口，确认正式入口仍能构建；该清理独立提交。
2. 在不改变行为的前提下拆分应用入口、房间页、共享组件和工具；运行现有构建与房间流程验证后独立提交。
3. 增加会话 `createdAt`、成员房间排序和精确 Tag 构建元数据，补充后端测试后独立提交。
4. 实现全局版本 Footer 和正式首页视觉基础，包括雷达纯逻辑及响应式样式，独立提交。
5. 接入真实首次昵称、房间分区、创建／加入 Modal、桌面／移动操作和个人中心，独立提交。
6. 接入真实通知审批与 SSE 刷新，独立提交。
7. 完成中英文、可访问性、桌面与移动浏览器验收，修正问题后提交最终结果。

每个阶段只暂存本阶段相关文件，不得把用户已有忽略规则修改或静态构建产物删除混入提交。提交信息必须遵循项目 Conventional Commits 规则，并在提交正文引用本 PRD 的仓库相对路径。

## Testing Decisions

- 测试关注用户可观察行为、数据契约和复杂状态，不测试内部组件名称、CSS 类名或普通静态展示快照。
- 不采用全面 TDD。只为后端响应与排序、纯逻辑边界、危险操作和复杂状态变化编写自动化测试。
- 后端会话测试必须验证创建、当前会话和昵称更新都返回相同真实 `createdAt`，且不是请求当前时间伪造值。
- 后端房间测试必须创建时间不同的成员关系，并验证成员房间按加入时间倒序；同时验证前端不能依赖房主记录顺序。
- 版本构建逻辑测试或可重复脚本检查必须覆盖：精确 Tag、非 Tag 有提交标识、元数据缺失三种结果。
- 前端增加轻量 TypeScript 测试能力，用于纯函数和状态算法，不为 Ant Design 组件本身重复测试。
- 头像工具测试覆盖中文、英文大小写、前后空格、空字符串和 Unicode 可见字符。
- 版本标签工具测试覆盖 Tag 优先、非 Tag 提交标识、`dev` 回退、接口失败 `--`，并验证不会拼接 Tag 与提交标识。
- 房间分组工具测试覆盖：只有房主、只有成员、两类同时存在、房主空槽、多个成员排序、`destroying` 禁用状态。
- 雷达状态测试使用可注入时钟和随机源，覆盖固定五个节点、编号前导零、十至三十秒期限、一次只退出一个、补入新随机坐标、中心禁入区、节点最小间距和最大尝试回退。
- 账户重置 UI 状态测试覆盖房主有效房间、房主正在释放房间、普通成员和无房间四种情况。
- 通知逻辑测试覆盖无房主房间不请求、真实数量、同意成功、拒绝成功、失败不删除以及 SSE Query 失效。
- 运行全部现有 Go 测试、前端 TypeScript 检查和 Vite 正式单入口构建。
- 使用 `playwright-cli` 的持久化可见浏览器与固定 Profile 验证约 1440×900 桌面和 390×844 手机视口。
- 浏览器验收至少覆盖：首次随机昵称、手动昵称三处联动、会话创建、头像菜单差异、语言切换、创建三种房间、两次 PIN 校验、加入导航、房间分区、空房主槽、桌面悬停操作、手机底部操作、解散／退出确认、`destroying` 禁用、通知审批、个人中心、重置限制、Footer Tooltip 和中英文。
- 连续观察雷达至少三十一秒，验证节点保持五个、至少发生一次独立替换、坐标变化且没有覆盖中心或标题。
- 检查浏览器控制台、网络失败和无障碍焦点返回，不允许保留 React 警告、Ant Design 弃用警告、404 资源错误或横向滚动。
- 房间详情页执行回归检查：加入三种验证方式、成员列表、申请处理、二维码、延期、退出、解散、踢出确认和十秒销毁蒙层的行为保持不变。

## Out of Scope

- 不重设计房间详情页、成员列表、加入验证页、二维码、解散蒙层或房间内通知面板的视觉。
- 不实现文件上传、下载、排队、聊天、文件消息或相关 SSE UI。
- 不读取或展示真实局域网房间作为雷达节点。
- 不增加头像上传、头像图片字段或服务端头像资源。
- 不修改房间标题，不实现自定义房间名称。
- 不实现查看原 PIN、可逆 PIN、PIN 重设或 PIN 本地存储。
- 不新增通知聚合后端接口，不新增第二条 SSE，不增加定时通知轮询。
- 不改变 Cookie、JWT、会话三十天有效期、房间生命周期或清理重试规则。
- 不进行全站 Ant Design 改造；房间详情页继续使用现有样式系统。
- 不提交临时原型入口、模拟数据、原型截图或浏览器快照作为正式产品资源。

## Further Notes

- 本 PRD 是已批准视觉原型的正式接入规格。原型只提供视觉参考，任何模拟数字、模拟房间、模拟注册时间或模拟操作结果都不能迁移到生产逻辑。
- 由于该 PRD 可能交给低智能模型执行，实施时必须严格按顺序完成并验证每一阶段，不能一边保留旧单文件实现一边复制出第二套长期并存逻辑。
- 模块拆分的目标是形成稳定职责边界，而不是追求文件数量。共享逻辑只有在存在真实复用或独立测试价值时才提取。
- 首页装饰房间的四位编号看起来像真实房间，因此必须继续保持默认光标、无悬停反馈和不可点击语义；真实加入只能通过右侧加入入口完成。
- 全局 Footer 的版本信息来自现有版本接口。Footer 与个人中心必须共享缓存，不能因为显示在两个位置而产生两次独立请求。
- 正式实现过程中如果发现需要改变本 PRD 的接口、范围或已确认交互，必须先更新 PRD 并取得用户批准后再继续。
